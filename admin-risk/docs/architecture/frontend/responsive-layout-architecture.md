# 响应式布局与跨视口稳定性架构

状态：`active`  
适用工程：`admin-risk`  
适用场景：桌面研究、交易、策略管理、风险管理及金融 AI 工作台  
文档权威：响应式布局、页面壳层、视口支持、滚动与溢出治理的唯一主文档

## 1. 文档定位

本文档解决平台在不同显示器、浏览器视口、系统缩放和浏览器缩放下出现的系统性布局失稳问题，包括：

- 组件错位、挤压、重叠或漂移。
- 底部操作区、浮层或固定元素遮挡正文。
- 页面背景、卡片边界和模块衔接断裂。
- 表格、图表、筛选器和操作区在中间宽度失效。
- 同一页面只在少数设计稿尺寸下正常。
- 页面整体滚动与内部滚动互相竞争。
- 为单个分辨率增加的 CSS 补丁影响其他页面。

专业定义：

> 平台缺少统一的响应式布局体系，导致跨视口布局稳定性、内容重排、滚动上下文和视觉连续性不足。

本文档不定义颜色、字体、圆角和品牌视觉；这些仍由 `../../design/platform-ui-guidelines.md` 管理。共享组件抽取和主题边界仍由 `../shared-ui-governance.md` 管理。

## 2. 核心目标

响应式治理的目标不是让所有屏幕呈现完全相同的像素位置，而是保证：

1. 信息层级稳定。
2. 关键操作始终可访问。
3. 空间不足时能够有序换行、降列、折叠或局部滚动。
4. 不出现非预期遮挡、裁切、重叠和结构断裂。
5. 同类页面使用同一页面壳层、间距和响应规则。
6. 页面行为由容器约束和内容需求决定，而不是依赖某个显示器型号。
7. 后续页面改造可以被自动化检查和截图回归验证。

## 3. 术语与测试记录

### 3.1 物理屏幕不等于网页视口

不得使用“15 英寸笔记本”“27 英寸显示器”作为布局验收依据。网页布局由 CSS 像素视口决定，并受到以下因素影响：

- 屏幕分辨率。
- Windows／macOS 系统缩放。
- 浏览器缩放。
- 浏览器工具栏、侧边栏和开发者工具占用。
- 设备像素比。
- 字体加载和系统字体差异。

测试记录必须至少包含：

```text
Viewport: 1536 × 754 CSS px
Browser zoom: 100%
OS scale: 125%
Browser: Chrome
Sidebar: expanded
```

### 3.2 关键术语

- **Viewport**：浏览器用于页面布局的 CSS 像素区域。
- **Breakpoint**：页面结构发生离散变化的阈值。
- **Reflow**：内容在空间变化时重新排列。
- **Overflow**：内容超出容器边界后的处理。
- **Scroll owner**：某一方向滚动行为的唯一责任容器。
- **Page shell**：页面标题、工具栏、摘要、主体和底部操作区的标准骨架。
- **Container query**：组件根据自身容器宽度而不是全局窗口宽度响应。
- **Layout integrity**：页面在约定视口中保持无碰撞、无遮挡、可读和可操作。

## 4. 支持范围与测试矩阵

### 4.1 产品定位

平台继续采用桌面工作台优先策略，不以手机端完整适配为当前目标。

正式支持范围：

- 最小目标视口宽度：`1280 CSS px`。
- 主要设计与验收区间：`1366–1920 CSS px`。
- 超宽屏验证：`2560 CSS px`。
- 小于 `1280px` 时允许进入受限桌面模式，但不得出现组件重叠、关键操作不可达或正文被遮挡。

### 4.2 宽度矩阵

| 级别 | 视口宽度 | 主要目的 |
|---|---:|---|
| Compact | 1280 | 最小正式桌面工作区、分屏窗口 |
| Common Laptop | 1366 | 常见 Windows 笔记本 |
| Standard | 1440 | 标准办公工作区 |
| Scaled Desktop | 1536 | 1920 分辨率配合 125% 系统缩放的常见结果 |
| Large | 1680 | 中大型显示器 |
| Full HD | 1920 | 标准全高清桌面 |
| Ultrawide | 2560 | 超宽屏和多栏扩展验证 |

### 4.3 高度矩阵

至少覆盖：

- `720px`
- `768px`
- `864px`
- `900px`
- `1080px`

高度测试用于发现底部遮挡、固定栏冲突、弹窗超高和嵌套滚动问题。

### 4.4 缩放矩阵

核心页面至少验证：

- 浏览器缩放：`90%`、`100%`、`110%`、`125%`。
- Windows 常见系统缩放：`100%`、`125%`、`150%`，记录最终 CSS 视口。

系统缩放不是独立 CSS 断点来源；最终仍以浏览器报告的 CSS 视口和可操作结果验收。

### 4.5 浏览器范围

当前最低范围：

- Chrome 当前稳定版。
- Edge 当前稳定版。

Safari 和 Firefox 可作为兼容性观察项，但在正式纳入前不得宣称已支持。

## 5. 布局架构分层

```text
Application Shell
└─ Module Shell
   └─ Page Shell
      ├─ Page Header
      ├─ Context / Filter Toolbar
      ├─ Summary Region
      ├─ Primary Work Region
      ├─ Secondary / Records Region
      └─ Optional Bottom Action Region
         └─ Business Blocks
            └─ Shared Layout Primitives
```

### 5.1 Application Shell

负责：

- 顶部导航、侧边栏和主内容区的整体尺寸关系。
- 应用级唯一纵向滚动策略。
- 侧边栏展开／折叠后的可用宽度计算。
- 全局浮层、弹窗和通知的层级基座。
- 主内容区的 `min-width: 0` 和 `min-height: 0` 等收缩条件。

不得负责：

- 具体业务页的列数。
- 图表和表格的内部布局。
- 某个策略页面的绝对位置。

### 5.2 Module Shell

负责：

- 模块标题和模块级页签。
- 模块内统一内容边距。
- 模块加载、错误和权限边界。
- 模块级顶部工具栏的稳定位置。

同一模块不得存在多套互不兼容的内容宽度和滚动规则。

### 5.3 Page Shell

负责：

- 页面标题、说明和主操作的排列。
- 筛选器、上下文工具栏和摘要区的响应行为。
- 页面业务区块的顺序、间距和主次关系。
- 固定或粘性底部操作区的正文空间预留。
- 页面级空数据、加载和错误状态的结构稳定性。

页面壳层应通过共享布局原语实现，不允许每个页面重新建立一套高度和滚动体系。

### 5.4 Business Block

负责：

- 一个明确业务区域内部的布局。
- 图表、表格、表单或摘要在自身容器内的响应行为。
- 向 Page Shell 声明合理的最小宽度和最小高度。

不得：

- 直接修改应用主内容区尺寸。
- 通过全局选择器影响其他页面。
- 使用固定坐标依赖某个分辨率。

## 6. 布局所有权矩阵

| 决策 | 唯一责任层 |
|---|---|
| 顶部栏、侧边栏、主内容尺寸 | Application Shell |
| 页面外边距和主要纵向滚动 | Application／Module Shell |
| 页面标题、工具栏、摘要和主体顺序 | Page Shell |
| 页面区块列数与降列 | Page Shell |
| 组件内部重排 | Business Block／基础组件 |
| 表格横向滚动 | Table 容器 |
| 图表 resize | Chart 容器 |
| 固定底栏正文预留 | Page Shell |
| 弹窗和抽屉最大宽高 | Overlay 基础组件 |
| 视觉 token | UI 设计规范／主题层 |

禁止多个层级同时计算同一高度、同时控制同一方向滚动或同时覆盖同一定位偏移。

## 7. 页面容器和间距

### 7.1 页面宽度

业务工作台默认使用可用工作区，不设置限制数据展示的窄版全局 `max-width`。

允许：

- 首页、登录页和品牌说明区使用内容最大宽度。
- 业务页面中的单个阅读型区块设置局部最大宽度。
- 超宽屏上通过内部栅格、合理列宽和局部最大宽度防止内容被无限拉长。

禁止：

- 为适配某台显示器给整个业务页面写固定宽度。
- 使用固定 `left` 偏移对齐侧边栏。
- 通过负 margin 抵消应用壳层边距。

### 7.2 页面边距

页面边距应由统一 token 控制，并可在紧凑桌面下降级：

```text
Compact: 16px
Standard: 20px
Large: 24px
```

具体实现可使用 CSS 自定义属性和 `clamp()`，但不允许各页面自行发明无规则边距。

### 7.4 LESS 预处理边界

当前 `admin-risk` 页面样式主要通过 LESS 编译。实现响应式宽度时必须考虑 LESS 与现代 CSS 函数的边界：

- `clamp()` 和 Grid 的 `minmax()` 可作为响应式表达式使用，但修改后必须通过 Vite 实际编译验证。
- 不在 LESS 文件中直接使用复杂 `min()` / `max()` 表达式，尤其是包含 `calc()`、百分比减法或 CSS 变量的写法。
- 需要“最大宽度 + 可用宽度”时，优先拆成 `width: calc(...); max-width: ...`。
- 需要“小元素不超过某宽度”时，优先拆成 `width: 100%; max-width: ...`。

错误示例：

```less
width: min(100% - calc(var(--page-gutter) * 2), 2040px);
```

正确示例：

```less
width: calc(100% - calc(var(--page-gutter) * 2));
max-width: 2040px;
```

这类错误会在 Vite dev server 中表现为 LESS 编译 overlay，不应进入后续视觉验收阶段。

### 7.3 栅格

采用 CSS Grid／Flex 的内容驱动布局：

- 指标卡使用 `auto-fit`／`minmax` 或明确的 4→3→2→1 降列规则。
- 双栏图表或执行区必须声明每栏最小宽度。
- 表格和主图需要完整宽度时独占一行。
- 不为了底边视觉对齐强制不同信息量区块等高。
- 不使用绝对定位实现业务区块主布局。

建议的通用最小宽度只是初始基准，最终应结合真实内容验证：

| 区块 | 建议最小宽度 |
|---|---:|
| 指标卡 | 220–260px |
| 标准表单列 | 280–320px |
| 普通图表 | 420–480px |
| 主分析图表 | 560–640px |
| 双腿执行参数区 | 360–420px |
| 详情侧栏 | 320–380px |

## 8. 断点策略

### 8.1 断点由结构变化决定

不得因为现有设计稿恰好是 1440px 或 1920px 就直接把该数字当作唯一断点。

断点应在以下情况触发：

- 页头标题与操作区无法保持可读间距。
- 工具栏控件低于最小可用宽度。
- 图表低于其最小可读宽度。
- 双栏区域无法保持业务完整性。
- 标签或页签需要换行、滚动或折叠。

### 8.2 推荐宽度区间

统一命名用于设计和实现沟通：

```text
compact: 1280–1439
standard: 1440–1679
large: 1680–1919
wide: 1920+
```

这些区间不是要求所有组件使用同一媒体查询。局部组件优先依据自身容器宽度响应。

### 8.3 Container Query 优先场景

以下组件优先考虑 Container Query：

- 可放在主区或侧栏的摘要组件。
- 侧边栏展开／折叠后宽度变化明显的业务区块。
- 可在不同页面复用的图表卡和指标卡集合。
- 分屏或多面板工作区中的独立组件。

全局媒体查询主要负责 Application Shell 和 Page Shell 的结构变化。

## 9. 高度与滚动架构

### 9.1 单一主要纵向滚动

原则上整个应用只有一个主要纵向滚动容器。

允许的局部滚动：

- 数据表格横向滚动。
- 明确高度的日志、订单流或长列表区域纵向滚动。
- 弹窗和抽屉内容在最大高度内滚动。
- 独立研究面板在产品明确要求下滚动。

禁止：

- 页面、页面主体、卡片和表格同时拥有纵向滚动条。
- 通过 `overflow: hidden` 隐藏无法到达的内容。
- 多层 `height: 100%` 但父级没有明确高度。

### 9.2 视口高度

禁止业务页面随意使用：

```css
height: 100vh;
height: calc(100vh - 64px);
```

Application Shell 可集中处理可用高度。业务页面优先使用文档流、Flex／Grid 和 `min-height: 0`，只在明确的工作台区域使用受控高度。

需要考虑动态视口时，优先在壳层统一评估 `dvh` 等现代单位，不允许各页面分别计算。

### 9.3 固定底部操作区

固定或粘性底栏必须满足：

- Page Shell 是唯一所有者。
- 正文预留不小于底栏实际高度的空间。
- 小高度视口下底栏不能覆盖最后一行表格或表单。
- 操作区内容过多时允许换行或进入更多菜单。
- 不使用任意高 `z-index` 掩盖结构问题。

## 10. Overflow、定位与层级

### 10.1 Overflow

- 页面整体不得出现非预期横向滚动。
- 超宽表格由表格容器提供横向滚动。
- 页签可使用横向滚动或折叠菜单，不压缩到不可识别。
- 图表不得通过裁切坐标轴、图例或 Tooltip 掩盖宽度不足。
- `overflow: hidden` 只能用于明确的视觉裁切，不得用于掩盖布局缺陷。

### 10.2 Position

允许：

- `sticky` 用于明确的表头、工具栏或底部操作区。
- `fixed` 用于应用级 Overlay、全局通知和明确产品要求的固定区域。
- `absolute` 用于组件内部装饰、图标或定位锚点。

禁止：

- 使用 `absolute` 组织页面主布局。
- 使用固定 `top/left` 像素定位业务卡片。
- 通过负 margin 和高 `z-index` 修复结构冲突。

### 10.3 层级系统

未来实现应统一层级 token，至少区分：

```text
base content
sticky page chrome
dropdown / popover
drawer
modal
global notification
critical blocker
```

页面不得自行使用 `9999` 等任意层级值。

## 11. 组件响应行为

| 组件类型 | 空间不足时的标准行为 |
|---|---|
| 页面标题区 | 标题与操作由同排转为分行，主操作保持可见 |
| 工具栏／筛选器 | 有序换行；次要条件可进入高级筛选 |
| 操作按钮组 | 保留一个主按钮；次要操作进入更多菜单或下一行 |
| 指标卡 | 按最小宽度降列，不压缩数字和标签到重叠 |
| 图表组 | 双栏逐级变单栏；单图保持最小高度和可读坐标轴 |
| 表格 | 容器内横向滚动；冻结关键列时不得遮挡其他列 |
| 表单 | 多列逐级变单列；标签和错误信息保持可见 |
| 主区＋侧栏 | 侧栏移至主区下方，或转为抽屉／折叠区 |
| 页签 | 横向滚动、折叠或下拉，不无限缩小文字 |
| 详情面板 | 左右结构转上下结构 |
| 弹窗 | 使用最大宽高；小视口内部滚动；操作区始终可达 |
| 抽屉 | 宽度使用视口约束，不超出可用区域 |
| 底部操作栏 | 正文预留空间；必要时操作换行或折叠 |
| 空／错／加载态 | 保持与正常状态相同的外层尺寸和区块位置 |

每个业务组件在实现时必须声明：

- 最小可用宽度。
- 最小可用高度（如适用）。
- 宽度不足时的重排策略。
- 是否拥有局部滚动。
- 长文本和异常数值的处理方式。

## 12. 内容韧性

布局不能只使用理想长度数据验收。

必须验证：

- 标题和标签长度增加约 30%。
- 金额、价格、比例和 ID 长度显著增加。
- 表格列数和操作数量达到真实上限。
- 加载、空数据、错误和权限不足状态。
- 中文、英文和数字混排。
- 字体加载失败或回退字体略宽。

默认规则：

- 关键业务值不得无提示截断。
- 可截断文字必须提供 Tooltip、展开或完整详情入口。
- 数字区域优先保留单位和正负号。
- 关键按钮文字不得被压缩成不可辨认的省略号。

## 13. 可访问性与缩放

- 浏览器缩放至 `125%` 时核心流程仍可完成。
- 焦点环、下拉菜单和 Tooltip 不得被容器裁切。
- 键盘导航中的焦点元素必须可滚动到可见区域。
- 颜色之外必须保留状态文字或图标。
- 不通过禁止用户缩放来解决布局问题。

## 14. 禁止的修复模式

以下做法默认不允许作为响应式问题的正式修复：

- 为单一分辨率增加专用 CSS。
- 大量固定像素宽度和高度。
- 页面主布局使用绝对定位。
- 使用负 margin 强行衔接模块。
- 多层 `100vh`／`calc(100vh - ...)`。
- 通过 `overflow: hidden` 隐藏错误。
- 通过 `z-index: 9999` 解决覆盖。
- 每个页面建立独立断点体系。
- JavaScript 持续读取窗口宽度并承担普通 CSS 布局。
- 修改全局通用选择器来修复单页问题。
- 未验证中间宽度，只对照 1440 和 1920 两张截图。
- 在 LESS 样式中使用未验证的现代 CSS 函数表达式后直接交付页面。

例外必须在 PR 中说明：

- 为什么 CSS Grid／Flex／Container Query 无法解决。
- 影响的视口范围。
- 回归测试和移除条件。

## 15. 设计与工程协作

### 15.1 设计交付

设计师必须为关键页面提供：

- 宽屏、标准和紧凑桌面下的结构变化。
- 哪些内容换行、降列、折叠、滚动或隐藏。
- 组件最小尺寸。
- 长文本、空数据、加载和错误状态。
- 底部操作区和弹窗在低高度视口下的行为。

设计稿应描述规则，例如：

> 容器宽度不足 760px 时，摘要侧栏移动到主图表下方。

不得只描述某个对象在单张画布中的 X／Y 坐标。

### 15.2 前端交付

前端必须提供：

- 页面壳层和组件的响应规则实现。
- 受影响视口列表。
- 关键视口截图或视觉回归结果。
- 横向／纵向滚动所有权说明。
- 是否新增媒体查询、Container Query、固定定位或层级 token。
- 对长内容、空状态和错误状态的验证。

## 16. 分阶段治理路线

响应式问题必须按以下顺序实施：

### Phase R1：资产与缺陷基线

- 记录核心页面、视口和缩放组合。
- 形成截图基线和缺陷清单。
- 按遮挡、碰撞、滚动、溢出、视觉断裂分类。
- 不在审计阶段顺手修复大量页面。

### Phase R2：Application Shell

- 统一顶部栏、侧边栏、主内容区和主要纵向滚动。
- 清理壳层中的高度重复计算。
- 建立统一页面边距和层级 token。

### Phase R3：Page Shell 与布局原语

- 建立标准页面壳层。
- 建立 Grid、Stack、Toolbar、ScrollableRegion 等有限布局原语。
- 统一固定底栏正文预留。

### Phase R4：共享组件响应行为

- 工具栏、筛选器、指标卡、图表卡、表格、弹窗和抽屉。
- 优先修复被多个页面复用的组件。

### Phase R5：核心页面迁移

建议顺序：

1. 交易执行和资费套利核心页面。
2. 策略管理与账户／订单页面。
3. 风险管理核心页面。
4. 对冲基金看板和研究图表页面。
5. 其他低频页面。

### Phase R6：自动化视觉回归

- Playwright 核心路由截图。
- 关键视口矩阵。
- 遮挡和横向溢出检查。
- PR 视觉差异审阅。

每个 Phase 必须使用独立 Issue 和 PR，不得将全平台响应式重构压入一个超大变更。

## 18. 变更治理

修改以下内容时必须同步更新本文档或新增替代 ADR：

- 最小支持视口。
- Application Shell 的滚动所有者。
- Page Shell 结构。
- 全局断点命名。
- 固定／粘性定位治理。
- 组件响应责任边界。
- 自动化视觉回归范围。

普通页面实现不得自行修改全平台响应式原则。发现规范无法覆盖的新场景时，先记录场景和约束，再决定更新架构或添加受控例外。
