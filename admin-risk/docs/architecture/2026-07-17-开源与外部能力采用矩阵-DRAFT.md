状态：`draft`  
产品基线：Platform V5  
架构讨论版本：Platform V6+  
适用分支：`refactor/frontend-architecture-v6`  
文档层级：交易平台能力采用讨论稿  
更新日期：2026-07-17

配套文档：`2026-07-17-Variable-Global交易平台总体架构方案-DRAFT.md`

> 本文按平台能力而不是按开源项目整体评审。表中“当前建议”只是讨论输入，不代表已经批准采用、采购、Fork、开发或上线。

## 1. 采用方式

| 采用方式 | 定义 |
|---|---|
| 自建 | 由平台定义模型、契约和主要实现 |
| 直接复用 | 在隔离边界内直接使用成熟组件 |
| 封装复用 | 通过 Adapter／Port 包装后使用 |
| Fork 维护 | 以外部实现为基础，由平台维护分支 |
| 设计参考 | 只吸收模型、流程、状态机或可靠性思想 |
| 暂缓 | 当前保留可能性，但不进入主路径 |
| 待验证 | 需要 PoC、兼容性或性能验证后决定 |

## 2. 决策原则

每项能力必须分别回答：

1. 是否属于平台核心业务能力。
2. 是否需要平台自有领域模型和数据权威。
3. 外部组件是否会把平台绑定到其对象、状态或存储。
4. 组件是否支持 MT5、Crypto、CTP 和多账户实际需求。
5. 是否支持幂等、恢复、对账和故障隔离。
6. 许可证、维护活跃度、版本策略和安全风险是否可接受。
7. 替换成本和退出路径是否清晰。

## 3. 平台核心业务能力

| 平台能力 | 平台主责 | 可参考来源 | 当前建议 | 原因与边界 | 待验证 |
|---|---|---|---|---|---|
| 产品模块和用户流程 | Product／Platform | 各项目 Web 产品 | 自建 | 必须符合平台六个一级模块和真实用户任务 | 后续用户流程评审 |
| 公共领域模型 | Domain | NautilusTrader、vn.py、rotki | 自建 | 外部对象只能通过 Adapter 输入 | ExecutionPlan 是否正式加入 |
| StrategyDefinition／Version／Instance | Strategy | Freqtrade | 自建，设计参考 | 平台需要自己的策略、账户、权限和版本关系 | 生命周期和自动策略边界 |
| StrategyAccountBinding | Strategy | 无特定项目 | 自建 | 属于平台业务关系，不属于 Gateway | 审批和生效流程 |
| TradeIntent／TradeCommand | Trading | NautilusTrader | 自建，设计参考 | 命令受理、权限、审批和幂等属于平台 | 命令撤销和过期模型 |
| ExecutionBatch | Trading | vn.py Spread、NautilusTrader | 自建 | 负责业务多腿关系和人工处理 | 与底层执行任务映射 |
| ExecutionPlan | Trading | vn.py Algo／Spread、NautilusTrader | 自建候选 | 连接业务目标和底层算法参数 | 是否持久化、版本方式 |
| RiskDecision | Risk | vn.py RiskManager、NautilusTrader | 自建 | 平台业务风控与底层订单检查分开 | 规则版本和证据存储 |
| ReconciliationResult | Reconciliation | NautilusTrader、rotki | 自建，设计参考 | 对账是平台核心恢复能力 | 自动修复范围 |
| EconomicEvent／LedgerEntry | PnL and Ledger | rotki | 自建，设计参考 | 必须适配平台自己的策略归因 | 账本粒度和重算规则 |
| PnLResult／Attribution | PnL | rotki、Freqtrade | 自建 | 资费、跨所、海内外损益均有专有口径 | 各策略详细公式 |
| Approval／Audit | IAM／Approval／Audit | 通用企业系统 | 自建 | 高风险动作必须符合平台权限和 Maker／Checker | 电子签名和二次认证 |

## 4. 事件、运行时和 OMS

| 平台能力 | 候选来源 | 当前建议 | 平台边界 | 主要风险 | 待验证 |
|---|---|---|---|---|---|
| Runtime 内部事件循环 | vn.py EventEngine | 封装复用候选 | 仅用于 Runtime 内部；平台事件契约独立 | 事件丢失、线程模型、扩展性 | 负载、异常隔离、重启行为 |
| Runtime Engine 管理 | vn.py MainEngine | 封装复用候选 | 作为 Gateway 和 Engine 宿主，不成为平台应用层 | 全局状态、单进程故障域 | 多 Runtime 和动态加载 |
| 实时 OMS 缓存 | vn.py OmsEngine | 封装复用或设计参考 | 只维护实时运行状态；平台数据库持久化权威记录 | 重启丢状态、对象映射 | 恢复后 OMS 重建 |
| 平台持久化订单模型 | 自建 | 自建 | Order／Fill／ExternalReference 由平台定义 | 与 Runtime 状态不同步 | 对账和版本并发 |
| Runtime Registry | 自建 | 自建 | 管理 Runtime、Gateway、Worker 和版本 | 控制面单点 | 高可用要求后评估 |
| Runtime Supervisor | 自建、进程管理框架 | 自建 | 启停、心跳、重启、资源和日志 | 自动重启引发重复交易 | 重启策略和人工确认 |
| Runtime Command Channel | RPC、Redis Streams、RabbitMQ、NATS、Kafka | 待验证 | 平台命令语义和幂等独立于中间件 | 丢消息、重复、结果未知 | PoC 比较 |
| Runtime Event Channel | 同上 | 待验证 | 支持重复、乱序、补发和版本 | 顺序和保留成本 | PoC 比较 |
| Outbox／Inbox | 自建模式 | 设计采纳候选 | 保证数据库提交和消息发布一致性 | 实现复杂度 | 是否所有交易命令强制使用 |

## 5. Gateway 标准与接入

| 平台能力 | 候选来源 | 当前建议 | 平台边界 | 待验证 |
|---|---|---|---|---|
| Gateway 基础抽象 | vn.py BaseGateway、官方 SDK | 平台定义 Port，封装复用 | 不直接把 BaseGateway 作为全平台业务接口 | 能力模型和错误模型 |
| GatewayCapability | 自建 | 自建 | 声明订单类型、账户模式、Funding、Transfer 等能力 | 动态变更和版本 |

| 合约标准化 | vn.py ContractData、官方元数据 | 自建 Instrument／ContractSpecification | 外部 symbol 与平台 instrumentId 分开 | 合约更新和版本 |
| 订单状态映射 | vn.py Status、经纪商状态 | 自建 Adapter | 平台 OrderStatus 为统一语义 | UNKNOWN 和迟到回报 |
| 错误码映射 | Gateway／SDK | 自建 Error Taxonomy | 保留原始错误并映射平台错误 | 跨交易所一致性 |

## 6. MT5 能力

|---|---|---|---|---|

| 远程 MT4／MT5 | PyTrader、EA Bridge | 暂缓／备用 | 仅在跨机器、MT4 或官方包受限时考虑 | 安全、延迟、可靠性和许可证 |

## 7. Crypto 能力

| 能力 | 候选来源 | 当前建议 | 原因与边界 | 待验证 |
|---|---|---|---|---|
| Binance 接入 | 官方 SDK／成熟 Gateway | 待验证后封装或 Fork | 需要现货、永续、Funding、账户和划转 | API 覆盖和维护成本 |
| OKX 接入 | 官方 SDK／成熟 Gateway | 待验证后封装或 Fork | 统一账户和账户模式较复杂 | 账户、订单和 WebSocket 恢复 |
| Bybit 接入 | 官方 SDK／成熟 Gateway | 待验证后封装或 Fork | 资费和跨所策略均可能使用 | 统一账户和数据完整性 |
| vn.py Crypto Gateway | 社区／商业实现 | 单 Gateway 独立评估 | 不将“使用 vn.py”视为全部交易所自动可用 | 版本、维护者、许可证 |
| Funding 数据 | 交易所 API | 自建标准化 Adapter | Funding 是策略和账本重要事实 | 预计值与实际结算区分 |
| Transfer | 交易所 API | 独立 Transfer Port | 不应被普通订单接口吞并 | 幂等和最终状态 |
| Borrow／Repay | 交易所 API | 独立 Borrow Port，后续 | 仅策略实际需要时接入 | 借贷限制和利率 |
| 统一账户 | 交易所 API | 专项适配 | 账户余额和保证金语义不同 | 跨产品余额口径 |

## 14. 当前建议汇总

### 14.1 明确自建

- 平台产品和领域模型。
- Strategy、TradeCommand、ExecutionBatch 和 ExecutionPlan。
- 业务风险、审批、对账和人工干预。
- Strategy Economic Ledger 和 PnL。
- Runtime Control Plane、Registry 和 Supervisor。
- 平台统一 Port、事件和错误契约。

### 14.2 优先研究封装复用

- vn.py EventEngine、MainEngine、OmsEngine。
- vn.py CTP Gateway。
- vn.py RiskManager。
- vn.py SpreadTrading 和 AlgoTrading 的底层能力。
- 官方 MetaTrader5 Python 包。
- 成熟 Crypto Gateway 或官方 SDK。

### 14.3 主要设计参考

- aiomql：MT5 异步、重试和 Session。
- Freqtrade：策略实例运营控制。
- rotki：经济事件、账本、缺失数据和报告版本。
- NautilusTrader：状态机、幂等、恢复、对账和降级。

### 14.4 当前暂缓

- PyTrader 主接入。
- 远程 MT4／MT5 节点。
- 金融AI分析开发。
- 未经 PoC 的数据库、消息队列和微服务拆分。

## 15. 后续评审要求

任何“采用”结论至少需要：

- 能力范围。
- 版本和许可证。
- 维护责任。
- 安全评估。
- PoC 结果。
- 性能和稳定性测试。
- 对账和恢复测试。
- 替换方案。
- 对 active 架构的影响。
- 是否需要 ADR。
