# Platform V6 安全、可观测性与运维架构

状态：`active`  
适用分支：`refactor/frontend-architecture-v6`  
架构层级：跨层技术架构

## 1. 文档定位

本文档定义贯穿前端、后端、接口、数据和交易执行的安全、日志、指标、追踪、告警、配置、发布和恢复原则。

金融平台不能只保证“页面能打开”，还必须能够回答：谁做了什么、系统发生了什么、数据是否可靠、异常影响了哪些账户，以及如何安全恢复。

## 2. 安全原则

- 最小权限。
- 默认拒绝。
- 前端权限只改善体验，后端执行最终校验。
- 演示、测试和实盘环境隔离。
- 敏感凭证不进入前端和普通日志。
- 关键操作可审计。
- 未知状态优先停止扩大风险。
- 数据导出和人工修正受权限控制。

## 3. 身份与会话

至少具备：

- 安全登录和会话管理。
- 会话过期和主动退出。
- 高风险操作二次认证，适用时。
- 登录失败和异常设备记录。
- 用户禁用后及时失效会话。
- 角色、能力权限和数据范围分离。

前端不得保存长期有效交易凭证。

## 4. 密钥与外部账户凭证

- 使用专用密钥管理或加密存储。
- 不写入 Git 仓库、前端构建产物和普通配置文件。
- 不通过日志、错误消息或审计详情输出完整凭证。
- 测试、模拟和实盘使用不同凭证。
- 凭证访问按 Gateway 和账户最小化授权。
- 支持轮换、吊销和访问记录。

## 5. 网络与接口安全

- 全部敏感通信使用 TLS。
- API 执行认证、授权、限频和输入校验。
- WebSocket／SSE 连接执行会话和订阅权限检查。
- 防止重放、重复命令和伪造请求。
- 管理接口与普通查询接口区分权限。
- 内部服务访问使用独立身份或服务凭证。

## 6. 数据安全

- 敏感账户字段按需展示和脱敏。
- 导出文件设置权限、有效期和访问日志。
- 数据库账号按环境和模块隔离。
- 备份数据同样加密和受控。
- 测试环境不得默认复制完整实盘敏感数据。
- 人工修正和删除使用审批或审计机制。

## 7. 日志分类

### 应用日志

记录应用运行、请求处理和异常。

### 交易日志

记录命令、执行批次、外部订单通信和状态变化。

### 审计日志

记录用户、权限、配置、风险覆盖、数据修正和人工处理。

### 安全日志

记录登录失败、权限拒绝、异常访问和凭证问题。

### 数据质量日志

记录延迟、缺失、重复、冲突和对账差异。

不同日志可以使用同一基础设施，但语义和保留周期应区分。

## 8. 日志字段

建议统一包含：

- `timestamp`
- `level`
- `service`
- `environment`
- `requestId`
- `traceId`
- `correlationId`
- `userId`，适用时
- `entityType`
- `entityId`
- `eventCode`
- `message`

交易和审计日志还应包含策略实例、账户、执行批次和结果。

## 9. 日志禁止项

不得记录：

- 完整 API Key、Secret 和密码。
- 完整令牌。
- 不必要的个人敏感信息。
- 大量未经脱敏的请求体。
- 仅有自然语言而没有结构化事件码的关键异常。

## 10. 指标体系

### 系统指标

- CPU、内存、磁盘和网络。
- 请求量、错误率和延迟。
- 数据库连接和慢查询。
- 任务队列积压。

### 交易指标

- 命令受理和拒绝数量。
- 订单提交和确认延迟。
- 成交率和撤单结果。
- 单腿暴露数量和持续时间。
- `result_unknown` 数量。
- 人工处理积压。

### 数据指标

- 行情延迟。
- 数据源中断。
- 缺失和重复记录。
- 对账差异数量。
- 损益重算失败。

### 业务指标

- 活跃策略实例。
- 活跃账户。
- 资金占用。
- 风险限制触发。
- 报表生成状态。

## 11. 分布式追踪

请求、命令和事件应通过以下标识关联：

- `requestId`
- `traceId`
- `correlationId`
- `causationId`
- `tradeCommandId`
- `executionBatchId`

从用户点击到后端命令、Gateway 请求、外部回报和最终状态应能够追踪。

## 12. 告警分级

建议分为：

- `info`：可观察，不需要立即处理。
- `warning`：需要关注，但当前业务仍可运行。
- `critical`：影响交易、账户或关键数据，需要及时处理。
- `emergency`：可能造成持续资金风险或平台级故障。

告警级别由明确规则决定，不直接等同于页面颜色。

## 13. 关键告警

至少包括：

- 实盘 Gateway 断开。
- 订单结果未知。
- 单腿暴露超时。
- 风险服务不可用。
- 账户或持仓对账差异。
- 行情严重延迟。
- 数据库写入失败。
- 审计记录失败。
- 备份失败。
- 权限异常变更。

## 14. 健康检查

服务应区分：

- 进程存活。
- 是否可以接收请求。
- 是否可以访问关键依赖。
- 是否可以执行交易命令。
- 数据是否新鲜。

普通页面可用不代表交易能力可用。

## 15. 配置管理

配置分类：

- 普通应用配置。
- 环境配置。
- 风险和交易业务配置。
- 密钥和凭证。
- 可动态调整配置。

规则：

- 配置有明确来源和版本。
- 实盘配置变更需要权限和审计。
- 密钥与普通配置分开。
- 页面不得通过本地常量决定后端实盘环境。
- 重要配置支持回滚。

## 16. 发布策略

后续建议采用：

- 独立开发、测试和生产环境。
- 可重复构建。
- 数据库迁移版本化。
- 发布前自动检查。
- 小范围灰度或受控启用交易能力。
- 发布后健康检查和回滚条件。

前端发布和交易后端发布可以独立，但接口兼容必须满足契约。

## 17. 故障处理

故障处理流程：

1. 识别和分级。
2. 判断是否需要阻断新增交易。
3. 保护现有订单和持仓。
4. 恢复服务和外部连接。
5. 重新查询权威状态。
6. 执行对账。
7. 处理遗留异常和人工任务。
8. 记录原因和改进措施。

故障恢复不得仅以页面重新打开作为完成标准。

## 18. 备份与灾难恢复

后续必须定义：

- RPO。
- RTO。
- 数据库和对象存储备份。
- 密钥和配置恢复。
- 跨区域或异地备份需求。
- 定期恢复演练。
- 恢复后订单、持仓、账户和账本对账。

## 19. 运维权限

运维人员不应默认获得全部交易和资金操作权限。

应分离：

- 系统运维。
- 用户权限管理。
- 风险规则管理。
- 交易操作。
- 数据修正。
- 审计查看。

高风险操作需要最小权限和完整记录。

## 20. 验收标准

- 安全、日志、指标、追踪和告警覆盖关键交易链路。
- 测试与实盘环境、账户和凭证隔离。
- 关键日志不泄露敏感信息。
- 用户操作可以关联到命令、执行批次和外部回报。
- 关键故障具有告警、阻断、恢复和对账流程。
- 配置、发布和回滚具有版本和审计。
- 备份恢复不是只写在文档中，而需在后续实施阶段定期演练。
