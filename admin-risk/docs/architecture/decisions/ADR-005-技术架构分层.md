# ADR-005：技术架构分为前端、后端、协作和公共领域四层

状态：`accepted`  
日期：2026-07-16  
适用分支：`refactor/frontend-architecture-v6`

## 背景

Platform V6 已经形成产品模块、策略范围、前端状态和领域模型等规范，但部分文档同时讨论页面、后端服务、接口和业务对象，容易产生以下问题：

- 把前端菜单归属误认为后端代码归属。
- 把前端注册表或 Mock 数据误认为平台最终业务真相。
- 前端和后端对订单、成交、损益和风险使用不同语义。
- 尚未建设后端时，技术选型和产品需求混在同一文档。

## 决策

Platform V6 技术架构划分为四层：

1. 前端架构。
2. 后端架构。
3. 前后端协作架构。
4. 公共领域模型。

### 前端架构

定义路由、页面、组件、状态、数据适配、权限展示、构建和测试。

### 后端架构

定义业务服务、规则执行、数据权威、存储、外部接入、可靠性和安全。

### 前后端协作架构

定义查询、命令、事件、API、实时推送、错误码、幂等、时间、币种和版本兼容。

### 公共领域模型

定义 Strategy、Account、Order、Execution、Position、PnL、Risk 等前后端共同业务语义。

## 产品架构关系

六个一级产品模块保持不变。

产品模块决定用户入口和功能归属，不直接决定技术服务、数据库或代码包边界。账户、权限、审计、通知和监控即使位于风险管理菜单内，也应保持各自技术领域边界。

## 原因

- 降低新人理解平台架构的难度。
- 避免页面结构反向决定后端服务设计。
- 避免后端接口字段直接控制前端组件。
- 为未来真实数据和交易系统接入建立清晰边界。
- 允许前端继续建设，同时不提前锁定后端技术选型。

## 影响

- `docs/architecture/README.md` 成为技术架构统一入口。
- 新增 `frontend/`、`backend/`、`integration/` 和 `domain/` 四类架构文档。
- 现有前端状态、共享组件和策略注册表规范归入前端架构。
- 现有领域模型规范升级为平台公共领域模型，不再只服务前端。
- 后续具体后端技术方案必须在后端边界和公共领域语义下评审。
- DRAFT 技术方案不得自动替代 active 架构规范。

## 禁止事项

- 不把六个一级菜单拆成同名后端服务。
- 不把前端本地状态作为订单和账户最终事实。
- 不在公共领域模型中加入页面样式或数据库实现细节。
- 不在未评审的情况下用单份整体方案同时决定产品、前端、后端和部署。

## 重新讨论条件

出现以下情况时可以形成新 ADR 替代本决策：

- 平台产品范围发生根本变化。
- 前后端不再采用独立交互边界。
- 系统演进到需要重新定义技术架构层级的阶段。
