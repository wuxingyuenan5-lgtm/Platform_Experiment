# ADR-009：采用最小 Fund、Portfolio 与 Book 层级

状态：`accepted`  
日期：2026-07-17  
适用分支：`refactor/frontend-architecture-v6`

## 背景

当前平台已经形成 Strategy、Account、Trading、Position、Risk、Reconciliation 和 PnL 等领域，但订单、账户、资金分配和策略损益仍主要围绕 StrategyInstance 组织。

如果未来所有数据长期直接挂在策略名称或交易账户上，会出现：

- 无法表达策略属于哪个基金或投资产品。
- 无法区分基金、组合、执行分区和策略实例。
- 同一账户被多个策略使用时，资金和风险归属不清。
- 策略净值容易被误称为基金 NAV。
- 后续增加多基金、多组合或投资人报告时需要大规模重构。

另一方面，当前项目尚不需要完整基金行政管理系统。立即建设 Investor、ShareClass、Subscription、Redemption 和法定基金会计会显著增加复杂度，并偏离当前投研、交易和风险主线。

## 决策

### 1. 采用最小层级

平台正式采用：

```text
LegalEntity
  ↓ manages / owns
Fund
  ↓ contains
Portfolio
  ↓ contains
Book
  ↓ allocates and governs
StrategyInstance
  ↓ uses account through binding
Account
```

### 2. LegalEntity

LegalEntity 表示具有法律、运营、管理或账户所有权意义的主体。

初期只维护满足账户归属、基金管理和权限范围所需的最小主档，不建设完整法律实体管理系统。

### 3. Fund

Fund 表示需要独立进行管理、风险汇总、绩效归属和报告的基金或内部投资产品。

Fund 至少拥有：

- 稳定 `fundId`。
- 正式名称和代码。
- 管理 LegalEntity。
- Reporting Currency。
- Valuation Calendar。
- 生效状态和有效期。

Fund 不等于 Strategy，也不等于 Account。

### 4. Portfolio

Portfolio 表示 Fund 下可独立进行资产、风险、绩效和资金管理的组合。

每个 Fund 初期至少具有一个默认 Portfolio。

Portfolio 至少拥有：

- 稳定 `portfolioId`。
- FundId。
- 名称和代码。
- Reporting Currency。
- 资金和风险边界。
- 生效状态和有效期。

### 5. Book

Book 是 Portfolio 下的执行、核算或管理分区。

Book 作为正式领域对象保留，但第一阶段采用简化原则：

- 每个 Portfolio 默认创建一个 Default Book。
- 不要求普通用户管理多 Book。
- 不在第一阶段实现复杂 Book 间资金划转和合并核算。
- 策略确有隔离需求时才新增独立 Book。

候选独立 Book 包括：

- Funding Arbitrage Book。
- Gold Spread Book。
- Trader L Book。
- Trader W Book。

### 6. StrategyAllocation

新增 StrategyAllocation，用于表达 Fund、Portfolio 或 Book 向 StrategyInstance 分配的资金、名义额度或风险预算。

StrategyAllocation 不等于：

- Account Balance。
- Cash Transfer。
- StrategyAccountBinding。
- Position。
- PnL。

### 7. Account Ownership 与 StrategyAccountBinding 分离

必须分别表达：

- Account Ownership：账户由哪个 LegalEntity 或 Fund 拥有或控制。
- Account Purpose：账户用途。
- StrategyAccountBinding：某 StrategyInstance 是否以及如何使用账户。
- StrategyAllocation：策略获得的预算或风险额度。

同一账户可以被多个策略实例引用，但必须具备明确额度、用途、归属和对账规则。

### 8. NAV 边界

- StrategyInstance 可以拥有策略净值和策略 PnL。
- Portfolio 可以拥有组合级绩效和估值结果。
- Fund NAV 只有在估值政策、费用、现金、份额和正式复核流程建立后才能形成。
- 当前不得将策略净值直接命名为正式 Fund NAV。

### 9. 延后对象

以下对象不进入当前开发主线：

- Investor。
- ShareClass。
- Subscription。
- Redemption。
- Transfer of Interest。
- 完整 Fund Fee Accrual。
- 完整 Finance Ledger。
- 法定基金会计和投资人报告。

## 原因

- 为多基金、多组合和多策略保留稳定归属结构。
- 避免账户、策略和基金概念混用。
- 支持未来组合级风险、绩效和报表。
- 不把当前内部投资管理平台过度扩张为基金行政管理系统。
- Book 保留扩展能力，同时以默认 Book 降低第一阶段复杂度。

## 影响

- 公共领域模型新增 LegalEntity、Fund、Portfolio、Book 和 StrategyAllocation。
- Account 增加 AccountOwnership 和 AccountPurpose 关系。
- StrategyInstance 必须归属于 Book 或通过明确的过渡映射归属。
- Query 和 Read Model 可以按 Fund、Portfolio、Book、StrategyInstance 和 Account 聚合。
- 风险、PnL、报表和数据范围需要支持上述稳定 ID。
- 统一数据架构需按本 ADR 更新并形成 active 领域蓝图。

## 禁止事项

- 不把 Fund、Portfolio、Book 和 StrategyInstance 合并为一个“策略账户”。
- 不把 Account Balance 当作 StrategyAllocation。
- 不按页面标签或策略名称推断基金归属。
- 不在第一阶段无需求地建设复杂多 Book 操作。
- 不把策略净值直接称为 Fund NAV。
- 不因预留 Fund 对象而立即建设完整投资人和基金会计系统。

## 重新讨论条件

出现以下情况时可新增 ADR 扩展本决策：

- 平台确认只服务单一自有账户且永久不需要基金或组合层级。
- 正式开展多基金、多 Portfolio 或复杂多 Book 运营。
- 建设投资人、份额、申赎和正式 Fund NAV。
- 法律、托管、行政管理或合规要求改变对象边界。
