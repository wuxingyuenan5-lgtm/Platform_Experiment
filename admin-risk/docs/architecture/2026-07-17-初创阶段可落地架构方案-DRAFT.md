> 本文将六层逻辑架构压缩为初创阶段可以开发、调试、部署和维护的工程结构。本文不是开发排期，不代表已经开始建设真实交易系统。

## 1. 核心结论

六层架构只用于划分职责，不直接拆成六个服务。

初创阶段只维护三个主要工程：

```text
Variable-Global
├─ admin-risk            # 现有 Vue 前端
├─ platform-backend      # Python 模块化单体业务后端
└─ execution-runtime     # Python 交易执行与外部连接进程
```

基础设施初期只采用：

```text
PostgreSQL
+
Redis
+
Docker Compose
+
Windows MT5 Runtime / Worker
```

运行关系：

```text
Browser
   ↓
Vue Frontend
   ↓ REST / WebSocket
Platform Backend
   ↓ reliable command / runtime event
Execution Runtime
   ↓
MT5 / Crypto / CTP
```

原则：

- 逻辑职责清楚。
- 工程数量少。
- 不提前拆微服务。
- 不提前引入 Kubernetes、Kafka 和复杂分布式系统。
- 平台后端与交易 Runtime 必须进程隔离。
- 外部组件必须通过 Adapter 和平台契约接入。
- Demo、Paper 和 Live 不共享凭证和交易许可。

## 2. 六层逻辑如何压缩为三个工程

| 六层逻辑结构 | 初期工程归属 | 是否独立部署 |
|---|---|---:|
| 产品与交互层 | `admin-risk` | 是 |
| 平台应用与控制层 | `platform-backend` | 否，与领域层同进程 |
| 核心业务领域层 | `platform-backend` | 否，模块化单体 |
| 交易执行与连接层 | `execution-runtime` | 是 |
| 数据、账本与查询层 | `platform-backend` | 否，使用同一 PostgreSQL |
| 运行保障与基础设施层 | 两个后端工程共享规范，按进程分别实现 | 部分独立 |

禁止将六层直接解释为：

- 六个微服务。
- 六套数据库。
- 六个仓库。
- 六个开发团队。
- 六套重复对象。

## 3. 推荐技术基线

### 3.1 前端

沿用现有：

- Vue。
- TypeScript。
- 现有路由、布局和组件体系。
- REST 查询和命令提交。
- WebSocket 或 Server-Sent Events 接收实时更新，最终方式后续确认。

前端只维护：

- 路由和页面上下文。
- 未提交表单。
- 查询状态。
- View Model。
- 实时展示状态。

前端不维护：

- 正式订单状态。
- 最终持仓。
- 外部成交判断。
- 策略最终 PnL。
- 交易密钥。

### 3.2 平台业务后端

推荐默认基线：

- Python 3.12。
- FastAPI。
- Pydantic v2。
- SQLAlchemy 2.x。
- Alembic。
- PostgreSQL。
- Redis。
- pytest。

选择原因：

- 与交易 Runtime 同为 Python，降低团队语言和工具成本。
- FastAPI 适合当前 API、WebSocket、数据模型和自动文档需求。
- SQLAlchemy 与 Alembic 能支持明确的数据模型和迁移。
- PostgreSQL 足以承载初期订单、成交、账户快照、账本、审计和 Read Model。
- Redis 初期可同时承担短期缓存、幂等键和轻量可靠消息验证。

这些是默认落地建议，不构成永久技术绑定。平台领域对象不得直接依赖框架类型。

### 3.3 交易 Runtime

推荐默认基线：

- Python 3.12，受外部组件兼容性限制时允许单独版本。
- 自有 Runtime 主程序。
- 自有 Port、Command 和 Event 契约。
- vn.py、官方 SDK、MetaTrader5 包、aiomql 等通过 Adapter 使用。
- Runtime 独立进程运行。

MT5 场景：

- Runtime 和 Worker 运行在 Windows。
- 一个 MT5 账户候选对应一个终端实例和一个 Worker。
- Worker 不直接暴露给浏览器。
- Platform Backend 不直接导入 MetaTrader5 包。

### 3.4 数据库

初期只使用一个 PostgreSQL 实例。

逻辑 Schema 可按模块区分，但不建立多个数据库：

```text
public / iam
strategy
trading
account
risk
reconciliation
ledger
reporting
audit
runtime
```

初期不强制使用独立时序数据库。行情历史可以先：

- 少量数据存 PostgreSQL。
- 大量 Tick 暂不全量保存。
- 需要回测和长期行情后，再评估 TimescaleDB、ClickHouse 或其他方案。

### 3.5 Redis

初期允许承担：

- 缓存。
- 短期会话。
- 幂等键。
- 分布式锁，谨慎使用。
- Redis Streams 命令与事件 PoC。

Redis 不承担：

- 永久订单权威。
- 永久成交权威。
- 策略经济账本。
- 唯一恢复来源。

### 3.6 本地与初期部署

推荐：

```text
Developer Windows PC
├─ admin-risk
├─ platform-backend
├─ execution-runtime
├─ MT5 Terminal / Worker
└─ Docker Desktop
   ├─ PostgreSQL
   └─ Redis
```

初期测试服务器可以是：

```text
Windows Host
├─ Platform Backend
├─ Execution Runtime
├─ MT5 Workers
├─ PostgreSQL
└─ Redis
```

后续稳定后再将 Web 后端和数据库迁移至 Linux，MT5 Runtime 保留在 Windows 节点。

## 5. platform-backend 内部边界

平台后端初期为单进程模块化单体。

### 5.1 API 层

负责：

- HTTP 和 WebSocket。
- 请求 DTO。
- 认证信息解析。
- 基础格式校验。
- 错误响应。

不负责：

- 交易业务规则。
- 直接调用 MT5 或交易所 SDK。
- 自行计算最终 PnL。

### 5.2 Application 层

负责用例编排：

- 创建和提交 TradeCommand。
- 权限和审批检查。
- 调用 RiskDecision。
- 创建 ExecutionBatch。
- 请求 ExecutionPlan。
- 将可靠命令发送给 Runtime。
- 处理人工干预。

### 5.3 Domain 层

负责稳定业务规则：

- StrategyDefinition、Version 和 Instance。
- TradeCommand 受理状态。
- ExecutionBatch 生命周期。
- ExecutionPlan 和 LegInstruction。
- RiskDecision。
- ReconciliationResult。
- EconomicEvent、LedgerEntry 和 PnLResult。

Domain 层不依赖：

- FastAPI Request。
- SQLAlchemy Session。
- Redis 客户端。
- vn.py 对象。
- MetaTrader5 对象。

### 5.4 Infrastructure 层

负责：

- PostgreSQL Repository。
- Redis。
- Runtime Command Channel。
- Runtime Event Consumer。
- 密钥和配置。
- 日志和指标。

### 5.5 Read Model

负责生成前端查询所需的数据结构。

初期允许 Read Model 与业务表位于同一个 PostgreSQL，但：

- 不接受业务命令写入。
- 可以删除并重建。
- 不成为订单、成交和 PnL 的第二套权威。

## 6. execution-runtime 内部边界

### 6.1 Runtime 主程序

负责：

- 接收平台命令。
- 调用 Gateway Adapter。
- 维护实时运行会话。
- 发布标准 Runtime Event。
- 启动同步、对账和恢复。
- 上报健康和能力。

### 6.2 Gateway Adapter

每个外部接入实现平台 Port：

- TradingGatewayPort。
- MarketDataGatewayPort。
- AccountGatewayPort。
- 其他专项 Port。

Adapter 负责：

- 外部字段转换。
- 状态映射。
- 错误映射。
- 时间戳和精度处理。
- 外部 ID 保存。

Adapter 不负责：

- 用户权限。
- 策略审批。
- 最终 PnL。
- 平台产品逻辑。

### 6.3 Runtime OMS

初期可以封装 vn.py OmsEngine 或自建最小 OMS。

只负责：

- 当前活动订单。
- 当前成交缓存。
- 当前账户和持仓快照。
- Gateway 实时状态。

Runtime OMS 不是永久数据库。

### 6.4 Worker

MT5 Worker 负责单个终端和账户：

- 初始化。
- 登录和连接。
- 行情和合约。
- 账户和持仓。
- 下单、撤单和历史。
- 心跳和错误。

Supervisor 负责 Worker 的：

- 启停。
- 心跳。
- 异常检测。
- 重启请求。
- 日志路径。
- 配置版本。

初期 Supervisor 可以作为 Runtime 内部模块，不必独立服务。

## 7. 初期最小跨进程契约

只建立必要契约，不一次定义全部平台对象。

### 7.1 RuntimeCommandEnvelope

```text
commandId
commandType
requestId
correlationId
idempotencyKey
strategyInstanceId
executionBatchId
payloadVersion
createdAt
expiresAt
payload
```

首批命令类型候选：

- SubmitLegOrder。
- CancelOrder。
- QueryRuntimeSnapshot。
- StartRecovery。
- AcknowledgeManualDecision。

### 7.2 RuntimeEventEnvelope

```text
eventId
eventType
sourceRuntimeId
sourceGatewayId
correlationId
externalReference
occurredAt
receivedAt
sequence
payloadVersion
payload
```

首批事件类型候选：

- RuntimeHealthChanged。
- GatewayStatusChanged。
- OrderUpdateReceived。
- FillReceived。
- AccountSnapshotReceived。
- PositionSnapshotReceived。
- RecoveryProgressChanged。
- RuntimeCommandRejected。

### 7.3 契约要求

- JSON 可序列化。
- 具有版本。
- 对未知字段向后兼容。
- 原始外部错误可以保留。
- 消费者可以幂等处理重复事件。
- 不直接传递 Python 类实例和 ORM 对象。

## 8. 初期通信默认方案

推荐默认采用：

```text
REST / WebSocket
用于 Browser ↔ Platform Backend

Redis Streams
用于 Platform Backend ↔ Execution Runtime
```

原因：

- 当前系统规模小。
- 部署简单。
- 支持消费者组、消息 ID 和一定程度的重放。
- 已经需要 Redis 缓存和幂等能力。
- 后续可替换为 RabbitMQ、NATS 或其他方案。

必须补充：

- Command Outbox。
- Runtime Inbox 或已处理命令记录。
- Event Inbox。
- 重试次数。
- Dead Letter 处理。
- 消息保留和清理。

不允许：

- API 进程调用 Runtime 后只依赖一次同步返回。
- 网络超时直接将命令标记为失败。
- Runtime 重启后丢失全部待处理命令。

## 10. 最小交易主链路

架构必须支持下面的完整闭环：

```text
1. 前端准备 TradeIntent
2. Platform Backend 接收并验证
3. 创建 TradeCommand
4. 执行权限、模式和风险检查
5. 创建 ExecutionBatch
6. 创建 ExecutionPlan 和 LegInstruction
7. 写入 Runtime Command Outbox
8. Runtime 消费命令
9. Gateway 提交外部订单
10. Runtime 发布订单回报
11. Platform 持久化 Order
12. Runtime 发布 Fill
13. Platform 持久化 Fill 和 Position Snapshot
14. 更新 ExecutionBatch、配平和暴露
15. 前端通过 Query 或实时事件刷新
16. 对账确认平台与外部状态一致
```

必须能够处理：

- 命令重复。
- 请求超时。
- 外部订单已创建但平台未及时收到回报。
- 部分成交。
- 撤单中。
- 未知订单。
- Runtime 重启。
- 前端断线重连。

## 11. 初期恢复模型

Runtime 启动后不能直接进入可交易状态。

```text
STARTING
→ CONNECTING
→ SYNCHRONIZING
→ RECONCILING
→ RECOVERING
→ READY
```

READY 至少要求：

- Gateway 已连接。
- 合约和能力已同步。
- 账户和持仓已同步。
- 活动订单已同步。
- 未完成 ExecutionBatch 已识别。
- 未知外部订单已进入对账。
- 无阻断级残腿或风险差异。
- Runtime 与 Platform 时间偏差在阈值内。

发现严重差异时进入：

- RISK_BLOCKED。
- MANUAL_INTERVENTION。
- DEGRADED，只读或仅允许减仓，按规则决定。

## 12. 初期安全边界

### 12.1 凭证

- 浏览器绝不持有交易凭证。
- Platform Backend 不向前端返回 Secret。
- Runtime 从受控配置或密钥存储读取凭证。
- 日志中不得打印完整密钥、密码和账户登录信息。

### 12.2 模式隔离

- Demo、Paper 和 Live 使用不同账户和凭证。
- Live 命令必须由服务端判断。
- 本地 URL、前端环境变量和页面开关不能赋予 Live 权限。
- 未知模式默认禁止交易。

### 12.3 操作

初期至少记录：

- 操作者。
- 时间。
- 请求和命令 ID。
- 策略实例。
- 账户。
- 动作。
- 风险结果。
- Runtime 结果。
- 原因和错误。

## 13. 初期测试要求

### 13.1 单元测试

重点覆盖：

- 状态映射。
- 数量和精度转换。
- 幂等。
- ExecutionPlan。
- 风险规则。
- PnL 基础公式，实施时。

### 13.2 契约测试

覆盖：

- Runtime Command 版本。
- Runtime Event 版本。
- Gateway Adapter 输入输出。
- 外部状态和错误映射。

### 13.3 集成测试

覆盖：

- PostgreSQL 事务。
- Outbox／Inbox。
- Redis Streams 重复和重放。
- Runtime 重启。
- Backend 重启。
- 前端断线恢复。

### 13.4 Demo 验证

真实资金前必须验证：

- Demo 或测试账户。
- 下单、撤单和部分成交。
- 订单拒绝。
- 外部手工订单。
- 断网和重连。
- Runtime 重启。
- 对账差异。
- 未知结果。

## 14. 明确暂缓项

初创阶段不建设：

- 微服务体系。
- Kubernetes。
- Kafka 集群。
- 多区域高可用。
- 独立数据湖。
- 全量 Tick 永久存储。
- 完整自动策略平台。
- 高级算法交易全家桶。
- 复杂双人审批工作流。
- 自动对账修复全部场景。
- 公司完整财务会计总账。
- 金融AI分析实际开发。
- 远程 MT4／MT5 主路径。

暂缓不等于架构中不存在边界。需要预留对象、接口和数据来源，但不提前实现。

## 15. 何时才拆分服务

只有满足以下条件之一才考虑从模块化单体拆服务：

- 某模块需要独立扩容。
- 某模块需要不同语言或运行环境。
- 某模块故障会严重影响交易主链路。
- 发布频率和团队责任已经独立。
- 数据边界稳定且跨模块事务较少。
- 单体构建、测试和部署已成为明确瓶颈。

可能优先独立的部分：

- Execution Runtime，本方案从一开始已独立。
- MT5 Worker。
- 行情采集。
- 重型 PnL 重算。
- 报表生成。

不会因为文件夹数量增加就拆微服务。

## 16. 初期可维护性规则

- 一个业务对象只有一个主责模块。
- 一个业务状态只有一个正式枚举来源。
- 外部 DTO 必须经过 Adapter。
- API 层不写核心业务规则。
- Runtime 不计算平台最终 PnL。
- 页面不自行维护订单真相。
- 数据库修改必须使用迁移。
- 所有跨进程消息具有版本和幂等标识。
- 所有交易相关异常可以通过 ID 串联日志。
- 每项新增复杂基础设施必须说明当前实际收益。

## 17. 新人开发视角

开发者日常只需要先理解三个入口：

```text
修改页面
→ admin-risk

修改业务规则和 API
→ platform-backend

修改 MT5、Crypto、CTP 和订单接入
→ execution-runtime
```

遇到功能时按以下问题判断位置：

1. 这是页面展示和输入吗？放前端。
2. 这是平台业务规则、权限、风险、账本或查询吗？放业务后端。
3. 这是外部连接、订单发送、回报和实时运行吗？放 Runtime。
4. 这是跨进程稳定数据结构吗？放 contracts。

无法判断时，先写在 Application 层用例，不直接塞进 API 或 Gateway。

## 18. 本方案的落地验收标准

在进入正式开发规划前，应确认：

- 六层逻辑结构已压缩为三个工程。
- 后端采用模块化单体，不拆微服务。
- Runtime 与 Web 后端独立进程。
- 默认技术基线明确。
- 本地开发和初期部署方式明确。
- 目录结构可直接创建。
- 最小命令和事件契约明确。
- 最小数据库对象明确。
- 交易主链路和恢复链路完整。
- 暂缓项明确，不会被误当成当前任务。
- 金融AI分析只预留读取边界，暂不开发。
