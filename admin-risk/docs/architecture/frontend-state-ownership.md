# 前端状态归属规范

状态：`active`  
适用基线：Platform V5

## 1. 目的

避免页面筛选、路由参数、全局状态和业务数据混在一起，降低页面切换、刷新恢复和跨模块联动时的维护成本。

## 2. 状态分为四类

### 2.1 路由状态

适用于：

- 用户刷新页面后应保留。
- 可以通过链接直接打开。
- 影响页面主视图或主要业务上下文。

典型内容：

- 当前策略 desk。
- 当前行情分析／交易执行 section。
- 当前策略管理 section。
- 当前对冲基金看板分类。
- 当前新闻日历分类。

规则：

- 优先使用 path、route meta 或 query。
- 参数必须有默认值和非法值回退。
- 页面不得同时维护另一份不同步的主状态。

### 2.2 页面本地状态

适用于只在当前页面生命周期内有效的交互：

- 图表显示项。
- 展开和折叠。
- 当前分页。
- 临时筛选条件。
- 输入中的交易参数。
- 弹窗开关。

规则：

- 使用 `ref`、`reactive` 或页面级 composable。
- 页面卸载后无需保留的状态不得进入全局 Store。
- 复杂状态应抽成当前模块内的组合式函数，而不是直接堆积在入口页。

### 2.3 模块共享状态

适用于同一模块多个页面或业务区块共享，但不需要全平台使用的内容：

- 当前策略上下文。
- 当前账户组合。
- 当前执行批次。
- 模块级筛选条件。

规则：

- 优先使用模块内 composable 或 provider/inject。
- 只有确实跨路由并需要保留时，才建立模块级 Pinia Store。
- 模块 Store 不得承载其他模块的业务对象。

### 2.4 全局状态

仅适用于全平台共同依赖：

- 当前登录用户。
- 角色和权限。
- 全局通知状态。
- 全局风险阻断状态。
- 用户界面偏好。
- 当前全局账户上下文（只有产品明确需要时）。

规则：

- 全局 Store 数量应保持克制。
- 页面筛选、图表开关和普通分页不得放入全局 Store。
- 全局状态必须有明确初始化、清理和持久化规则。

## 3. 数据状态与界面状态分离

同一页面中应区分：

- 业务数据：订单、持仓、损益、账户、风险记录。
- 请求状态：loading、error、lastUpdated。
- 界面状态：tab、筛选、折叠、选中项。

不得使用一个大型 reactive 对象同时承载全部状态。

## 4. 当前模块建议

### 交易平台

- desk、section：路由状态。
- 交易所、标的、时间粒度：页面或模块状态；确认需要分享链接时再进入 query。
- 下单参数：页面本地状态。
- 当前执行批次：模块共享状态。

### 策略管理

- strategy、section：路由状态。
- 日期、订单状态、分页：页面本地状态。
- 当前策略基础信息：从策略注册表读取，不复制进 Store。

### 对冲基金看板

- category：路由 meta/path。
- 图表时间区间和显示项：页面本地状态。
- 用户收藏工具：未来可进入用户偏好 Store。

## 5. 禁止事项

- 不因多个组件需要使用就立即放入 Pinia。
- 不在路由状态和本地状态中同时保存同一个主字段。
- 不把 Mock 数据本身存入全局 Store。
- 不使用全局事件总线代替清晰的数据流。
- 不把后端响应原样当作长期领域状态。

## 6. 验收标准

- 刷新页面后主要视图上下文符合预期。
- 页面离开后临时交互状态能够正确清理。
- 全局 Store 中不存在普通页面分页和图表开关。
- 同一个状态只有一个权威来源。
