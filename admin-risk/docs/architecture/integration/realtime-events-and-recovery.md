# Platform V6 实时事件与状态恢复规范

状态：`active`  
适用分支：`refactor/frontend-architecture-v6`  
架构层级：前后端协作架构

## 1. 文档定位

本文档定义行情、订单、成交、执行批次、账户和风险状态的实时推送、断线恢复、重复事件处理和权威状态重建规则。

实时连接用于提高及时性，不是唯一数据来源。任何关键页面都必须能够通过查询重新获得权威状态。

## 2. 适用数据

适合实时推送：

- 报价和行情质量。
- 订单状态变化。
- 新增成交。
- 执行批次状态和配平状态。
- 账户余额、保证金和持仓摘要。
- 风险状态和阻断状态。
- Gateway、数据源和服务健康。
- 对账差异和人工处理状态。

不适合只依赖实时推送：

- 历史订单完整查询。
- 正式报表。
- 长区间损益重算。
- 大批量数据导入。
- 用户权限和敏感配置的唯一来源。

## 3. 通信方式

可以采用：

- WebSocket：双向订阅和高频事件。
- SSE：服务端单向推送和较简单状态流。
- 消息代理到 Platform API，再由前端通道推送。

具体技术后续确定，但事件语义保持一致。

## 4. 连接生命周期

前端应管理：

- `connecting`
- `connected`
- `degraded`
- `reconnecting`
- `disconnected`
- `unauthorized`

连接状态不得与业务数据状态混为一体。

## 5. 订阅模型

订阅主题应使用稳定业务 ID，例如：

```text
market.instrument.{instrumentId}
trading.execution-batch.{executionBatchId}
trading.account.{accountId}
risk.strategy-instance.{strategyInstanceId}
system.gateway.{gatewayId}
```

规则：

- 前端只订阅当前页面和授权范围需要的数据。
- 页面离开后释放无用订阅。
- 权限变化后重新建立订阅。
- 不使用显示名称作为主题标识。
- 服务端再次校验订阅权限。

## 6. 事件信封

建议统一结构：

```ts
interface RealtimeEvent<T> {
  eventId: string;
  eventType: string;
  entityType: string;
  entityId: string;
  occurredAt: string;
  publishedAt: string;
  version?: number;
  sequence?: number;
  source: string;
  payload: T;
}
```

必要时增加：

- `correlationId`
- `causationId`
- `environment`
- `qualityStatus`

## 7. 事件语义

事件名称使用已经发生的事实，例如：

- `QuoteUpdated`
- `OrderAcknowledged`
- `OrderPartiallyFilled`
- `ExecutionCreated`
- `ExecutionBatchStatusChanged`
- `BalanceSnapshotUpdated`
- `RiskDecisionChanged`
- `GatewayDisconnected`

不要使用含糊命令式名称，例如 `UpdateOrder`。

## 8. 重复事件

前端必须能够安全处理同一 `eventId` 的重复投递。

处理原则：

- 已处理事件不重复产生通知和副作用。
- 当前状态更新应具有幂等性。
- 成交事件以稳定成交 ID 去重。
- 不能仅凭显示时间去重。

## 9. 乱序事件

当事件具有 `version` 或 `sequence` 时：

- 旧版本不得覆盖新版本。
- 发现序列缺口时标记状态可能不完整。
- 触发对应资源重新查询。

没有可靠序列时，前端依据权威查询结果恢复，不自行猜测顺序。

## 10. 断线重连

重连流程：

1. 标记实时连接中断。
2. 页面显示数据可能不是最新。
3. 指数退避重连。
4. 重新认证和恢复订阅。
5. 查询关键对象当前快照。
6. 使用快照覆盖本地过期状态。
7. 从可用序列点继续接收事件。
8. 恢复正常状态。

不得仅依赖“补收断线期间事件”而跳过权威快照查询。

## 11. 交易页面恢复

交易执行页重连后至少查询：

- TradeCommand 当前状态。
- ExecutionBatch 当前状态。
- 所有关联订单和成交。
- 当前账户和持仓。
- 当前暴露和风险状态。

在恢复完成前：

- 禁止重复提交相同命令。
- 对结果未知命令显示明确状态。
- 不将本地最后一条事件当作最终结果。

## 12. 行情恢复

行情重连后：

- 获取最新 QuoteSnapshot。
- 比较报价时间和接收时间。
- 标记延迟或失效。
- 历史图表缺口通过历史查询补齐。
- 不用一条最新报价自动补造缺失 K 线。

## 13. 心跳与健康

通道应支持：

- 心跳或 ping／pong。
- 服务端时间。
- 最近事件时间。
- 订阅确认。
- 降级和维护状态。

前端可展示：

- 已连接。
- 延迟升高。
- 数据延迟。
- 正在恢复。
- 服务不可用。

## 14. 背压与限流

高频行情和大量事件应支持：

- 按标的订阅。
- 服务端聚合或采样。
- 前端节流渲染。
- 重要事件优先。
- 最大队列和丢弃策略。

不得因图表渲染速度不足阻塞订单和风险事件处理。

## 15. 通知与业务事件

业务事件和用户通知分开：

- OrderPartiallyFilled 是业务事实。
- “订单部分成交，请关注”是通知。

通知模块决定展示渠道、阅读状态和聚合方式，不改变原始业务事件。

## 16. 安全

- 实时连接必须认证。
- 订阅执行数据时检查账户和策略数据范围。
- 令牌过期后停止推送敏感数据。
- 日志不记录完整凭证和敏感 payload。
- 不允许客户端通过伪造主题订阅其他账户。

## 17. 可观测性

至少监控：

- 当前连接数。
- 重连次数。
- 事件发布和消费延迟。
- 重复事件量。
- 序列缺口。
- 订阅失败。
- 客户端恢复查询次数。
- 关键事件丢失告警。

## 18. 测试场景

至少覆盖：

- 正常连接和订阅。
- 连接短暂中断。
- 长时间中断。
- 重复事件。
- 乱序事件。
- 序列缺口。
- 权限在连接期间变化。
- 命令提交后立即断线。
- 部分成交期间断线。
- Gateway 中断和恢复。

## 19. 验收标准

- 实时通道不是唯一权威来源。
- 事件具有稳定 ID、类型、对象 ID 和时间。
- 前端可处理重复、乱序和缺口。
- 断线重连后通过查询重建权威状态。
- 交易页面恢复前不会重复提交命令。
- 行情、订单和风险事件具有独立优先级和质量状态。
- 实时订阅执行服务端权限校验。
