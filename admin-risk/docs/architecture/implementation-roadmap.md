# Platform V6 架构实施路线

状态：`active`  
适用分支：`refactor/frontend-architecture-v6`  
架构层级：跨层实施规划

## 1. 文档定位

本文档定义 Platform V6 从当前前端原型和架构文档，逐步演进到可接入真实数据、模拟交易和受控实盘的平台路线。

本路线用于控制顺序和风险，不表示所有阶段必须同时启动。

## 2. 当前起点

当前平台状态：

- 六个一级产品模块已确认。
- 前端页面和 Mock 数据已存在。
- 交易平台与策略管理需求已形成。
- 前端、后端、协作和领域架构已建立。
- 真实后端、数据库、权限服务和交易执行尚未完成。
- 两份 vn.py 相关 DRAFT 暂不作为实施依据。

## 3. 总体原则

- 先稳定语义和边界，再选技术和写服务。
- 先只读数据，再写入普通管理数据，再接交易命令。
- 先模拟和测试，再小范围实盘。
- 每阶段都有进入条件、完成标准和回退方案。
- 不从前端 Mock 直接跳到真实资金交易。
- 不因后端建设推翻已经确认的产品模块。

## 4. 阶段 0：文档与代码基线对齐

目标：让 V6 架构开始在现有前端代码中生效。

主要工作：

- 策略页签接入统一策略注册表。
- 移除重复策略主清单和废弃 ID。
- 策略与主要视角进入路由状态。
- 建立前端能力权限接口。
- 明确 demo／simulation／test／paper／live 环境。
- 建立 Repository、Adapter、Domain Model 和 View Model 分层。
- 将真实交易样式页面明确标记为演示或模拟环境。
- 建立仓库根目录可运行 CI。

完成标准：

- 文档与前端行为不再存在重大冲突。
- Mock 数据可以通过 Repository 接口读取。
- 路由刷新可以恢复主要页面上下文。
- 没有任何页面会误导用户认为 Mock 已产生真实订单。

## 5. 阶段 1：公共领域与接口契约

目标：形成前后端可以共同开发的稳定语言。

主要工作：

- 稳定 Strategy、Account、Instrument、Position、Order、Fill、ExecutionBatch、PnL 和 Risk 模型。
- 确定稳定 ID 格式和映射原则。
- 确定状态枚举和生命周期。
- 建立 OpenAPI 基线。
- 建立统一错误码、时间、金额、币种和分页规范。
- 建立前端 DTO Adapter 和契约测试。

完成标准：

- 前端不再依赖随机 Mock 字段。
- 核心接口具有机器可读契约。
- Mock 与未来 API 使用同一业务语义。
- 破坏性变化可以被 CI 识别。

## 6. 阶段 2：后端基础与身份权限

目标：建立安全、可部署、可审计的后端基础。

主要工作：

- 建立模块化单体后端骨架。
- 建立 IAM、会话和能力权限。
- 建立配置、密钥和环境隔离。
- 建立数据库迁移、日志、追踪和审计基础。
- 建立健康检查、CI/CD 和备份基础。
- 建立 Platform API／BFF。

完成标准：

- 用户身份和权限由后端权威返回。
- 测试和实盘环境隔离。
- 核心请求具有 requestId 和 traceId。
- 数据库迁移可重复执行和回滚。
- 关键操作能够产生审计记录。

## 7. 阶段 3：只读数据服务

目标：用真实数据替换部分 Mock，但不开放交易写入。

优先顺序：

1. 标的和合约基础信息。
2. 行情和资金费率。
3. 账户和余额只读。
4. 持仓、历史订单和成交只读。
5. 损益和风险摘要。
6. 数据质量和服务健康。

完成标准：

- 页面可明确显示数据来源、更新时间和质量状态。
- Mock 与真实数据可以按环境切换。
- 账户和交易数据具有稳定 ID。
- 对账机制能够识别外部数据差异。
- 只读服务异常不会误开放交易能力。

## 8. 阶段 4：模拟交易执行

目标：完整验证交易命令和 ExecutionBatch，但不连接真实资金。

主要工作：

- 建立 TradeCommand 和幂等。
- 建立 ExecutionBatch 和 LegInstruction。
- 建立订单、成交、部分成交和撤单模拟。
- 建立风险检查。
- 建立实时事件和断线恢复。
- 建立结果未知、重试和人工处理。
- 建立订单、持仓和余额对账。

完成标准：

- 双腿交易完整覆盖成功、部分成交、失败和结果未知。
- 前端断线不影响后台执行。
- 服务重启可恢复未完成批次。
- 所有交易命令和人工处理可审计。
- 自动化测试覆盖主要状态路径。

## 9. 阶段 5：测试网、沙盒或 Paper Trading

目标：验证真实外部协议、连接和市场约束。

主要工作：

- 选择首个 Gateway 和测试账户。
- 验证认证、限频、订单状态和成交映射。
- 验证合约精度、最小数量和费用。
- 验证断线、重连和外部状态恢复。
- 验证账户、订单、成交和持仓对账。
- 验证告警、阻断和人工处理。

完成标准：

- 外部状态能稳定映射到平台状态。
- 无重复订单和无法解释的持仓差异。
- 对账差异有明确处理流程。
- 关键故障经过演练。
- 交易、风险和运维人员确认可以进入下一阶段。

## 10. 阶段 6：受控小范围实盘

目标：以最小资金、最小策略范围验证真实运行。

限制建议：

- 单一环境。
- 单一 Gateway。
- 单一或少量账户。
- 单一策略。
- 小资金和严格额度。
- 明确交易时段和人工值守。
- 默认开启告警和全局阻断能力。

进入条件：

- Paper 阶段稳定运行。
- 权限、审计、对账和恢复全部通过。
- 风险规则和额度已确认。
- 实盘凭证和密钥管理完成。
- 故障和人工处理流程已演练。

退出或回退条件：

- 未知订单结果无法及时确认。
- 持仓或余额持续无法对账。
- 风险服务或审计不可用。
- Gateway 不稳定。
- 单腿暴露超出容忍范围。

## 11. 阶段 7：扩展策略和账户

目标：在经过验证的基础上逐步增加范围。

扩展顺序：

1. 增加同一 Gateway 的账户。
2. 增加同类策略实例。
3. 增加新的策略。
4. 增加新的 Gateway。
5. 增加更复杂的多腿和跨市场执行。

每次扩展都需要重新确认：

- 领域模型是否适用。
- 接口和状态映射。
- 风险和额度。
- 对账和损益。
- 运维和告警。

## 12. 文档交付物

各阶段至少形成：

- 对应需求和架构更新。
- ADR，涉及重大决策时。
- API／事件契约。
- 数据模型和迁移说明。
- 测试计划和结果。
- 发布、回滚和恢复说明。
- 已知限制。

## 13. 质量门槛演进

### 当前

- 类型检查。
- 构建。
- 人工冒烟。

### 前端架构对齐后

- 注册表和路由测试。
- Adapter 和 View Model 单元测试。
- 核心页面 Playwright。

### 后端基础后

- API 契约测试。
- 领域和应用服务测试。
- 数据库迁移测试。
- 权限和安全测试。

### 交易执行后

- 状态机测试。
- 幂等和并发测试。
- 故障注入。
- 恢复和对账测试。
- 压力和延迟测试。

## 14. 决策门槛

以下事项不得在普通页面开发中顺带决定：

- 后端语言和框架。
- 数据库和消息队列。
- vn.py 或其他交易内核。
- Gateway 实现方式。
- 实盘部署拓扑。
- 账本和会计口径。
- 风险覆盖权限。

这些决策需要专项评审和 ADR。

## 15. 当前推荐下一步

在不改后端的前提下，优先完成阶段 0：

1. 统一策略注册表真正接入页面。
2. 路由状态与需求对齐。
3. 建立前端权限和环境模型。
4. 建立 Repository／Adapter 层。
5. 修正字符串化金额和状态。
6. 建立真实可运行 CI。

完成后再开始具体后端技术选型，成本和返工风险最低。

## 16. 验收标准

- 每个阶段具有明确目标、完成标准和回退条件。
- 真实交易能力不跨阶段提前开放。
- 后端技术选型不反向破坏产品和领域边界。
- Mock、模拟、测试和实盘环境明确分开。
- 架构、接口、测试和运维同步演进。
