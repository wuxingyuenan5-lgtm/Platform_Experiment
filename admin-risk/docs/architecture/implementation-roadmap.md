# Platform V6 架构演进路线讨论稿

状态：`draft`  
产品基线：Platform V5  
架构版本：Platform V6  
适用分支：`refactor/frontend-architecture-v6`  
文档层级：规划讨论稿

## 1. 文档定位

本文档记录 Platform V6 从当前前端原型演进至真实数据、模拟交易和受控实盘的候选阶段。

本文件当前不是已批准开发计划，不确定：

- 具体优先级。
- 任务负责人。
- 工期和里程碑。
- 技术选型。
- 首个 Gateway、账户或策略。

正式规划应在架构和全部 active 文档审阅完成后另行确认。

## 2. 当前起点

当前平台状态：

- 六个一级产品模块已确认。
- 前端页面和 Mock 数据已存在。
- 交易平台与策略管理需求已形成。
- 前端、后端、协作和公共领域架构已建立。
- 真实后端、数据库、权限服务和交易执行尚未完成。
- 两份 vn.py 相关 DRAFT 暂不作为实施依据。

## 3. 不变的演进原则

无论正式计划如何安排，都应遵守：

- 先稳定语义和边界，再确定技术选型。
- 先只读数据，再开放普通写入和交易命令。
- 先 Demo 和 Simulation，再 Paper 和受控 Live。
- 每阶段具有进入条件、完成标准和回退条件。
- 不从前端 Mock 直接连接真实资金交易。
- 不因后端建设推翻已确认的产品模块。
- DeploymentEnvironment 与 TradingMode 分开。
- 权限、风险、审批、审计和对账在 Live 前形成闭环。

## 4. 候选阶段 A：文档与现有前端对齐

候选工作：

- 策略页签接入统一策略注册表。
- 移除重复策略清单和废弃 ID。
- 策略和主要视角进入路由状态。
- 建立前端能力权限接口。
- 引入 DeploymentEnvironment、TradingMode 和 TradingPermissionState。
- 建立 Repository、Adapter、Domain Model 和 View Model 分层。
- 明确 Demo 页面不会产生真实订单。
- 建立仓库根目录可运行 CI。

候选完成标准：

- 文档与前端行为不存在重大冲突。
- Mock 通过 Repository 接口读取。
- 刷新后恢复主要页面上下文。
- 页面不会误导用户认为 Mock 已产生真实订单。

## 5. 候选阶段 B：公共领域和接口契约

候选工作：

- 稳定 Strategy、Account、Instrument、Position、Order、Fill、ExecutionBatch、PnL、Risk、Approval 和 Reconciliation 模型。
- 确定稳定 ID 和外部映射原则。
- 确定状态枚举和生命周期。
- 建立 OpenAPI 基线。
- 建立错误码、时间、金额、币种、分页和版本规范。
- 建立前端 DTO Adapter 和契约测试。

候选完成标准：

- 前端不再依赖随机 Mock 字段。
- 核心接口具有机器可读契约。
- Mock 和 API 使用同一业务语义。
- 破坏性变化可以被 CI 识别。

## 6. 候选阶段 C：后端基础和身份权限

候选工作：

- 建立模块化单体后端骨架。
- 建立 IAM、会话、能力权限和数据范围。
- 建立配置、密钥和环境隔离。
- 建立数据库迁移、日志、追踪和审计基础。
- 建立健康检查、CI/CD 和备份基础。
- 建立 Platform API／BFF。
- 建立 Approval 基础，适用于高风险配置和数据修正。

候选完成标准：

- 用户身份和权限由后端权威返回。
- DeploymentEnvironment 和 TradingMode 明确隔离。
- 核心请求具有 requestId 和 traceId。
- 数据库迁移可重复执行和回滚。
- 关键操作产生审计记录。

## 7. 候选阶段 D：只读数据服务

候选优先范围：

1. 标的和合约基础信息。
2. Execution Market Data。
3. Research Data 和内容数据，按产品需求。
4. 账户和余额只读。
5. 持仓、历史订单和成交只读。
6. 损益和风险摘要。
7. 数据质量和服务健康。

候选完成标准：

- 页面显示数据来源、更新时间和质量状态。
- Mock 与真实数据可以按受信任配置切换。
- 账户和交易数据具有稳定 ID。
- 对账机制能够识别外部差异。
- 只读服务异常不会误开放交易能力。

## 8. 候选阶段 E：Simulation

候选工作：

- 建立 TradeCommand 和幂等。
- 建立 ExecutionBatch 和 LegInstruction。
- 模拟订单、Fill、部分成交和撤单。
- 建立风险检查和 TradingPermissionState。
- 建立实时事件和断线恢复。
- 建立结果未知、重试和人工处理。
- 建立订单、持仓、余额和策略经济账本对账。

候选完成标准：

- 双腿交易覆盖成功、部分成交、失败和结果未知。
- 前端断线不影响后台执行。
- 服务重启可以恢复未完成批次。
- 交易命令和人工处理可审计。
- 自动化测试覆盖主要状态路径。

## 9. 候选阶段 F：Paper Trading

候选工作：

- 选择测试网、沙盒或模拟账户 Gateway。
- 验证认证、限频、订单状态和 Fill 映射。
- 验证合约精度、最小数量和费用。
- 验证断线、重连和外部状态恢复。
- 验证账户、订单、成交、持仓和账本对账。
- 验证告警、阻断和人工处理。

候选完成标准：

- 外部状态稳定映射到平台状态。
- 无重复订单和无法解释的持仓差异。
- 对账差异具有处理流程。
- 关键故障经过演练。

## 10. 候选阶段 G：受控 Live

候选限制：

- 单一 Gateway。
- 单一或少量账户。
- 单一策略。
- 小资金和严格额度。
- 明确交易时段和人工值守。
- 默认启用告警和全局阻断。

候选进入条件：

- Paper 稳定运行。
- 权限、审批、审计、对账和恢复通过。
- 风险规则和额度确认。
- Live 凭证和密钥管理完成。
- 故障和人工处理流程完成演练。

候选退出或回退条件：

- 结果未知无法及时确认。
- 持仓或余额持续无法对账。
- 风险服务、审批或审计不可用。
- Gateway 不稳定。
- 单腿暴露超出容忍范围。

## 11. 候选阶段 H：扩展范围

可能的扩展顺序：

1. 同一 Gateway 增加账户。
2. 增加同类 StrategyInstance。
3. 增加新策略。
4. 增加新 Gateway。
5. 增加复杂多腿和跨市场执行。

每次扩展重新确认：

- 公共领域模型。
- 接口和状态映射。
- 权限、审批、风险和额度。
- 对账和损益。
- 运维、告警和恢复。

## 12. 正式规划前需要确认

- 当前产品范围是否已经审阅完成。
- 第一阶段是否只做前端架构对齐。
- 后端语言和框架是否需要先做选型。
- 首批真实数据源。
- 首个只读账户或 Gateway。
- 是否优先建设研究看板后端或交易后端。
- 团队人数、技能和可投入时间。
- 对 Paper 和 Live 的实际目标时间。

## 13. 文档使用规则

- 本文件只作为后续规划输入。
- 不因本文件的阶段顺序直接创建代码任务。
- 正式规划确认后，应建立独立 planning 文档或 issue／milestone。
- 重大架构变化仍回写 active 架构和 ADR。
