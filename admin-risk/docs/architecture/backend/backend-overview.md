# Platform V6 后端架构总览

状态：`active`  
适用分支：`refactor/frontend-architecture-v6`

## 1. 文档定位

本文档定义 Platform V6 后端的目标职责、逻辑边界和建设原则。当前尚未确定具体交易内核、数据库、消息队列或部署拓扑，因此本文不作为具体技术选型方案。

后端负责业务事实、规则执行、数据持久化和系统可靠性；前端负责交互、展示和用户输入。订单、成交、账户、持仓、损益、风险和审计的最终权威不得存在于浏览器本地状态中。

## 2. 目标架构形态

当前阶段建议采用模块化单体后端，并为交易执行、行情接入和异步任务保留独立进程边界。

```text
Web / Client
    ↓
Platform API / BFF
    ↓
Application Services
    ↓
Domain Services
    ↓
Repositories / Event Publishers
    ↓
Database / Cache / External Gateways
```

不建议在业务边界尚未稳定前直接拆成大量微服务。

## 3. 逻辑领域

### 3.1 Identity and Access Management

负责：

- 用户身份认证。
- 角色和能力权限。
- 数据范围权限。
- 会话、令牌和安全策略。

### 3.2 Market Data

负责：

- 行情接入。
- 标的和合约基础信息。
- 报价、K 线、资金费率和市场统计。
- 数据新鲜度和质量状态。

### 3.3 Strategy

负责：

- 策略身份和版本。
- 策略实例与账户关系。
- 策略运行状态。
- 策略参数和已确认业务配置。

前端策略注册表不是后端策略运行状态的最终来源。

### 3.4 Trading and Execution

负责：

- 交易意图和交易命令。
- 执行批次和交易腿。
- 订单提交、撤销和状态同步。
- 成交、部分成交、配平和暴露。
- 幂等、重试和异常恢复。

### 3.5 Account and Position

负责：

- 账户主档。
- 余额、权益和保证金。
- 当前持仓和持仓快照。
- 多账户和多币种折算。

### 3.6 PnL and Ledger

负责：

- 实际损益和结算结果。
- 策略损益归因。
- 费用、资金费、隔夜费和汇率损益。
- 原始经济事件和可重算记录。

### 3.7 Risk

负责：

- 风险指标。
- 风险规则和阈值。
- 执行前检查。
- 风险事件和处置结果。
- 全局或策略级阻断状态。

### 3.8 Reconciliation and Data Quality

负责：

- 订单、成交、持仓、余额和损益核对。
- 外部数据完整性。
- 差异记录和人工确认。
- 数据延迟、缺失、重复和来源冲突。

### 3.9 Audit and Notification

负责：

- 关键操作审计。
- 配置和数据修正记录。
- 人工干预记录。
- 告警和通知生成。

### 3.10 Reporting and AI Support

负责：

- 结构化报表数据。
- 报表版本和导出任务。
- 为金融 AI 提供受权限控制、可追溯的数据查询能力。

## 4. 产品模块与后端领域的关系

前端菜单不等于后端服务边界。

| 产品入口 | 主要后端领域 |
|---|---|
| 对冲基金看板 | Market Data、Research Data |
| 新闻日历与理财 | Content、Calendar、Product Data |
| 交易平台 | Strategy、Trading、Account、Risk |
| 策略管理 | PnL、Account、Position、Order、Reconciliation |
| 风险管理 | Risk、Account、IAM、Audit、Notification、Reporting、Observability |
| 金融 AI | AI Support、Research Data、Permission |

同一后端领域可以被多个前端模块读取，但只能有一套权威业务规则和持久化事实。

## 5. 命令与查询

后端接口应区分：

### 查询

- 可以重复调用。
- 可以缓存。
- 返回数据时间和质量状态。
- 不改变核心业务事实。

### 命令

- 改变订单、账户、策略或风险状态。
- 需要权限和幂等检查。
- 返回受理结果，不把“已受理”等同于“已成交”。
- 形成审计记录。

例如提交双腿交易后，后端应返回执行批次 ID，而不是直接返回“交易成功”。

## 6. 数据权威

| 数据 | 权威来源 |
|---|---|
| 用户、角色和权限 | IAM |
| 标的和合约 | Instrument／Market Data |
| 账户和余额 | Account |
| 订单和成交 | Trading／Execution |
| 当前持仓 | Position |
| 实际损益 | PnL／Ledger |
| 风险规则和事件 | Risk |
| 对账结果 | Reconciliation |
| 审计记录 | Audit |

前端缓存、Mock、页面表格和导入文件均不是最终权威来源。

## 7. 数据存储原则

具体数据库技术后续确认，但必须满足：

- 核心对象使用稳定业务 ID。
- 订单和成交分开保存。
- 当前状态和历史事件可以追溯。
- 金额保留币种和精度。
- 时间保留原始时区或统一 UTC 时间。
- 汇率记录包含来源和时间。
- 人工修正不覆盖原始记录，应形成调整或版本。
- 审计和对账记录不可被普通业务操作无痕修改。

## 8. 实时与异步处理

适合实时推送：

- 报价。
- 订单和成交状态。
- 执行批次状态。
- 账户、保证金和风险状态。
- 系统和数据源状态。

适合异步任务：

- 历史数据同步。
- 损益重算。
- 对账。
- 报表生成。
- 大批量导入。
- AI 分析任务。

实时连接断开不应导致交易进程或后台任务停止。

## 9. 安全与可靠性

后端至少应具备：

- 服务端权限校验。
- 敏感凭证加密和隔离。
- 命令幂等。
- 超时和重试边界。
- 交易所或经纪商异常隔离。
- 关键操作审计。
- 数据备份和恢复。
- 未知执行结果的人工处理流程。

前端禁用按钮不能替代后端安全控制。

## 10. 建设顺序

### 第一阶段：接口和领域基础

- 稳定领域对象和 ID。
- IAM 和操作权限。
- 查询／命令接口规范。
- Mock Adapter 与 API Adapter 对齐。

### 第二阶段：只读数据服务

- 行情。
- 账户和持仓。
- 订单、成交和损益查询。
- 数据质量和更新时间。

### 第三阶段：交易命令闭环

- TradeCommand。
- ExecutionBatch。
- 订单生命周期。
- 风险检查。
- 状态推送和异常处理。

### 第四阶段：账本、对账和恢复

- 经济事件。
- 损益归因。
- 对账。
- 审计。
- 系统恢复和正式报表。

## 11. 待专项确认事项

以下内容不得由本文直接决定：

- 是否采用 vn.py 或其他交易内核。
- MT5、加密交易所和国内期货接入方式。
- 数据库、时序库、缓存和消息队列选型。
- 单体与独立交易进程的具体部署拓扑。
- 高可用、灾备和生产环境规模。

上述事项应分别形成技术验证、实施方案和 ADR。
