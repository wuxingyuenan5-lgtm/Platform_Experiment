# Platform V6 数据存储、账本与审计架构

状态：`active`  
适用分支：`refactor/frontend-architecture-v6`  
架构层级：后端架构

## 1. 文档定位

本文档定义核心业务数据如何持久化、如何区分当前状态与历史事实、如何支持损益重算、对账和审计。

本文不绑定具体数据库产品，但规定后续选型必须满足的业务约束。

## 2. 数据分类

### 2.1 主数据

相对稳定的定义：

- 用户和权限。
- 策略定义和版本。
- 账户主档。
- 标的和合约规则。
- 风险规则。
- 报表定义。

### 2.2 交易事实

已经发生的业务事实：

- 交易命令。
- 执行批次。
- 订单。
- 成交。
- 资金费、手续费和其他经济事件。
- 人工干预。

### 2.3 当前状态

用于快速查询的当前结果：

- 当前订单状态。
- 当前持仓。
- 当前账户余额。
- 当前风险状态。
- 当前策略实例状态。

### 2.4 快照

某一时点的状态记录：

- BalanceSnapshot。
- MarginSnapshot。
- PositionSnapshot。
- RiskSnapshot。
- ValuationSnapshot。
- QuoteSnapshot。

### 2.5 派生结果

可由原始事实重新计算：

- 损益。
- 归因。
- 净值。
- 回撤。
- 风险指标。
- 报表汇总。

### 2.6 审计与对账

- AuditEvent。
- ReconciliationResult。
- DataCorrectionRecord。
- 配置变更记录。

## 3. 核心存储原则

- 所有核心对象使用稳定业务 ID。
- 外部系统 ID 与平台 ID 分开保存。
- 订单和成交分开存储。
- 当前状态和历史事件分开。
- 金额和数量保留精度、币种和单位。
- 时间保留事件时间、接收时间和更新时间。
- 人工修正不覆盖原始事实。
- 数据删除、归档和保留策略明确。
- 敏感凭证不与普通业务数据混存。

## 4. 当前状态与事件历史

推荐同时保留：

1. 当前状态表或读模型，用于快速页面查询。
2. 状态变化记录或领域事件，用于追踪和恢复。

例如 Order：

- 当前状态记录 `filled`。
- 历史记录保留 `submitted → acknowledged → partially_filled → filled`。

不得只保存最终状态而丢失过程。

## 5. 订单与成交

Order 至少保存：

- 平台订单 ID。
- 外部订单 ID。
- 执行批次和交易腿。
- 账户和标的。
- 方向、订单类型和委托参数。
- 当前平台状态。
- 外部原始状态。
- 创建、提交和更新时间。

Execution／Fill 至少保存：

- 平台成交 ID。
- 外部成交 ID。
- 订单 ID。
- 价格、数量和费用。
- 成交时间和接收时间。
- 原始币种和费用币种。

成交记录原则上追加保存，不因后续状态变化被覆盖。

## 6. 持仓

当前持仓可以由：

- 平台成交推导。
- 外部账户持仓同步。
- 对账后的权威结果。

持仓来源必须明确。

同时保留：

- 当前 Position。
- 定期 PositionSnapshot。
- 影响持仓的成交和调整记录。

出现平台推导持仓与外部持仓不一致时，进入对账流程，不静默覆盖。

## 7. 账本与经济事件

建议建立不可变经济事件或账本记录，用于损益和资金变化重算。

经济事件可包括：

- 交易成交。
- 手续费。
- 资金费。
- 隔夜费。
- 借贷利息。
- 入金和出金。
- 汇率折算。
- 结算。
- 已确认调整项。

每条记录至少包含：

- 事件 ID。
- 账户和策略实例。
- 事件类型。
- 金额和币种。
- 业务时间。
- 来源对象。
- 数据来源。
- 是否已核对。

## 8. 损益结果

PnLResult 属于派生结果，应记录：

- 计算口径版本。
- 策略版本。
- 数据截止时间。
- 计价币种。
- 汇率来源和时间。
- 归因项。
- 是否估算或已结算。
- 最近重算时间。

损益规则变化后应允许按新版本重算，但历史正式报表仍保留原版本。

## 9. 调整与修正

错误修正遵循：

- 不删除或覆盖原始事实。
- 创建 DataCorrectionRecord 或 AdjustmentEntry。
- 记录修正前、修正后、原因、操作人和时间。
- 对损益和报表产生影响时触发重算。
- 高风险修正需要审批或二次确认。

## 10. 审计记录

以下操作必须审计：

- 登录和安全事件。
- 交易提交、撤单、平仓和配平。
- 风险规则和限制修改。
- 人工覆盖风险结果。
- 账户和策略绑定修改。
- 数据导入、修正和对账确认。
- 报表生成和正式版本发布。
- 权限变更。
- 环境或 Gateway 配置变更。

审计至少记录：

- `auditEventId`
- 操作人和会话。
- 能力权限。
- 操作类型。
- 目标对象。
- 变更摘要。
- 请求和追踪 ID。
- 时间、来源 IP 或客户端信息。
- 结果。

## 11. 数据库事务

- 单模块内需要强一致的写入使用本地事务。
- 跨模块不建立大范围数据库事务。
- 写入核心事实和待发布事件时，可采用 Outbox 等可靠发布模式。
- 外部交易所结果不属于本地数据库事务。
- 状态变化必须能够应对重复消息和重放。

## 12. 并发控制

关键对象应使用：

- 版本号或乐观锁。
- 唯一约束。
- 幂等键。
- 有序序列或更新时间。

重点防止：

- 重复订单。
- 同一执行批次被重复完成。
- 旧事件覆盖新状态。
- 两个人同时确认同一对账差异。
- 风险规则并发修改丢失。

## 13. 缓存

可以缓存：

- 标的基础信息。
- 策略静态定义。
- 高频查询读模型。
- 短期行情和状态摘要。

缓存不得成为以下数据的唯一来源：

- 订单和成交。
- 账户余额。
- 当前持仓。
- 风险规则。
- 权限。
- 审计记录。

缓存失效、重建和降级策略必须明确。

## 14. 数据保留和归档

后续应按数据类型制定保留周期：

- 订单、成交、账本、审计：长期保留。
- 行情 Tick：根据业务价值和成本分层保存。
- K 线和聚合指标：长期或可重建保存。
- 临时导入文件：完成核对后按策略归档或清理。
- 日志：按安全、运维和审计要求区分周期。

归档不得破坏历史报表、对账和审计查询。

## 15. 备份与恢复

至少明确：

- 备份频率。
- 恢复点目标 RPO。
- 恢复时间目标 RTO。
- 核心数据库和对象存储备份。
- 配置和密钥恢复方式。
- 恢复演练。

交易、账户、账本和审计数据应优先保障。

## 16. 数据安全

- 密钥和交易凭证使用专用密钥管理或加密存储。
- 日志和审计不得输出完整密钥。
- 敏感账户信息按最小权限访问。
- 测试和实盘数据隔离。
- 导出文件具有权限、有效期和访问记录。
- 数据库账号按模块和环境隔离。

## 17. 技术选型评估标准

数据库或存储方案至少评估：

- 事务能力。
- 数值精度。
- 时间序列查询。
- 写入吞吐。
- 历史审计能力。
- 备份恢复。
- 运维复杂度。
- 团队掌握程度。
- 与部署环境兼容性。

不因某项技术流行而提前引入过多存储系统。

## 18. 验收标准

- 原始事实、当前状态、快照和派生结果明确分开。
- 订单、成交和账本记录可追溯。
- 损益可以基于稳定事实重算。
- 人工修正不会覆盖原始数据。
- 关键操作具有不可缺失的审计记录。
- 缓存不是交易事实的唯一来源。
- 数据具备备份、恢复和长期归档方案。
