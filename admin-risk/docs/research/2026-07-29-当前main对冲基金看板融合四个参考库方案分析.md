# 当前 `main` 对冲基金看板融合四个参考库方案分析

状态：`proposal`  
分析日期：`2026-07-29`  
产品基线：当前最新 `main`  
基线提交：`a4e22021c71cf5cd703cb0bc35676ff5adbfec36`  
工作分支：`docs/hedge-board-library-integration-plan`  
实施状态：仅方案分析，不修改功能代码，不合并至 `main`

## 1. 文档目的

本文以 Platform Experiment 当前最新 `main` 上的对冲基金看板为唯一基线，分析如何吸收以下四个参考项目的有效能力：

1. `simonlin1212/globalpercent`
2. `simonlin1212/Vibe-Research`
3. `simonlin1212/global-stock-data`
4. `simonlin1212/a-stock-data`

目标不是把四个仓库整体复制进当前项目，而是在不推倒现有看板的前提下，形成一套可逐步实施的融合方案：

- 保留七个固定栏目及当前主要页面形态。
- 保留现有 Vue、TypeScript、FastAPI、PostgreSQL 和 Redis 技术方向。
- 将当前静态数据、硬编码表格和第三方嵌入逐步替换为统一 Research Data 服务。
- 将四个项目中的数据源经验、事件概率、研究工作流和 AI 工具思想拆分吸收。
- 保持 Research Data、Execution Market Data、Content and Calendar Data 的既有边界。
- 每个后续实施步骤建立独立功能分支，不直接修改或自动合并 `main`。

## 2. 核心结论

### 2.1 总体判断

当前看板不应被四个参考项目中的任何一个“替换”。

更合理的方案是：

```text
保留当前看板导航、页面布局和研究栏目
                │
                ▼
将静态 WidgetConfig / MarketTerminalConfig
替换为统一 Research Read Model
                │
                ▼
在 platform-backend 内建设 Research Data 模块
                │
                ▼
通过 Provider Adapter 分别吸收四个项目的能力
```

四个参考项目的正确分工是：

| 参考项目 | 在融合方案中的角色 | 不承担的角色 |
|---|---|---|
| `globalpercent` | 事件概率、市场预期、Last Known Good 和异步刷新参考 | 不作为全部宏观数据服务，不提供正式交易信号 |
| `global-stock-data` | 美国和全球数据源知识库，尤其是 SEC、Treasury、CFTC | 不直接作为生产后端包，不直接暴露原始来源字段给前端 |
| `a-stock-data` | A 股行情、广度、成交、板块、资金、公告和情绪的数据源经验 | 不作为稳定申万分类主数据，不直接代表商用授权数据 |
| `Vibe-Research` | Research Tool Registry、事实底稿、流式进度、研究上下文与证据审计参考 | 不作为机构权限、正式持仓、生产调度和 Research Data 权威层 |

### 2.2 推荐融合定位

融合后的对冲基金看板应定位为：

> 由统一 Research Data 服务驱动的跨资产研究工作台。页面负责组织研究问题、图表、表格、来源、时间和质量状态；后端负责数据获取、标准化、存储、版本、修订、质量和研究查询；AI 只读取经授权的研究上下文，不反向修改权威数据。

### 2.3 优先级判断

优先顺序不应按“功能看起来是否丰富”排列，而应按平台可信度排列：

1. 先建设来源目录、统一数据契约、Provider Adapter、Instrument Mapping、质量状态和 Last Known Good。
2. 再接入事件概率、美债曲线、CFTC、SEC、A 股广度和成交结构等高价值模块。
3. 再将当前静态看板区块逐项切换为动态 Research Read Model。
4. 最后才引入 Vibe-Research 式 AI 工具、事实底稿、多视角研究和反思审计。

## 3. 当前 `main` 看板基线判断

## 3.1 产品边界是正确的

当前 active 文档已经明确：

- 固定栏目为宏观、商品、加密、美股、A 股、全球和交易工具。
- 看板回答市场变化、历史位置、相对关系和后续研究方向。
- 看板不承担正式下单、策略长期绩效、账户资金、风险处置和 AI 任务管理。
- Research Data、Execution Market Data 和 Content and Calendar Data 必须分层。

这些边界应全部保留，不因引入四个参考库而改变。

## 3.2 当前页面已经形成两套主要展示壳

### 研究区块型页面

宏观、商品和加密主要通过：

```text
HedgeResearchModule
  └─ ChartSection
      └─ WidgetConfig
          ├─ TradingView Widget
          └─ Local Chart Widget
```

该结构适合：

- 主图。
- 专题图表。
- 相关关系。
- ETF、央行、利率和事件概率等研究区块。

### 市场终端型页面

美股、A 股和全球主要通过：

```text
MarketTerminalPage
  ├─ Overview Cards
  ├─ Mover Cards
  ├─ Breadth Cards
  ├─ Volatility Cards
  ├─ Detail Table
  └─ Rotation / Heatmap
```

该结构适合：

- 市场横截面。
- 行业和国家表现。
- 市场广度。
- 风格与轮动。
- 排名、热力图和明细表。

融合方案应保留这两类页面壳，不需要重新设计一级导航和全部页面。

## 3.3 当前实现的主要问题

### 数据仍大量存在于前端

当前存在以下形态：

- `dashboardClean.ts` 内直接定义研究模块和 Widget。
- `marketTerminal.ts` 内直接定义行情、涨跌幅、技术状态和 sparkline。
- `index.vue` 内存在市场明细和 BTC ETF／财库流量等静态数组。
- `nativeData/generated/marketData.ts` 以生成后的大体量 TypeScript 数据进入前端。
- TradingView 组件承担部分行情展示，但来源、修订、质量和平台存储不可控。

因此，当前页面本质上仍是“静态研究原型 + 第三方嵌入”，而不是完整 Research Data 产品。

### 前端配置同时承担了产品定义和数据承载

当前 `WidgetConfig` 主要表达：

- 类型。
- 标题。
- 高度。
- TradingView 配置。
- 本地 Widget Key。

它尚未表达：

- `datasetId`。
- `queryId`。
- `sourceId`。
- `observedAt`、`publishedAt`、`fetchedAt`、`asOf`。
- 数据版本和计算版本。
- 质量状态和新鲜度。
- 降级策略。
- 合法无数据与来源异常的区别。

### Research Data 后端边界已定义，但尚未形成实际能力

当前架构文档已经定义 Research Data 应拥有：

- ResearchSeries。
- ResearchObservation。
- ResearchRevision。
- Dataset／DatasetVersion。
- DerivedResearchIndicator。
- ResearchDataQuality。
- 数据血缘和计算版本。

但当前实际 FastAPI 应用主要围绕策略、账户、交易、执行、对账和 PnL，尚未形成正式 Research Data API、Provider Registry、研究任务和研究存储。

### 当前前端组件缺少标准化局部降级

虽然存在 Widget Error Boundary，但还需要区分：

- 来源暂时不可用。
- 返回上一份有效快照。
- 数据尚未发布。
- 该市场当日合法无数据。
- 部分字段缺失。
- 来源字段发生变化。
- 数据许可不允许当前环境使用。

页面不能把这些状态统一显示为“暂无数据”。

## 4. 融合原则

## 4.1 不替换现有看板，只替换数据供给方式

当前页面结构、栏目顺序、路由和视觉语言继续保留。

重点改变：

```text
原来：Vue 配置或静态数组直接包含数值

改为：Vue 配置只声明研究区块和查询需求
      后端返回统一 Research Read Model
```

## 4.2 四个参考仓库不进入前端依赖

禁止：

- Vue 直接请求 Polymarket、Kalshi、东财、Yahoo、SEC 或其他第三方来源。
- 将四个仓库作为完整子目录复制进 `admin-risk`。
- 让页面认识东财字段号、SEC CIK 解析、Kalshi 特有字段或 Polymarket 原始 JSON。
- 将 `SKILL.md` 直接当生产运行时代码。

## 4.3 Provider 实现必须唯一

Vibe-Research 中“上游工具副本”和“应用运行时代码”双轨维护会产生版本漂移。

Platform Experiment 应规定：

```text
一个来源能力
    ↓
一个 Provider Adapter 实现
    ↓
多个 Research Use Case 复用
```

不允许宏观、美股、A 股和 AI 分别复制一份同来源抓取逻辑。

## 4.4 研究数据不得升级为执行行情

四个库提供的行情、K 线、概率、资金和网页接口数据仅属于 Research Data 候选。

除非另行经过 Execution Market Data 的来源、延迟、质量和交易适用性验证，否则：

- 不用于正式下单价格。
- 不用于阻断或放行交易。
- 不替代交易所或经纪商权威行情。
- 不进入 Runtime 的订单判断。

## 4.5 AI 延后，先保证事实底稿

Vibe-Research 的 AI 工作流有价值，但当前项目的金融AI分析专项后端仍处于冻结状态。

因此融合顺序应为：

1. 先有 Research Query。
2. 再有结构化事实底稿。
3. 再有证据引用和数据缺口。
4. 最后再开放 AI 问答、多视角研究和反思审计。

## 6. 统一数据契约

## 6.1 Research Data Envelope

建议后端所有研究数据响应统一携带：

```ts
interface ResearchDataEnvelope<T> {
  data: T
  datasetId: string
  datasetVersion?: string
  sourceId: string
  providerName: string
  observedAt?: string
  publishedAt?: string
  fetchedAt: string
  asOf: string
  frequency?: string
  timezone?: string
  marketCalendar?: string
  currency?: string
  unit?: string
  calculationVersion?: string
  qualityStatus:
    | 'verified'
    | 'partial'
    | 'stale'
    | 'missing'
    | 'estimated'
    | 'error'
  freshnessStatus:
    | 'live'
    | 'delayed'
    | 'snapshot'
    | 'historical'
  licenseStatus:
    | 'approved'
    | 'research-only'
    | 'restricted'
    | 'unknown'
  isEstimated?: boolean
  warnings?: string[]
}
```

其中必须区分：

- `observedAt`：数据对应的观察期或市场时间。
- `publishedAt`：来源正式发布时间。
- `fetchedAt`：平台获取时间。
- `asOf`：该响应整体的数据截止时间。

## 6.2 Dashboard Read Model

页面不应自行拼装多个 Provider 响应。建议后端直接返回页面级 Read Model：

```ts
interface ResearchDashboardView {
  sectionId: string
  context: ResearchContext
  summary: DashboardSummary
  blocks: ResearchBlockView[]
  sourceSummary: SourceSummary
  qualitySummary: QualitySummary
}
```

区块候选：

```ts
interface ResearchBlockView {
  blockId: string
  blockType:
    | 'time-series'
    | 'comparison'
    | 'market-terminal'
    | 'heatmap'
    | 'breadth'
    | 'event-probability'
    | 'filing-list'
    | 'snapshot-table'
    | 'external-tool'
  title: string
  description?: string
  data: unknown
  metadata: ResearchBlockMetadata
  state: 'ready' | 'partial' | 'stale' | 'empty' | 'error'
}
```

## 6.3 错误和降级语义

统一错误码至少包括：

- `NO_DATA`：该标的或日期合法无数据。
- `NOT_PUBLISHED`：数据尚未发布。
- `PROVIDER_UNAVAILABLE`：来源暂时不可用。
- `RATE_LIMITED`：来源限流。
- `AUTH_REQUIRED`：缺少鉴权、User-Agent 或授权配置。
- `LICENSE_RESTRICTED`：当前环境不允许使用。
- `SCHEMA_CHANGED`：来源字段或结构发生变化。
- `PARTIAL_DATA`：部分来源或字段缺失。
- `STALE_DATA`：返回上一份有效快照。
- `INVALID_INSTRUMENT`：标的与市场不匹配。
- `MAPPING_MISSING`：缺少代码、行业、CIK 或板块映射。

## 7. Provider 与数据存储方案

## 7.1 Provider Registry

每个 Provider 必须注册：

- `providerId`。
- 支持的 Capability。
- 适用市场和数据集。
- 鉴权类型。
- 限速规则。
- 超时、重试和熔断策略。
- 健康检查方式。
- 数据许可状态。
- 主源／备用源关系。
- 原始响应保留策略。
- 字段契约测试。

## 7.2 来源目录

建议建立 Source Catalog，至少维护：

- `sourceId`。
- `providerName`。
- `sourceType`。
- `licenseTier`。
- `commercialUse`。
- `redistributionAllowed`。
- `authenticationType`。
- `rateLimitPolicy`。
- `termsReviewedAt`。
- `termsReference`。
- `dataOwner`。
- `fallbackSourceId`。
- `enabledEnvironments`。

代码许可证不能代替数据使用许可审查。

## 7.3 Last Known Good

所有外部 Research Provider 应遵循：

1. 新拉取结果通过 Schema、字段完整度和业务有效性检查。
2. 只有有效结果才能替换当前有效快照。
3. 空数组、空对象或异常字段不得覆盖上一份有效快照。
4. 来源异常时返回上一份有效快照，并明确标记 `stale`。
5. 快照替换必须原子化。
6. 每次替换记录 Provider Run、数据版本、截止时间和质量结果。

## 7.4 调度方式

不建议在 FastAPI Web Worker 启动时直接创建长期后台任务。

初期建议：

- 调度逻辑仍属于 `platform-backend` 代码库。
- 通过独立命令入口或部署进程执行定时刷新。
- PostgreSQL 或 Redis 提供任务锁和幂等键。
- Web API 只提交刷新请求或查询刷新状态。
- 耗时任务通过 SSE 返回阶段进度，但不由浏览器维持任务权威状态。

这不是新增业务微服务，而是同一模块化单体的独立运行角色。

## 7.5 建议最小存储对象

第一阶段无需一次建设全部历史仓库，建议最小对象为：

- `research_source`。
- `research_dataset`。
- `research_dataset_version`。
- `research_series`。
- `research_observation`。
- `research_snapshot`。
- `research_provider_run`。
- `research_data_quality`。
- `instrument_mapping`。
- `classification_membership`，A 股分类启用时。

后续再补：

- `research_revision`。
- 原始响应对象存储。
- Point-in-Time 财务数据。
- 公司行为和复权。
- 复杂派生指标血缘。

## 8. 四个参考项目的具体融合方式

## 8.1 `globalpercent`

### 融合目标

建设独立的 Event Probability 能力，不复制整个 React 面板。

### 建议 Provider

- `PolymarketEventProvider`。
- `KalshiEventProvider`。

### 统一对象

```ts
interface EventProbabilityView {
  eventId: string
  title: string
  categoryId: string
  conditionLabel: string
  probability: number
  previousProbability?: number
  change?: number
  volume?: number
  liquidity?: number
  sourceId: string
  marketUrl?: string
  expiresAt?: string
  asOf: string
  qualityStatus: string
}
```

### 吸收能力

- 多来源统一 Schema。
- Taxonomy 和栏目映射。
- 事件稳定 ID。
- 多档位事件必须连同条件标签展示。
- Last Known Good。
- stale-while-revalidate。
- 来源、成交量、到期时间和趋势。
- 每个栏目设置事件数量和重要性上限。

### 必须重写

- 磁盘 JSON 快照。
- 进程内 `_rebuilding` 状态。
- Web Worker 内 `asyncio.create_task`。
- 仅关键词驱动的长期分类。
- 缺少审计和多实例锁的刷新逻辑。

### 页面落位

- 宏观：政策、通胀、就业、衰退、地缘事件概率。
- 商品：油价、黄金、贸易和供应事件的注释层。
- 加密：BTC／ETH 价格档位、ETF／监管事件的概率注释层。
- 全球：选举、政策和地缘事件概率。

事件概率只能作为研究温度计，不能描述为官方预测或交易信号。

## 8.2 `global-stock-data`

### 融合目标

将其作为美国与全球数据源、字段和异常处理知识库，抽取独立 Provider。

### 第一批候选能力

优先接入相对正式、研究价值高的数据源：

1. U.S. Treasury 收益率曲线。
2. CFTC COT。
3. SEC Filing 列表和全文入口。
4. SEC XBRL 公司数据。
5. SEC Frames 横截面筛选。

### 第二批候选能力

需要先完成数据条款和稳定性评估：

- FINRA Short Volume。
- CBOE 期权和 Greeks。
- Nasdaq 财报日历。
- Yahoo Finance 行情。
- 东财、新浪和腾讯的美港股数据。

### 页面落位

- 宏观：Treasury 曲线、期限利差、CFTC。
- 商品：CFTC 持仓。
- 美股：SEC、财务横截面、申报事件、期权和空头数据。
- 全球：国家 ETF、主要指数和利率候选。
- 交易工具：SEC 全文检索、XBRL 筛选和期权结构工具。

### 必须补齐

- Instrument Master。
- Ticker／CIK／交易所／外部代码映射。
- Point-in-Time 财务数据。
- 公司行为和复权。
- 供应商级限速和并发控制。
- 正式数据许可状态。

## 8.3 `a-stock-data`

### 融合目标

优先解决 A 股看板当前静态数据问题，不追求一次接入全部 44 个端点。

### 第一批候选能力

1. 宽基指数行情。
2. 全市场上涨、下跌、涨停和跌停数量。
3. 成交额和换手结构。
4. 当日成交额超过指定阈值的个股数量及行业分布。
5. 行业表现。
6. 板块资金流。
7. 规模、成长、价值和红利风格代理。

### 第二批候选能力

- 龙虎榜。
- 融资融券。
- 大宗交易。
- 股东户数。
- 解禁。
- 研报和一致预期。
- 公告。
- ETF 期权。
- 打板情绪。

### 分类治理

必须建立平台自己的稳定分类对象：

```text
classificationSystem
classificationVersion
classificationNodeId
effectiveFrom
validTo
instrumentMembership
sourceReference
```

规则：

- 申万一级、二级、三级必须明确版本和稳定 ID。
- 东财行业、同花顺概念和地域分类不能混成申万行业。
- 页面筛选必须显示当前使用的分类体系。
- 来源返回的板块名称不能直接成为平台主键。

### 页面落位

当前 `MarketTerminalPage` 可以直接承接：

- Overview Cards：宽基指数。
- Mover Cards：成交额、涨跌幅或主题异动。
- Breadth Cards：上涨率、涨停率、成交集中度。
- Detail Table：指数、行业、主题和风格明细。
- Rotation Heatmap：申万行业、风格和主题轮动。

## 8.4 `Vibe-Research`

### 融合目标

吸收研究工作流，不复制个人持仓、浏览器密钥和本地应用架构。

### 第一阶段可吸收

- 统一 Research Tool Registry 的接口设计。
- 页面研究上下文对象。
- 工具结果裁剪和结构化错误。
- 事实底稿模板。
- 数据缺口清单。
- 页面级局部失败。
- SSE／NDJSON 风格的任务进度。

### 后续 AI 阶段

在金融AI分析后端重新启用后，候选能力包括：

- “问 AI”自动携带当前栏目、标的、频率和日期范围。
- 基于同一事实底稿的多视角分析。
- 事实、计算和模型推断分层。
- 结论引用具体数据集、数据时间和来源。
- 反思审计检查无来源数字和不受支持的判断。
- 输出验证清单，而非直接输出交易命令。

### 不迁移

- 本地个人持仓作为正式平台持仓。
- 浏览器保存模型密钥。
- 单一全局 API Key 权限。
- 进程启动即运行调度器。
- AI 输出写回 Research Data 原始事实。

## 9. 七个固定栏目的融合方案

- `global-stock-data`：Treasury 和 CFTC。

- CFTC COT。

- 数据单位、币种、合约和换月口径元数据。

## 10. 前端改造方案

## 10.1 保留组件

建议保留：

- `HedgeResearchModule.vue`。
- `MarketTerminalPage.vue`。
- `TerminalDetailPanel.vue`。
- TradingView Widget。
- Widget Error Boundary。

## 10.2 将配置和数据分开

当前配置对象应逐步从“配置 + 数据”变为纯产品配置：

interface ResearchWidgetDefinition {
  widgetId: string

数值、历史序列、涨跌幅、来源和质量由 API 返回。

## 10.3 新增统一组件状态

每个 Widget 至少支持：

- `loading`。
- `ready`。
- `partial`。
- `stale`。
- `empty`。
- `error`。

同时展示：

- 数据截止时间。
- 来源。
- 质量状态。
- 当前是否为上一份有效快照。
- 估算或修订提示。
- 原始来源入口，适用时。

interface MarketTerminalViewModel {

  status: string

  breadthCards: BreadthCardView[]

## 10.5 TradingView 的位置

TradingView 可以继续作为：

- 用户查看主图的外部嵌入。
- 辅助图表。
- 当前尚未自建历史序列时的过渡方案。

但不应继续承担：

- 平台 Research Data 的唯一历史来源。
- 质量和修订记录。
- 统一跨市场计算。
- 后端 Research API。

## 11. API 方案

建议的页面级 API：

```text
GET /api/v1/research/dashboards/{sectionId}
GET /api/v1/research/widgets/{widgetId}
GET /api/v1/research/series/{seriesId}
GET /api/v1/research/markets/{marketId}/snapshot
GET /api/v1/research/events/probabilities
GET /api/v1/research/filings
GET /api/v1/research/sources
GET /api/v1/research/sources/health
POST /api/v1/research/refresh-jobs
GET /api/v1/research/refresh-jobs/{jobId}
GET /api/v1/research/refresh-jobs/{jobId}/events
```

原则：

- API 按研究用例设计，不按第三方网站设计。
- 前端不调用 `/polymarket/...`、`/eastmoney/...` 或 `/sec/...` 等来源耦合接口。
- 页面级 Dashboard API 可以聚合多个 Dataset，但必须保留每个区块来源和质量。
- 刷新 API 不保证同步完成，必须返回任务状态。

## 14. 主要风险

## 14.1 数据许可风险

代码仓库使用 Apache-2.0 或 MIT，不代表其调用的数据可商用或再分发。

所有来源必须单独确认：

- 商业使用。
- 展示范围。
- 历史存储。
- 再分发。
- 用户导出。
- API 转发。

## 14.2 上游接口变化

网页前端接口经常发生：

- 字段重命名。
- 参数变化。
- 防爬增强。
- 返回空结构。
- 代码路由变化。

必须建立：

- Fixture 契约测试。
- Live Shape Smoke Test。
- Provider Health Check。
- Schema Change 告警。
- 空拉取保护。

## 14.3 分类和标的映射风险

最危险的问题不是直接报错，而是静默映射到错误标的或错误行业。

必须避免：

- 只按股票代码字符串判断市场。
- 将国家 ETF 当成本地指数。
- 将东财行业当申万行业。
- 将概念板块名称当稳定 ID。
- 将当前分类覆盖历史分类。

## 14.4 数据时间风险

同一页面可能混合：

- 实时行情。
- 延迟行情。
- 日收盘。
- 周度 ETF。
- 月度宏观。
- 不规则事件概率。

页面必须显示各区块截止时间，不能只显示一个整页“更新时间”。

## 14.5 过度范围扩张

四个仓库功能很多，但当前阶段不应同时建设：

- 完整 Bloomberg 替代品。
- 全市场逐笔行情。
- 完整量化回测平台。
- 自动交易信号系统。
- 新闻全文库。
- 全量 AI Agent 平台。

融合方案应围绕现有七个栏目和明确研究问题选择能力。

## 15. 明确不建议的做法

- 不把四个仓库整体复制到当前仓库。
- 不直接在 `main` 上实现。
- 不在一个分支同时改前端、后端、全部 Provider 和 AI。
- 不让 Vue 直接访问第三方数据源。
- 不让 Provider 原始字段进入 View Model。
- 不把 `SKILL.md` 当生产依赖。
- 不复制同一数据源逻辑到多个模块。
- 不用空数组覆盖上一份有效数据。
- 不把所有错误统一解释为“暂无数据”。
- 不把预测市场概率描述成官方结论。
- 不把 Research Data 用作正式执行行情。
- 不在数据许可未知时对外展示或导出。
- 不先做 AI，再补数据可信度。

## 16. 验收标准

完整融合并不是“页面能显示更多数字”，而应满足以下标准。

### 架构

- 四个参考仓库的能力均通过 Provider Adapter 或 Research Tool 接入。
- 前端不认识来源特定字段。
- Research Data 和 Execution Market Data 保持隔离。
- Provider 实现不存在应用内双轨复制。

### 数据

- 每个区块可识别来源、截止时间、观察期和获取时间。
- 数据版本、计算版本和质量状态可追踪。
- 空拉取不会覆盖有效数据。
- 合法无数据与来源异常可以区分。
- A 股分类具有稳定 ID、版本和生效日期。

### 页面

- 七个固定栏目和当前主要页面壳保持稳定。
- 每个 Widget 支持局部加载、失败、部分数据和陈旧快照。
- 页面不因一个 Provider 失败而整体不可用。
- URL 或 Saved View 能恢复研究上下文。
- TradingView 嵌入和平台 Research Data 的边界清楚。

### 治理

- 每个来源具有许可状态和负责人。
- 每次 Provider 刷新有运行记录和质量结果。
- 关键字段变化能够被测试或监控发现。
- AI 输出能够引用具体数据和时间，且不修改原始事实。

## 17. 推荐决策

### 应立即确认的方向

1. 保留当前看板七栏目和两类主要页面壳。
2. 以 Research Data 模块而非前端页面作为融合中心。
3. 四个项目按能力拆分，不选任意一个作为整个平台底座。
4. 第一实施目标是数据契约、质量和 Provider 基础，而不是新增大量页面。
5. 事件概率、Treasury、CFTC、SEC 和 A 股广度作为首批高价值能力。
6. AI 工作流延后至 Research Data 稳定后。

### 不应在本方案分支实施的内容

本分支仅保存分析，不应直接：

- 修改 `index.vue`。
- 修改 `dashboardClean.ts`。
- 修改 `marketTerminal.ts`。
- 新增外部 Provider。
- 新增数据库迁移。
- 修改 FastAPI 路由。
- 引入 AI 功能。
- 合并至 `main`。

## 18. 最终方案摘要

当前最新 `main` 的看板已经具备较清晰的产品边界和可复用页面壳，但实际数据供给仍以静态前端配置和第三方嵌入为主。

四个参考项目最合理的融合方式不是页面级拼接，而是：

```text
保留现有七栏目和 UI
        ↓
建立统一 Research Read Model
        ↓
在 platform-backend 建设 Research Data 模块
        ↓
用唯一 Provider Registry 吸收四库能力
        ↓
逐个 Widget 替换静态数据
        ↓
最后开放 AI 研究工作流
```

其中：

- `globalpercent` 负责提供事件概率设计参考。
- `global-stock-data` 负责提供美国和全球数据源参考。
- `a-stock-data` 负责提供 A 股数据源和市场路由参考。
- `Vibe-Research` 负责提供研究任务、工具注册、事实底稿和 AI 使用方式参考。
- Platform Experiment 自身必须负责统一架构、权限、审计、存储、版本、质量、分类、Instrument Master 和数据许可治理。

这套方案能够最大限度保留当前看板已经完成的产品与交互投入，同时避免把个人研究项目、网页抓取脚本和来源特定字段直接带入机构级平台核心。
