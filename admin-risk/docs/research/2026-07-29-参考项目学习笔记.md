状态：`reference-only`  
研究日期：`2026-07-29`  
适用范围：对冲基金看板后续优化参考  
实施状态：仅研究与归档，不修改现有产品、架构和功能代码  
目标分支：`docs/reference-projects-study`

## 1. 文档目的

本文研究以下四个项目，并判断其对 Platform Experiment，尤其是“对冲基金看板”的参考价值、可复用边界与后续吸收方式：

1. `simonlin1212/globalpercent`
2. `simonlin1212/Vibe-Research`
3. `simonlin1212/global-stock-data`
4. `simonlin1212/a-stock-data`

本文不是实施方案，不替代现有 active 产品文档和架构文档。后续应以用户上传的新版本为基线，再决定具体接入范围、分支和任务拆分。

## 2. 研究基线

本次基于各仓库 `main` 分支进行研究，记录的上游版本点如下：

| 项目 | 研究时参考提交 | 代码许可 | 核心定位 |
|---|---|---|---|
| globalpercent | `eef366444d0d4d0d64720d928520f6ad6c850b24` | Apache-2.0 | Polymarket + Kalshi 全球事件概率面板参考实现 |
| Vibe-Research | `37a23f8c96da9a201f8dde9839464086da277e76` | MIT | 面向个人的 A 股为主、多市场 AI 投研应用 |
| global-stock-data | `c0b3ed8d8a1fdff0932e5899fc64a5994308a5ef` | Apache-2.0 | 美股、港股、官方宏观和监管数据工具箱 |

## 3. 总体结论

这四个项目并不是四套互相独立的完整产品，而是一套相互补充的参考体系：

```text
a-stock-data ─────────────┐
                          ├─► 数据能力与接口经验
 global-stock-data ───────┘

 globalpercent ─────────────► 事件概率与宏观预期补充层

 上述数据与能力
       │
       ▼
 Vibe-Research ─────────────► 页面、AI 工具、研究工作流和本地应用装配
```

对 Platform Experiment 的价值可以归纳为：

- `globalpercent`：宏观事件概率模块的主力参考。
- `Vibe-Research`：投研工作流、AI 工具注册、客观底稿和渐进式交互的主力参考。
- `global-stock-data`：美股、SEC、美国宏观、期权、做空与监管事件数据源目录的主力参考。
- `a-stock-data`：A 股行情、板块、成交、资金、研报、公告和市场情绪数据源经验的主力参考。

但四个项目都不能直接视为 Platform Experiment 的生产数据层。它们更接近：

1. 已验证的数据源与字段知识库。
2. 可运行的参考代码。
3. 个人研究产品的交互原型。
4. 上游接口变更和异常处理经验集合。

后续正确做法不是整体复制，而是把有价值的能力拆成 Provider Adapter、统一数据契约、研究查询服务和可审计的 UI 区块。

## 4. globalpercent 研究

### 4.1 项目定位

`globalpercent` 将 Polymarket 与 Kalshi 的公开市场数据统一成“全球宏观预期概率面板”。其定位不是交易系统，而是事件和预期的市场温度计。

主要链路：

```text
Polymarket / Kalshi
        │
        ▼
各数据源 Fetcher
        │ 统一字段
        ▼
共享 Taxonomy 分类
        │
        ▼
聚合、限量、翻译、快照
        │
        ▼
FastAPI 查询接口
        │
        ▼
React 概率面板与趋势图
```

### 4.2 最值得学习的设计

#### 统一来源 Schema

不同预测市场先被整形成同一套对象，聚合层不关心数据来自 Polymarket 还是 Kalshi。该原则非常适合 Platform Experiment 的 Research Data 层：

- Provider 负责解析来源字段。
- Adapter 负责转成统一 DTO。
- 研究区块不直接读取第三方字段。
- 新增数据源不要求重写上层页面。

#### Last Known Good 快照

项目将完整聚合结果固定到磁盘快照，普通页面加载直接读取快照，主动刷新才重新拉取。

更重要的是其明确规定：

> 拉取结果为空时，不得覆盖上一份有效快照。

这是后续所有外部数据源都应采用的底线规则。上游短暂不可用不应表现为“历史数据被清空”。

#### 异步刷新

Kalshi 全量拉取较慢，项目采用“先返回旧快照并标记 updating，再后台刷新，前端轮询 as_of”的思路。该模式适合低频 Research Data，但后续应升级成独立任务系统，而不是依赖 Web 进程内的 `asyncio.create_task`。

#### 多档事件语义

对于 CPI、油价、BTC 价格等多档位事件，项目不是随意取一个概率，而是选择最接近 50% 的档位，并把档位标签一起展示。

这个思路的核心不是“取 50%”，而是：

- 数值必须和其条件、区间或档位一起呈现。
- 不允许把有条件概率压缩成没有语义的单个百分比。
- UI 必须告诉用户“这个概率究竟对应什么事件”。

#### Taxonomy 与流量控制

项目通过有序关键词和来源原生分类进行主题归类，同时对各模块设置数量上限，避免体育、天气或大量衍生合约淹没宏观信号。

这对看板的启示是：研究首页不能简单按数据量排序，必须有主题优先级、信号密度和降噪规则。

### 4.3 可用于对冲基金看板的部分

适合后续进入“宏观”栏目：

- 美联储政策事件概率。
- CPI、就业、衰退等宏观事件概率。
- 地缘政治事件概率。
- 重要政治和选举事件概率。
- 概率变化趋势。
- 来源、成交量、截止时间和事件到期日。

也可以作为“商品”“加密”和“全球”栏目的事件注释层，但不应取代正式价格、期限结构、供需或宏观数据。

### 4.4 不能直接照搬的部分

- 磁盘 JSON 快照缺少数据库级版本、原子写入、审计和多实例锁。
- `_rebuilding` 是进程内状态，多 Worker 或服务重启后不可靠。
- 关键词分类适合初版，不适合作为长期唯一分类方法。
- 预测市场概率不是官方概率，也不是无条件可靠的预测结果。
- 目前 Schema 对流动性质量、市场深度、异常成交和来源健康度表达不足。

### 4.5 后续吸收原则

应吸收：

- Polymarket / Kalshi Provider 经验。
- 统一事件概率 DTO。
- Last Known Good。
- 异步刷新和 stale-while-revalidate。
- 多档事件语义。
- 来源徽章、截止时间和趋势图。

应重写：

- 任务调度。
- 快照存储。
- 分布式锁。
- 数据质量状态。
- 事件去重与稳定 ID。
- 分类规则和人工校正机制。

## 5. Vibe-Research 研究

### 5.1 项目定位

`Vibe-Research` 是一个本地优先的个人 AI 投研应用，主要服务 A 股，同时补充美股、港股和全球市场。其核心不是单一数据接口，而是将以下能力装成一套可操作产品：

- 每日复盘。
- 资讯雷达。
- 个股数据。
- 自选股。
- 板块中心。
- 持仓和研报。
- 研究记录。
- AI 问答。
- 多空辩论。
- 反思审计。
- MCP 与本地 CLI 接入。

技术结构为 FastAPI + React，后端提供数据查询、工具调用和 AI 编排，前端承担工作台式交互。

### 5.2 最值得学习的设计

#### 一个客观数据层，多种 AI 出口

后端数据能力先统一进入 `tools.py`，再被 Chat、MCP、Debate 等不同入口复用。新增工具时不需要分别修改每种 AI 工作流。

该模式适合 Platform Experiment：

```text
Research Query / Data Service
          │
          ▼
统一 Research Tool Registry
          ├─► 金融AI分析
          ├─► 页面“问 AI”
          ├─► MCP / Agent
          └─► 固定研究工作流
```

#### 工具层先裁剪再交给模型

`tools.py` 不把上游原始响应直接塞给模型，而是：

- 只取最近 N 条。
- 保留关键字段。
- 增加必要汇总。
- 控制 token。
- 将异常转成结构化 error，让模型继续处理其他工具。

这对金融 AI 很重要。数据越多不代表推理越好，未经裁剪的原始数据会淹没核心证据。

#### 事实底稿先行

多空辩论不是让模型自由决定要调用哪些数据，而是先按固定清单拉取客观底稿，再让不同角色基于同一份事实立论。

该模式具有以下价值：

- 可复现。
- 多方和空方使用相同数据。
- 数据缺口明确。
- 不允许模型编造未获取的数字。
- 输出终点是“分歧与验证清单”，不是交易结论。

这比“多 Agent 最后给买卖建议”的常见模式更适合研究平台。

#### 对空数据进行语义区分

项目区分：

- 合法无记录。
- 数据源没有返回。
- 配置或依赖缺失。
- 单项失败但整体可以继续。

这是值得直接吸收的思想。空数组不能自动解释成“没有事件”，也可能是来源异常。

#### 渐进式进度反馈

底稿包含多个数据项，项目通过流式事件不断告诉前端已完成哪一项，避免长时间白屏。

后续对耗时研究任务、批量筛选、AI 报告和数据刷新都可采用统一进度事件。

### 5.3 需要特别注意的结构问题

#### 上游数据工具与运行时代码存在双轨

仓库中内嵌了较新的 `a-stock-data` 和 `global-stock-data` 副本，但运行时仍维护独立的：

- `backend/astock.py`
- `backend/gstock.py`

其中 `backend/astock.py` 是面向应用的裁剪实现，仍包含与完整上游不同的依赖、路由和数据层；`backend/gstock.py` 也明确只移植东财子集，不等于完整启用 `global-stock-data`。

这未必是功能错误，但会形成明显的版本漂移风险：

- 上游 Skill 修复了字段或路由，应用侧未必同步。
- README 中的数据能力版本不等于运行时实际暴露能力。
- 同一数据源逻辑可能维护两份。

Platform Experiment 后续应避免“复制一份 Provider 代码到业务后端”的做法，应由唯一 Provider 实现被多个模块复用。

#### 个人本地应用与机构平台差异较大

Vibe-Research 的特点包括本地存储、浏览器保存配置、单一 API Key、默认宽松 CORS 和进程内调度。这些设计适合个人自托管，但不适合作为机构平台的权限、审计和数据治理方案。

### 5.4 对 Platform Experiment 的主要价值

最值得参考的不是持仓页或个人研报页，而是：

1. Research Tool Registry。
2. 客观事实底稿。
3. 工具结果裁剪。
4. 数据缺口显式化。
5. NDJSON 或 SSE 式进度流。
6. “问 AI”携带当前页面研究上下文。
7. 反思审计与证据核查。
8. 页面级局部失败和降级。

### 5.5 不应直接迁移的部分

- 本地个人持仓作为平台正式持仓。
- 浏览器内保存敏感模型密钥。
- 单全局 API Key 作为正式权限体系。
- 进程启动时直接启动后台调度器。
- 页面直接绑定具体数据源函数。
- 把完整数据工具代码复制进多个后端模块。
- 将 AI 分析结果当成 Research Data 权威事实。

## 6. global-stock-data 研究

### 6.1 项目定位

`global-stock-data` 是面向 AI 编程助手的美股、港股和美国官方数据工具箱。其优势不在于已经构建了完整市场数据服务，而在于汇总了大量经过验证的端点、字段、合规要求和异常处理经验。

覆盖能力包括：

- 美股、港股行情。
- K 线和技术指标。
- 财务三表、关键指标和机构持仓。
- SEC EDGAR Filing 与 XBRL。
- CBOE 期权链、希腊字母和 0DTE。
- FINRA 空头成交量。
- SEC 当日申报事件流与全文检索。
- EDGAR Frames 全市场横截面。
- 美债收益率曲线。
- CFTC COT。
- 财报日历。

### 6.2 最值得学习的设计

#### 官方源优先与合规分级

项目把来源分成 S、B、C 等级，并明确指出“官方源不等于可自由商用”。该思想应成为 Platform Experiment 数据源目录的正式字段，而不是只写在说明文档里。

建议后续每个数据源至少维护：

- `sourceId`
- `providerName`
- `licenseTier`
- `commercialUse`
- `redistributionAllowed`
- `authenticationType`
- `rateLimit`
- `termsReviewedAt`
- `termsUrl`
- `owner`
- `fallbackSourceId`

#### 按来源限速

项目为不同域名配置不同限速，并使用线程锁避免并发击穿。相比简单的“记录上次调用时间”，线程安全的限速更可靠。

#### 明确错误语义

项目区分：

- `DataNotAvailable`：该日或该标的确实无数据，可以安全回退。
- `RuntimeError`：网络、限流、权限或配置错误，必须暴露。
- `ValueError`：调用参数或市场类型错误。

特别值得学习的是：不能把所有 403 都解释成无数据。必须判断是对象不存在、User-Agent 未声明、限流还是权限拒绝。

#### 标的与代码映射

项目处理了 ticker、CIK、东财 secid、SECUCODE、港股代码等多套编码规则。对于 Platform Experiment，这说明 Instrument Master 是必要基础设施，不能把代码转换散落在各组件中。

### 6.3 可直接作为数据源候选的能力

优先级较高且相对适合正式研究数据层的候选：

- SEC EDGAR Filing。
- SEC XBRL。
- SEC Frames 横截面。
- US Treasury 收益率曲线。
- CFTC COT。

需要进一步核实条款或获得授权的候选：

- FINRA 数据。
- CBOE 期权数据。
- Nasdaq 日历。
- Yahoo Finance。
- 东财、新浪、腾讯的美港股数据。

### 6.4 不能直接视为生产服务的原因

- 主要实现集中在一个大型 `SKILL.md`，不是稳定 Python Package 或独立服务。
- 不同数据层尚未统一成完整的跨来源 DTO。
- 多数调用使用同步 `requests`，不适合直接放入高并发异步 Web 服务。
- 缺少统一持久化、历史版本、Point-in-Time、公司行为和修订管理。
- 免费和零鉴权不代表 SLA、稳定性和商用权利。
- 部分来源属于网页前端接口，长期稳定性有限。

### 6.5 对看板栏目的映射

- 宏观：Treasury、CFTC。
- 美股：SEC、财务、期权、做空、申报事件。
- 全球：主要指数、利率和跨市场数据候选。
- 商品：CFTC 持仓可作为一部分，但不足以覆盖库存、基差、期限结构和供需。
- 交易工具：SEC 全文检索、市场筛选器、期权结构分析。

## 7. a-stock-data 研究

### 7.1 项目定位

`a-stock-data` 是 A 股数据源和接口经验最丰富的参考对象之一，覆盖行情、研报、板块、资金、财务、公告、打板、期权和互动数据。

主要层次：

- 行情。
- 研报。
- 信号与板块。
- 资金面与筹码。
- 新闻。
- 基础数据和财务。
- 公告。
- 打板情绪。
- ETF 期权。
- 舆情和互动。

### 7.2 最值得学习的设计

#### 数据源优先级

项目明确优先使用相对不容易封 IP 的来源，将高风控来源仅用于独有数据。这比“所有数据都走一个网站”更具韧性。

#### 统一请求入口与防封

东财请求集中通过 `em_get`，包含：

- Session 复用。
- 最小调用间隔。
- 随机抖动。
- 连接重试。
- 对 429 和 5xx 的退避。

后续 Provider 层应统一做限速、重试、熔断、指标和日志，而不是每个函数单独处理。

#### 真实取数验活

对 mootdx 服务器不是仅检测 TCP 可连接，而是进一步执行真实 K 线请求，避免“握手成功但返回空数据”的假健康状态。

这个原则应推广到所有 Provider Health Check：

- 网络可达不等于数据可用。
- HTTP 200 不等于字段有效。
- 返回空结构不等于服务健康。

#### 代码和市场路由

项目积累了大量 A 股代码路由、ETF、指数、北交所号段和歧义处理经验。该知识应进入统一 Instrument Master 和 Mapping Service，而不是散落在行情、板块和财务函数里。

#### 主源与备用源

项目对多个能力提供备用来源，并记录主源失效时的降级方式。对研究平台而言，Provider Fallback 应是显式策略，不能隐藏在组件内部。

### 7.3 对 A 股看板的高价值能力

- 宽基指数与 ETF 行情。
- 全市场成交额排名。
- 上涨、下跌、涨停、跌停和打板情绪。
- 行业板块表现。
- 板块资金流。
- 个股所属行业、概念和地域。
- 融资融券。
- 大宗交易。
- 股东户数。
- 解禁。
- 龙虎榜。
- 研报、一致预期和公告。
- ETF 期权。

其中最适合优先映射到“对冲基金看板 A 股栏目”的是：

1. 宽基指数。
2. 市场广度。
3. 成交额结构。
4. 行业表现。
5. 板块资金流。
6. 风格和主题轮动的基础数据。

### 7.4 需要谨慎处理的部分

- 申万一级、二级、三级分类必须有稳定 ID、版本和生效日期，不能直接用混合板块名替代。
- 东财或同花顺概念分类不能等同于正式行业分类。
- 北向资金等数据披露规则已经发生变化，历史实现不能默认持续有效。
- 网页前端接口的商用与再分发权利需要单独确认。
- 资金流字段属于供应商算法口径，不能在 UI 中无来源地表述为客观资金真值。
- K 线、指数和财务数据需要交易日历、复权、公司行为和 Point-in-Time 管理。

### 7.5 不能直接照搬的部分

- 将完整实现长期保存在一个 Markdown Skill 文件中。
- 在业务页面直接调用数据源函数。
- 同步阻塞式批量抓取。
- Provider 原始字段直接进入 Vue View Model。
- 把来源返回的行业或概念名称直接作为平台稳定主键。
- 在缺少许可确认时把数据作为正式商业数据集对外展示。

### 9.1 Provider 层职责

Provider Adapter 负责：

- 请求和鉴权。
- 限速和重试。
- 字段解析。
- 来源特定代码映射。
- 来源健康检查。
- 原始响应留存，适用时。
- 转换为统一 DTO。

Provider Adapter 不负责：

- 页面展示。
- 研究结论。
- AI 分析。
- 跨来源最终排序。
- 正式交易报价判定。

### 9.2 Research Service 职责

Research Service 负责：

- 跨来源合并。
- 单位和币种转换。
- 频率与交易日对齐。
- 历史分位和统计计算。
- 事件、资产和主题映射。
- 质量状态和新鲜度判断。
- Last Known Good。
- 查询缓存和版本。

### 9.3 UI 层职责

UI 只读取统一 View Model，不认识：

- 东财字段号。
- Yahoo crumb。
- Kalshi `*_dollars`。
- Polymarket JSON 字符串字段。
- SEC CIK 解析细节。
- mootdx 服务器地址。

## 10. 建议的统一数据 Envelope

四个参考项目共同暴露出一个问题：仅返回 `data` 不够。后续研究查询至少应携带：

```ts
interface ResearchDataEnvelope<T> {
  data: T
  sourceId: string
  providerName: string
  observedAt?: string
  publishedAt?: string
  fetchedAt: string
  asOf: string
  frequency?: string
  timezone?: string
  marketCalendar?: string
  unit?: string
  currency?: string
  datasetVersion?: string
  calculationVersion?: string
  qualityStatus: "verified" | "partial" | "stale" | "missing" | "estimated" | "error"
  freshnessStatus: "live" | "delayed" | "snapshot" | "historical"
  licenseTier?: "S" | "B" | "C" | "licensed" | "unknown"
  isEstimated?: boolean
  warnings?: string[]
}
```

其中应特别区分：

- `observedAt`：数据对应的观测时间。
- `publishedAt`：来源正式发布时间。
- `fetchedAt`：平台抓取时间。
- `asOf`：当前结果的数据截止时间。

这比只显示“更新时间”更准确。

## 11. 建议的错误和降级语义

参考四个项目后，建议未来统一错误码至少包括：

- `NO_DATA`：该标的或日期确实没有数据。
- `NOT_PUBLISHED`：数据尚未发布。
- `PROVIDER_UNAVAILABLE`：来源临时不可用。
- `RATE_LIMITED`：触发限速。
- `AUTH_REQUIRED`：缺少鉴权或 User-Agent 声明。
- `LICENSE_RESTRICTED`：当前环境不允许使用该来源。
- `SCHEMA_CHANGED`：来源字段发生变化。
- `PARTIAL_DATA`：部分来源或字段缺失。
- `STALE_DATA`：仅能返回上一份有效快照。
- `INVALID_INSTRUMENT`：标的代码或市场不匹配。
- `MAPPING_MISSING`：缺少 Instrument、CIK、行业或板块映射。

页面不得把以上状态统一显示为“暂无数据”。

## 13. 明确不建议的做法

- 不把四个仓库整体复制进 Platform Experiment。
- 不让 Vue 直接请求第三方数据源。
- 不把 `SKILL.md` 当成正式运行时代码包。
- 不在多个模块复制同一 Provider 逻辑。
- 不把零鉴权等同于可商用。
- 不把 HTTP 200 等同于数据有效。
- 不让空拉取覆盖有效数据。
- 不把来源板块名直接当平台稳定行业 ID。
- 不把预测市场概率描述为官方预测。
- 不把研究行情自动升级为执行行情。
- 不让 AI 输出反向修改 Research Data 原始事实。
- 不在未完成许可核验前对外分发来源数据。

## 14. 当前参考项目无法解决的缺口

即使吸收四个项目，Platform Experiment 仍需自行建设：

- 机构级权限、用户和数据范围控制。
- 数据血缘、审计和修订历史。
- Point-in-Time 数据。
- 公司行为与复权体系。
- 统一交易日历、时区和频率对齐。
- 多币种和单位转换。
- 正式 Instrument Master。
- 申万行业版本管理。
- 数据供应商合同与许可治理。
- 任务队列、分布式锁和多实例部署。
- 长期历史仓库和查询性能。
- Research Data 与 Execution Market Data 的严格隔离。
- 商品期限结构、库存和供需数据。
- 加密 ETF、财库公司、资金费、OI 和链上数据。

因此，这四个项目应被视为强参考和能力加速器，而不是最终架构答案。

## 15. 后续使用规则

1. 后续每次吸收具体能力时，单独建立功能分支。
2. 先确认上游提交和数据源条款，再决定移植。
3. 优先提取设计和接口经验，不默认复制实现。
4. 直接采用代码时保留许可证和版权声明。
5. 新增 Provider 必须配套契约测试、来源健康检查和字段变更检查。
6. 参考项目更新时，不自动覆盖平台实现；先比较变更，再人工决定是否同步。
7. 当前文档保持 `reference-only`，不直接进入 active 架构或需求文档。

## 16. 最终判断

用户将这四个项目作为后续优化的主力参考对象是合理的。

它们最有价值的组合不是“功能很多”，而是已经沉淀了大量真实数据工程中容易被低估的问题：

- 字段会变化。
- 同一状态码可能有不同语义。
- 代码映射会静默指向错误标的。
- 上游返回空不一定代表没有数据。
- 进程内缓存和本地快照有适用边界。
- 免费数据与商用许可不是同一概念。
- AI 需要高密度客观底稿，而不是原始数据堆积。
- 个人应用和机构平台不能使用同一套权限与治理方案。

后续 Platform Experiment 应以这四个项目为参考，加速 Provider、研究工作流和数据稳定性建设，但最终必须收敛到自身的统一领域模型、数据契约、权限、审计和模块边界。
