## 1. 审视目的

本文以基金平台技术负责人的视角，对当前 Variable-Global 项目进行一次独立于单项需求和单项架构设计的全局审视。

审视重点不是判断页面是否美观或文档是否足够长，而是回答：

1. 当前产品究竟是什么平台。
2. 现有需求和架构能否约束真实开发。
3. 当前代码处于原型、开发、测试还是生产准备阶段。
4. 是否具备接入 Crypto、MT5 和真实资金的工程基础。
5. 是否具备基金平台所需的数据、账本、权限、审计、运维和治理能力。
6. 下一阶段继续写文档、建设工程和执行 PoC 的合理顺序是什么。

本文是审视和建议，不直接批准 V1、技术选型、实盘接入或开发排期。

## 2. 总体结论

### 2.1 一句话判断

当前项目已经形成一套较成熟的**内部投资研究、策略交易、策略运营与风险管理平台目标设计**，但工程实现仍主要是前端 Mock 原型，尚不是可以接入真实资金的基金平台系统。

### 2.2 当前最强的部分

当前最强的不是代码，而是：

- 一级产品模块和策略范围已经清楚。
- 三类套利策略的交易与损益口径已经显著细化。
- 策略管理、风险、对账、EconomicEvent、PnL 和审计的边界已经建立。
- 模块化单体 Platform Backend 与独立 Execution Runtime 的方向正确。
- MT5、Crypto、CTP 和开源组件没有被错误地当作平台业务权威。
- 结果未知、幂等、恢复、对账、单腿暴露和人工处理已进入正式架构。

### 2.3 当前最大的风险

当前最大的风险是：

> 文档成熟度明显领先工程成熟度，容易让团队误以为项目已经接近可开发、可联调甚至可交易。

现实状态是：

- 仓库中尚无 `platform-backend` 工程。
- 仓库中尚无 `execution-runtime` 工程。
- 当前页面主要直接读取 Mock 和本地配置。
- 尚无真实 API、Command、Event、数据库迁移和 Runtime 契约实现。
- GitHub CI 没有真实运行。
- 自动化测试体系尚未建立。
- 权限模型在前端代码中仍是粗粒度 Role。
- 生产凭证、环境隔离、备份、恢复和发布均只有原则，没有落地实现。

## 3. 产品定位判断

### 3.1 当前实际产品定位

按照现有需求和架构，Variable-Global 当前最准确的定位应为：

> 面向内部投研、策略交易、策略管理、风险运营和数据核对的投资管理工作平台。

当前核心业务链是：

```text
研究和市场背景
→ 策略机会分析
→ 交易准备与执行
→ 订单、成交、持仓和账户
→ EconomicEvent 和策略损益
→ 风险、对账、审计和报表
```

这个定位与当前产品模块和六类策略是匹配的。

### 3.2 当前还不能宣称为完整基金行政管理平台

若目标中的“基金平台”包含完整基金运营和行政管理能力，当前仍缺少或尚未正式确认以下领域：

- Fund／Legal Entity：基金、产品、管理主体和法律实体。
- Portfolio／Book：组合、子组合、Book 和策略资金分配层级。
- Investor／Share Class：投资人、份额类别和持有人结构。
- Subscription／Redemption：申购、赎回、转让和资金到账。
- NAV Strike：估值日、NAV 计算、锁定、复核和发布。
- Valuation Policy：价格层级、估值源、Fallback 和估值调整。
- Administrator／Custodian／Prime Broker：行政管理人、托管人和主经纪商关系。
- Corporate Action：分红、拆合股、权益事件和基金费用。
- Cash and Treasury：公司现金、基金现金、保证金和策略资金的正式层级。
- Compliance：投资限制、适当性、集中度和合规报告。
- Finance Ledger：完整财务会计总账和法定报表。
- Investor Reporting：投资人报表、份额净值和披露。

因此当前应避免将策略 Economic Ledger 误称为完整基金会计系统。

### 3.3 推荐定位处理

短中期建议：

- 产品主线继续聚焦内部投研、策略、交易、风险、对账和策略损益。
- Fund、Portfolio、NAV 和正式财务领域在总体数据架构中预留稳定边界。
- 不在 V1 中建设完整基金行政管理能力。
- 对外或内部正式描述时，区分“投资管理与交易平台”和“完整基金行政管理平台”。

## 5. 已确认的正确决策

### 5.1 三工程主体

以下结构正确，应继续保持：

```text
admin-risk
├─ Vue 前端

platform-backend
├─ 模块化单体业务后端

execution-runtime
├─ 独立交易执行、Gateway 和 Worker
```

不建议：

- 将六层逻辑架构拆成六个服务。
- 立即引入 Kubernetes 和大量微服务。
- 让 Platform API 直接加载 MetaTrader5、Broker 或 Exchange SDK。

### 5.2 Platform 与 Runtime 权威分离

正确边界是：

- Platform Backend 拥有策略、权限、命令、执行批次、平台订单、风险、对账、EconomicEvent 和 PnL。
- Runtime 拥有连接、Worker、实时 OMS 缓存、外部请求和恢复位置。
- 外部系统拥有外部订单、成交、余额和持仓事实。
- Read Model 只服务查询。

### 5.3 开源组件按能力采用

当前没有将 vn.py、CCXT、aiomql、Freqtrade、rotki 和 NautilusTrader 整体吞入平台，这一决策正确。

继续要求：

- 外部组件通过 Adapter 和 Port 接入。
- 平台业务对象不继承外部框架对象。
- 组件采用必须经过版本、许可证、安全、恢复和对账 PoC。

### 5.4 交易可靠性原则

以下原则已经达到真实交易系统设计应有的方向：

- 命令受理不等于交易完成。
- 外部提交前预创建 platformOrderId。
- 至少一次传输加幂等消费。
- 结果未知不是失败终态。
- Runtime 重启后先同步、对账和恢复，再 READY。
- 单腿暴露和残腿具有独立状态。
- 人工处理、审批和审计进入正式链路。

## 6. 当前工程实现风险

### 6.1 后端和 Runtime 尚不存在

当前 GitHub 仓库中未发现：

- `platform-backend` 工程。
- `execution-runtime` 工程。
- 数据库迁移。
- Command Outbox／Event Inbox 实现。
- Runtime Journal 实现。
- Fake Gateway。
- Crypto 和 MT5 Adapter。

因此所有后端和交易基础设施结论目前仍是设计资产，而非已验证工程能力。

### 6.2 前端仍直接依赖 Mock

当前策略页面仍存在以下模式：

```text
Vue Page
→ import mock/data
→ computed / local ref
→ View Components
```

例如资费套利和策略管理页面直接导入 Mock 数据。

这意味着尚未完成：

- Repository Interface。
- Mock Adapter／API Adapter 切换。
- DTO 到 Domain／View Model 适配。
- Loading、Partial、Stale 和 Permission 状态的真实数据驱动。
- API 错误、重试和断线恢复。

前端下一阶段不能继续在页面中直接追加业务 Mock，而应先完成数据访问边界。

### 6.3 页面和本地数据仍存在硬编码

当前代码仍直接硬编码：

- Binance、OKX、Bybit。
- XAUTUSDT.P、XAUUSD、SHFE.au2606、AU9999。
- 默认日期和分辨率。
- 策略桌面列表。
- 页面本地标签和执行区切换。

这些值可以作为原型默认值，但不能成为正式产品配置和业务权威。

未来应由：

- StrategyDefinition／Version。
- Instrument 和 ContractSpecification。
- GatewayCapability。
- Route Context。
- Backend Query。

共同驱动。

### 6.4 View Model 类型过于字符串化

当前策略管理类型中大量使用：

- `value: string`。
- `[key: string]: string`。
- 已格式化金额、数量和百分比。

这适合作为展示层 View Model，但不能直接成为 API DTO 和 Domain Model。

后续必须分开：

```text
Domain Amount / Quantity / Price / Rate / Time
→ API DTO
→ Frontend Adapter
→ Formatted View Model
```

禁止用带逗号、单位和正负号的字符串参与金融计算。

### 6.5 当前权限实现过于粗粒度

当前前端 Role 仍以：

- SUPER。
- TEST。
- ADMIN。
- EMPLOYEE。
- GUEST。

为主要枚举，策略路由主要允许 ADMIN 和 EMPLOYEE。

这与已确认的：

```text
Role
+ Capability
+ Data Scope
+ Environment Scope
+ Trading Mode Scope
+ Approval Requirement
```

仍有显著距离。

结论：

- 现有 Role 只能作为原型菜单展示条件。
- 不能用于真实交易、资金、风险覆盖和数据修正授权。
- 后端建设时必须从 Capability 和 Scope 开始，而不是继续扩充前端 Role 枚举。

### 6.6 看板页面仍有大型单文件和内嵌数据

对冲基金看板主页面仍同时承担：

- 导航。
- 模块选择。
- 多类图表配置。
- 本地组件定义。
- 大量市场表格 Mock。
- 数据来源链接。

这种结构适合快速原型，但会阻碍：

- 数据源替换。
- 单独测试。
- 权限和数据质量处理。
- 图表性能优化。
- 模块级降级。

后续应按照栏目、Widget、Query 和 Adapter 拆分，不应继续向主页面追加大型数据常量。

## 7. 工程质量与 CI 风险

### 7.1 GitHub Actions 实际未生效

当前 Workflow 位于：

```text
admin-risk/.github/workflows/
```

GitHub 仓库只会从仓库根目录的：

```text
.github/workflows/
```

加载 Workflow。

当前提交没有 CI 状态检查，也与该目录问题一致。

P0 修正：

- 将有效 Workflow 移到仓库根目录。
- 明确工作目录为 `admin-risk`。
- 对目标分支和 Pull Request 运行。
- 将检查设为分支保护必需项。

### 7.2 当前没有正式自动测试入口

`package.json` 当前具有：

- build。
- type:check。
- lint。

但没有正式：

- unit test。
- component test。
- end-to-end test。

质量文档也明确 Vitest 和 Playwright 尚未启用。

最低升级顺序：

1. 纯函数、格式化、单位和金融计算 Vitest。
2. Adapter 和 Query 映射测试。
3. Strategy Registry 和路由一致性测试。
4. Playwright 核心页面和策略切换。
5. 后续交易 Command／状态恢复端到端测试。

### 7.3 类型检查只覆盖局部范围

`type:check` 当前使用 `tsconfig.strategy.json`，其主要覆盖策略页面，并排除：

- 公共组件。
- Store。
- 风险模块。
- 部分其他页面。

这可以作为历史债务阶段的临时门槛，但不能作为完整平台发布门槛。

建议建立两级门禁：

- `type:check:changed` 或策略子集：本地快速反馈。
- `type:check:full`：CI 必须执行，逐步清除历史错误后设为阻断。

### 7.4 依赖和工具链需要专项治理

当前前端继承自 vue-vben-admin，并保留较多通用后台依赖和旧工程配置。

上线前必须完成：

- 依赖清单和实际使用盘点。
- 许可证和供应链审查。
- Node、pnpm、Vue、Vite、TypeScript 的支持基线确认。
- 漏洞扫描和锁文件检查。
- 删除不再使用的富文本、编辑器、导出和通用后台依赖。
- 构建产物、Source Map 和环境变量安全检查。

不建议在尚未盘点时一次性大版本升级全部依赖；应先建立可重复测试和回滚。

## 8. 文档治理风险

### 8.1 文档质量高，但数量和重复度快速上升

当前已经形成大量：

- 模块需求。
- 策略专项。
- 总体架构。
- 后端专项。
- DRAFT。
- ADR。
- 历史交接和审计。

风险是：

- 相同对象在多份文档重复定义。
- active 入口未及时更新。
- Platform V5、V6 和 V6+ 元数据混用。
- 新增 ADR 后总入口遗漏。
- 开发人员无法快速确认唯一来源。

### 8.2 当前已观察到的漂移

包括：

- `docs/README.md` 尚未列入新 active 总体架构、Runtime 专项和 ADR-008。
- `StrategyDeskKey` 中仍包含历史 `spread` 值，而正式策略范围没有该策略。
- Mock 中的交易场所和正式策略需求存在不一致，例如部分跨所 Mock 使用 Gate／Binance，而正式目标是 Crypto 与 MT5。
- active 文档仍有 Platform V5／V6 与 V6+ 混合标记。

这些不一定立即造成运行错误，但说明文档、注册表、Mock 和代码尚未形成自动一致性约束。

### 8.3 建议的文档控制

- active 文档必须进入统一索引。
- 每个核心对象只有一个语义主文档。
- 策略 ID、模块 ID、状态和 PnL 归因建立机器可读注册表。
- 文档和代码之间增加自动一致性检查。
- DRAFT 不继续无限扩张，确认后进入 ADR 或 active，未采用则归档。
- 每次架构批次结束执行一次源事实审计。

## 9. 数据与基金平台领域缺口

### 9.1 当前数据架构仍停留在原则层

现有文档已经定义：

- 主数据。
- 交易事实。
- 经济事实。
- 当前状态。
- 快照。
- 派生结果。
- 治理记录。

但尚未形成统一的：

- 数据域总表。
- 核心对象关系图。
- 业务主键和唯一约束。
- 时间和 businessDate 模型。
- Currency、Money、Quantity 和 Unit 模型。
- 事件与表之间的映射。
- 数据保留、分区和归档矩阵。
- 数据质量规则目录。
- 物理数据库候选和迁移原则。
- 研究数据与交易事实的生命周期差异。

因此统一数据架构是正确的下一项工作。

### 9.2 必须补入 Fund 和 Portfolio 边界

即使 V1 不开发完整基金行政管理，也建议在数据架构中至少定义：

- LegalEntity。
- Fund。
- Portfolio／Book。
- StrategyAllocation。
- Account Ownership。
- Reporting Currency。
- Valuation Calendar。
- NAV／ValuationResult 预留边界。

否则后续账户、策略和损益可能直接挂在用户或展示名称上，难以扩展为正式基金组合体系。

### 9.3 Strategy Economic Ledger 与 Finance Ledger 必须继续分开

当前这一边界正确，但下一阶段要进一步定义：

- 哪些 EconomicEvent 进入策略账本。
- 哪些资金流只是 Capital Flow，不是 PnL。
- 哪些事件需要进入未来 Fund／Finance Ledger。
- PnLResult、NAV 和公司财务结果之间的关系。
- 对账和调整如何跨账本传播。

## 10. 交易与运行体系缺口

### 10.1 当前架构正确，但尚未经过任何 PoC

以下高风险假设尚未验证：

- MT5 一账户一 Terminal／Worker 的资源和稳定性。
- CCXT 与官方 SDK 的组合方式。
- Binance、OKX、Bybit 的统一订单和账户语义。
- 实际 FundingSettlement 的完整历史和去重。
- Runtime Journal 的崩溃一致性。
- Worker 崩溃后订单结果查询。
- Redis Streams、RabbitMQ 或其他通道的选择。
- vn.py EventEngine、OmsEngine、SpreadTrading 的实际复用价值。

### 10.2 PoC 必须验证失败路径

PoC 不能只验证“成功下单”，至少覆盖：

- 重复 Command。
- 下单超时但外部成功。
- 部分成交。
- 撤单结果未知。
- Runtime 崩溃。
- Worker 崩溃。
- Event 通道不可用。
- 外部手工订单。
- 订单回报乱序和重复。
- 账户、订单和持仓对账差异。

## 11. 安全、合规和运营缺口

### 11.1 安全原则完整，实施为零

当前安全文档已经涵盖：

- 最小权限。
- 环境和 TradingMode 隔离。
- Secret 管理。
- TLS。
- 审计。
- 备份和恢复。
- 运维权限分离。

但当前代码中尚无可验证实现。

### 11.2 基金平台应增加的运营治理

后续正式架构和运行手册应覆盖：

- 访问权限定期复核。
- Live 账户和密钥轮换。
- 交易前后控制证据。
- 重大故障和资金事件分级。
- 生产变更审批和回滚。
- 值班、告警和人工接管。

## 13. 继续工作的推荐顺序

审视后，项目不应回到无边界地补写所有文档，也不应立即开始真实 Gateway 开发。

推荐顺序：

```text
技术负责人全局审视
→ 统一数据架构
→ 公共领域对象和状态收敛
→ Runtime／API 契约
→ 安全、部署和工程质量门禁
→ 架构一致性审计
→ V1 范围
→ 工程骨架和 PoC
```

## 14. 进入真实资金前的不可妥协门槛

任何 Live 交易前必须至少具备：

- 后端服务端 Capability 和 Scope 权限。
- 独立 Live 凭证和账户白名单。
- Maker／Checker 或明确审批政策。
- 交易 Command 幂等。
- platformOrderId 预创建。
- Runtime Journal。
- 结果未知处理。
- 订单、成交、持仓和账户对账。
- GlobalTradingBlock 和受控减险动作。
- 审计日志。
- 告警和人工接管。
- 自动化测试和故障测试。
- 备份、恢复和演练。
- 依赖和 Secret 安全检查。
- Demo／Paper 验收记录。

未达到上述门槛时，系统只能用于研究、展示、模拟或只读接入。

## 15. 最终判断

当前架构不需要推翻，六层逻辑职责、模块化单体 Platform Backend 和独立 Execution Runtime 是适合当前团队和产品阶段的方向。

但从基金平台技术负责人的角度，下一阶段必须完成三个转变：

1. 从“文档完整”转向“关键契约可验证”。
2. 从“页面 Mock”转向“数据和接口边界”。
3. 从“功能展示”转向“安全、对账、恢复和运营证据”。

在此基础上，统一数据架构应成为下一项正式架构工作；V1 仍应在完整架构和关键 PoC 后确定。
