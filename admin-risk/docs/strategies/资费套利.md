## 1. 文档定位

本文定义资费套利策略的业务目标、市场和账户范围、策略身份、行情分析、资金费语义、现货与永续双腿执行、订单成交与持仓关系、EconomicEvent、损益归因、账户资金、风险、对账、数据质量、策略管理 Read Model、外部组件能力依赖和验收标准。

本文是以下专项口径的唯一来源：

- 仅做正资金费率机会。
- 现货腿与永续腿的业务结构。
- 预计 Funding 与实际 Funding 结算的区分。
- 库存费累计收益、综合基差损益和累计交易成本的定义。
- 现货平台溢价损益与永续基差损益合并为综合基差损益。
- 不设置“配平误差”一级损益归因。

通用交易命令、权限、状态、运行可靠性和页面共同规则仍以上位文档为准，本文不重复建立第二套通用平台模型。

## 2. 策略定位与核心约束

资费套利是通过同时持有现货与永续合约的反向头寸，降低基础资产价格方向暴露，并主要获取正向资金费结算及现货—永续价格关系变化收益的双腿套利策略。

当前正式原则：

1. 仅做正资金费率方向。
2. 典型结构为买入现货、卖出永续。
3. 现货腿和永续腿原则上使用同一基础资产。
4. 两腿按照标准化名义价值进行目标配平。
5. Funding 预计值只用于机会判断，实际结算记录才进入正式库存费收益。
6. 交易手续费、已确认滑点和其他执行成本单独作为交易成本。
7. 现货平台溢价与永续基差不拆成两个一级损益项。
8. 数量偏差、时间差和残腿问题进入执行状态、风险、成本或异常记录，不建立配平误差一级损益。
9. 平台不因为资金费率为正就自动认定机会可执行，还必须评估基差、成本、流动性、账户资金和风险。

## 4. 核心用户问题

### 4.1 行情分析

- 当前资金费率是否为正，数值是否足够高？
- 当前显示的是上一期、即将结算还是下一期预测 Funding？
- 资金费率结算间隔和下一结算时间是什么？
- 费率在历史中处于什么位置，是否具有持续性？
- 现货与永续综合价差当前是否有利？
- 哪个交易所、标的和账户组合更适合？
- 订单簿深度、成交量和预计滑点是否支持目标规模？
- 预计 Funding、基差变化和交易成本合计后，净收益是否为正？
- 数据是否新鲜、完整和可比较？

### 4.2 交易准备与执行

- 当前 StrategyVersion 和 StrategyInstance 是否允许该交易？
- 现货腿和永续腿分别使用哪个平台、账户和标的？
- 两腿按什么价格、合约乘数和单位换算数量？
- 采用并行、主动腿／被动腿还是人工确认执行？
- 两腿是否达到目标名义价值关系？
- 当前是否出现单腿成交、部分成交或结果未知？
- 暴露数量、方向、名义价值和持续时间是多少？
- 是否允许继续补单、重新配平、撤单或紧急减险？

### 4.3 持有与管理

- 实际收到多少 Funding，来自哪个结算周期和账户？
- 累计收益来自库存费、综合基差还是交易成本？
- 当前现货和永续持仓是否仍然配平？
- 资金费率是否反转或低于策略阈值？
- 两端账户余额、保证金和可用资金是否安全？
- 订单、成交、Funding 结算和调整记录能否完整追溯？
- 外部账户与平台记录是否已对账？

## 5. 策略身份、版本与实例

### 5.1 StrategyDefinition

稳定定义：

- `strategyId = funding`。
- 正式名称：资费套利。
- 执行类型：平台执行策略。
- 腿模型：双腿。
- 主要资产类型：Crypto 现货与永续。
- 主要收益来源：正向 Funding 与综合基差变化。

### 5.2 StrategyVersion

每个正式版本至少记录：

- 适用交易所和产品范围。
- 允许的基础资产和交易对。
- 仅正费率方向约束。
- Funding 机会判断口径。
- 历史统计窗口和年化口径。
- 目标配平口径和容忍范围。
- 允许的执行模式。
- 最大订单规模、策略名义价值和集中度限制。
- 最大单腿暴露和最大残腿时间。
- Funding 反转、基差恶化和退出政策。
- 手续费、滑点和其他成本口径。
- PnL 归因公式和正负号规则。
- 数据源和质量门槛。
- 生效时间、审批和替代关系。

历史执行和 PnLResult 必须关联交易发生时的 StrategyVersion，不能使用当前版本无痕重解释历史结果。

### 5.3 StrategyInstance

具体实例至少表达：

- `strategyInstanceId`。
- StrategyVersionId。
- DeploymentEnvironment。
- TradingMode。
- 运行状态。
- 目标交易所、账户和资产范围。
- 实例级额度和风险参数。
- 实例是否允许开仓、平仓和调整。
- 创建、启用、暂停和终止时间。

### 5.4 StrategyAccountBinding

账户用途至少区分：

- `spot_leg`：现货腿账户。
- `perpetual_leg`：永续腿账户。
- `settlement`：资金或费用结算用途，适用时。
- `observation_only`：只读观察账户，适用时。

每个绑定至少记录：

- AccountId。
- 交易所和账户类型。
- 允许的 Instrument 范围。
- 允许的 TradingMode。
- 分配额度或使用上限。
- 绑定生效和失效时间。
- 是否允许正式下单。
- 审批和审计记录，适用时。

## 6. 市场、交易所与标的范围

当前产品范围包括：

- Binance。
- OKX。
- Bybit。

范围说明：

- 三家交易所均属于产品候选范围，不代表每个环境和每项能力均已接入。
- 行情、账户、交易、Funding、划转和借贷是不同能力，必须通过 GatewayCapability 分别声明。
- 同一交易所内现货与永续可以构成策略组合。
- 不同交易所之间的现货和永续也可以构成组合，但需要额外考虑资金分布、账户风险、币种和传输限制。
- 当前策略默认不依赖自动借币，因此典型正费率结构要求现货端具有可用资产或可直接购买。

### 6.1 Instrument 与 Symbol Mapping

平台使用稳定 InstrumentId，不直接以外部 symbol 字符串作为业务身份。

每个现货和永续 Instrument 至少需要：

- 外部交易所和市场类型。
- 基础资产和计价资产。
- 现货、线性永续或其他产品类型。
- 外部 symbol。
- 合约乘数和数量单位。
- 价格精度和数量精度。
- 最小数量、最小名义价值和数量步进。
- 保证金币种和结算币种。
- 当前可交易状态。
- 元数据版本和更新时间。

## 7. 交易腿与账户结构

### 7.1 现货腿

典型方向：买入并持有现货。

至少表达：

- AccountId。
- VenueId。
- InstrumentId。
- 买卖方向。
- 目标数量。
- 目标名义价值。
- 订单类型和价格政策。
- 成交数量和平均价。
- 当前可用数量、冻结数量和持仓市值。

### 7.2 永续腿

典型方向：卖出永续合约。

至少表达：

- AccountId。
- VenueId。
- InstrumentId。
- PositionSide 和账户持仓模式。
- 目标合约数量和标准化基础资产数量。
- 目标名义价值。
- 保证金模式和杠杆信息。
- 订单类型和价格政策。
- 成交数量、平均价和当前持仓。
- 强平价格或风险距离，数据源支持时。

### 7.3 标准化配平关系

两腿不能只比较外部订单数量，必须先转换为统一基础资产数量或统一名义价值。

候选表达：

```text
spot_base_quantity
perpetual_base_equivalent_quantity
spot_notional
perpetual_notional
hedge_ratio
balance_deviation
```

平台必须保留：

- 原始数量。
- 原始单位。
- 合约乘数。
- 转换后数量。
- 使用价格和时间。
- 目标配平比例。
- 容忍范围。
- 当前实际偏差。

## 8. Funding 数据语义

### 8.1 Funding 类型必须区分

至少区分：

- `previousFundingRate`：上一结算周期已完成或已确认的费率。
- `currentFundingRate`／`upcomingFundingRate`：下一次即将结算的动态费率。
- `nextFundingRateEstimate`：更远一期预测值，数据源支持时。
- `FundingSettlement`：账户实际发生的资金费结算记录。

命名可以根据平台统一模型调整，但语义不得混淆。

### 8.2 FundingRateSnapshot

至少包含：

- VenueId。
- InstrumentId。
- Funding Rate。
- Rate Type。
- Funding Interval。
- Funding Time。
- Source Time。
- Received At。
- 数据来源。
- DataQualityStatus。
- 是否为预测、动态值或已完成值。

### 8.3 FundingSettlement

实际结算至少包含：

- `fundingSettlementId` 或稳定 EconomicEventId。
- AccountId。
- InstrumentId。
- 外部结算 ID。
- 结算周期。
- 实际费率，能够获得时。
- 参考名义价值或持仓数量，能够获得时。
- 实际结算金额。
- 币种。
- occurredAt 和 receivedAt。
- 来源和原始字段引用。
- 对账状态。

实际库存费累计收益只读取 FundingSettlement 或经正式确认的等价账户账本事实，不使用预计 Funding Rate 直接入账。

## 9. 行情和数据需求

### 9.1 必要实时或准实时数据

- 现货 Bid／Ask 和必要深度。
- 永续 Bid／Ask 和必要深度。
- Mark Price。
- Index Price，数据源支持时。
- Last Price，仅作为补充，不能默认替代可执行价格。
- Funding Rate 和下一结算时间。
- 现货与永续成交量和流动性摘要。
- Instrument 和 ContractSpecification。
- 账户余额、保证金和当前持仓。

### 9.2 历史数据

- Funding Rate 历史。
- Funding Settlement 历史。
- 现货和永续价格历史。
- 综合基差历史。
- 订单簿或滑点样本，具备时。
- 交易手续费和费率等级历史，适用时。

### 9.3 数据质量

至少检查：

- 两腿 sourceTime 差异。
- 报价新鲜度。
- Funding Time 和 Interval 是否完整。
- Instrument 元数据是否有效。
- 价格、数量和合约乘数是否可换算。
- Mark、Index、Last 和 Bid／Ask 是否被正确区分。
- 多来源是否冲突。
- 历史 Funding 是否有缺口或重复。
- 实际结算是否完整同步。

缺失 Funding、报价、合约规格或账户数据时，不得以零替代并继续正式执行。

## 10. 行情分析与机会指标

### 10.1 页面结构

至少包含：

1. 交易所、账户和标的上下文。
2. 当前 Funding 和结算倒计时。
3. Funding 历史曲线和分布。
4. 现货—永续综合基差图表。
5. 多交易所机会比较。
6. 流动性、成本和目标规模预估。
7. 账户资金与保证金摘要。
8. 数据来源、时间、质量和计算版本。

### 10.2 当前 Funding 指标

建议展示：

- 当前即将结算费率。
- 上一实际或已完成费率。
- 下一预测费率，具备时。
- Funding Interval。
- 下一结算时间。
- 倒计时。
- 历史均值、中位数和分位。
- 连续正费率周期。
- 近期费率波动。

### 10.3 综合基差

候选基础表达：

```text
comprehensive_basis = perpetual_reference_price - spot_reference_price
```

也可以表达为比例或年化，但必须同时记录：

- 使用 Bid、Ask、Mid、Mark 或其他价格口径。
- 开仓和退出方向。
- 原始币种和统一币种。
- 计算时间和两腿时间差。
- 计算版本。

机会分析需要优先使用方向相关的可执行价格，而不是无条件使用 Last 或 Mid。

### 10.4 预计收益

预计收益可以由以下候选项组成：

```text
预计 Funding 收益
+ 预计综合基差变化收益
+ 预计其他已确认收益
+ 预计交易成本
= 预计净收益
```

预计交易成本通常为负值，至少包含：

- 现货手续费。
- 永续手续费。
- 开仓和退出预计滑点。
- 必要的资金划转、借贷或其他成本，正式启用时。

预估年化必须明确：

- 使用的 Funding 是否为单期、滚动平均或情景假设。
- 年化周期。
- 预计持有时间。
- 是否假设费率持续不变。
- 是否包含基差和交易成本。

预估结果不能与实际 PnLResult 混用。

## 11. 交易准备与 ExecutionPlan

### 11.1 TradeIntent

至少包含：

- StrategyInstanceId。
- 开仓、平仓、调整或补对冲。
- 现货腿和永续腿账户。
- 两腿 InstrumentId。
- 目标基础资产数量或名义价值。
- 目标配平比例和容忍范围。
- 两腿方向。
- 订单类型、价格和保护参数。
- 执行模式。
- 最大滑点。
- 最大单腿暴露时间。
- 部分成交和残腿政策。
- 预计收益、成本、资金和风险计算引用。

### 11.2 ExecutionPlan 候选

资费套利可以支持：

- `parallel`：两腿近似同时提交。
- `active_passive`：主动腿成交后，以实际成交量驱动被动腿。
- `sequential`：一腿达到指定状态后提交另一腿。
- `manual_confirmed`：关键步骤人工确认。
- `simulation`：使用模拟执行服务。

每个实例和 Gateway 不一定支持所有模式。

ExecutionPlan 至少表达：

- 主动腿和被动腿。
- 订单政策。
- 数量换算和取整方式。
- 最大滑点和价格保护。
- 超时和撤单政策。
- 部分成交处理。
- 最大裸露时间。
- 残腿补救。
- 是否允许追价、转市价或紧急对冲。
- 计划版本。

### 11.3 服务端执行前校验

除平台通用校验外，资费套利至少检查：

- Funding 当前为正且满足策略版本条件。
- Funding 数据时间和结算时间有效。
- 现货和永续基础资产匹配。
- 数量、乘数和名义价值换算完整。
- 两个账户具有对应现货和永续交易能力。
- 现货端有足够计价资产或基础资产。
- 永续端保证金和持仓模式满足要求。
- 两腿订单类型均被 Gateway 支持。
- 当前流动性和最大滑点满足限制。
- 目标规模不超过实例、账户和标的限制。
- 当前不存在禁止新增风险的 GlobalTradingBlock。
- 当前未存在冲突或重复的未完成执行。

## 12. 执行、订单、成交与持仓

### 12.1 标准业务链路

```text
TradeIntent
→ TradeCommand
→ ExecutionBatch
→ ExecutionPlan
→ Spot LegInstruction + Perpetual LegInstruction
→ 预创建平台 Order
→ Gateway 提交外部订单
→ Order 回报
→ Fill
→ Position 更新
→ 配平与暴露判断
→ 完成、异常或人工处理
```

### 12.2 稳定身份

必须使用：

- tradeCommandId。
- executionBatchId。
- legInstructionId。
- platformOrderId。
- clientOrderId 或等价外部映射。
- externalOrderId。
- executionId／fillId。
- externalTradeId。

重复订单或成交事件不得重复增加持仓、费用和 PnL。

### 12.3 配平与暴露

分别表达：

- 目标基础资产数量。
- 现货实际成交数量。
- 永续基础资产等价值。
- 当前数量偏差。
- 当前名义价值偏差。
- ExecutionBalanceStatus。
- ExposureStatus。
- 暴露方向、数量、名义价值和持续时间。

未配平是执行和风险状态，不自动形成“配平误差”一级 PnL。

### 12.4 持有期间

持有期间需要持续监控：

- Funding Rate 和下一结算时间。
- 实际 FundingSettlement。
- 综合基差。
- 两腿持仓和配平。
- 永续保证金、强平距离和 ADL 等状态，数据源支持时。
- 现货资产可用与冻结状态。
- 账户和交易所健康。
- 资金费率反转和退出条件。

### 12.5 平仓

平仓必须作为新的 TradeCommand／ExecutionBatch 或明确关联原策略头寸的关闭批次，保留：

- 关闭原因。
- 目标关闭数量。
- 实际关闭数量。
- 两腿执行顺序。
- 残余持仓。
- 费用和实际成交。
- 最终配平和对账结果。

## 13. EconomicEvent

从第一笔交易开始至少记录：

- Spot Fill。
- Perpetual Fill。
- Spot TradingFee。
- Perpetual TradingFee。
- FundingSettlement。
- TransferFee，正式启用时。
- BorrowInterest，正式启用时。
- ManualAdjustment。

每个 EconomicEvent 至少关联：

- StrategyId、StrategyVersionId 和 StrategyInstanceId。
- AccountId。
- InstrumentId。
- ExecutionBatchId、OrderId 或 FillId，适用时。
- 外部 ID。
- 事件类型。
- 金额、币种和单位。
- occurredAt、receivedAt 和 businessDate。
- 数据来源。
- 对账与质量状态。
- 是否为原始事实或正式调整。

预计 Funding、预计手续费和机会预估不属于实际 EconomicEvent。

## 14. 损益结构与核对

### 14.1 累计总损益

当前正式结构：

```text
累计总损益
= 库存费累计收益
+ 综合基差损益
+ 累计交易成本
+ 已确认调整项
```

正负号规则：

- 收益通常为正。
- 成本通常为负。
- AdjustmentEntry 按正式调整方向记录。

### 14.2 库存费累计收益

指持有永续合约期间账户实际发生并经确认的 FundingSettlement 累计金额。

支持按以下维度统计：

- StrategyInstance。
- 交易所。
- Account。
- Instrument。
- Funding 结算周期。
- 日期和 businessDate。

预计 Funding 不进入正式库存费累计收益。

### 14.3 综合基差损益

现货平台溢价损益与永续基差损益合并为一个一级归因。

综合基差损益表达：

- 现货腿与永续腿组合价格关系变化形成的交易损益。
- 不含 FundingSettlement。
- 不含明确交易手续费。
- 不与配平误差建立独立一级归因。

计算必须基于平台确认的现货和永续持仓、成交、估值价格、合约乘数和币种换算，并记录计算版本。

### 14.4 累计交易成本

至少包含：

- 现货交易手续费。
- 永续交易手续费。
- 已确认滑点成本，具备正式口径时。
- TransferFee，正式纳入时。
- 其他明确属于交易执行的成本。

手续费以外部实际记录或正式确认数据为优先，不能长期只使用费率估算。

### 14.5 已确认调整项

仅通过 AdjustmentEntry 进入，至少记录：

- 调整原因和证据。
- 金额、币种和方向。
- 关联对象。
- 创建人和审批。
- 生效时间。
- 是否替代或撤销另一调整。

页面不得直接编辑累计总损益或归因数字。

### 14.6 不使用配平误差

资费套利不设置“配平误差”一级归因。

数量偏差、执行时间差和残腿影响按以下方式处理：

- ExecutionBalanceStatus 和 ExposureStatus。
- 异常与风险事件。
- 已确认滑点或执行成本。
- 综合基差损益中的实际组合价格变化。
- AdjustmentEntry，只有在确有正式修正时。

不得为了表格完整而创建无业务含义的配平误差。

### 14.7 PnLResult

正式结果至少包含：

- pnlResultId。
- StrategyVersionId 和 StrategyInstanceId。
- 统计期间和 businessDate 口径。
- 原始币种和统一计价币种。
- 累计总损益。
- 三个正式一级归因和调整项。
- 数据截止时间。
- EconomicEvent 截止位置。
- 计算版本。
- 汇率来源和时间，适用时。
- DataQualityStatus。
- ReconciliationStatus。
- 估算、已核对或已结算属性。

## 15. 账户资金

### 15.1 合并总览

- 策略分配资金。
- 合并权益。
- 合并可用资金。
- 现货市值。
- 永续保证金占用。
- 总持仓名义价值。
- 资金使用率。
- 策略净值和回撤。
- 当前风险、数据质量和对账状态。

### 15.2 现货端

- Account 和交易所。
- 基础资产数量。
- 可用和冻结数量。
- 计价资产余额。
- 当前现货市值。
- 现货腿目标和实际持仓。
- 数据来源、时间和质量。

### 15.3 永续端

- Account 和交易所。
- 合约持仓和基础资产等价值。
- 保证金模式和杠杆。
- Margin Used 和 Available Margin。
- Margin Level，适用时。
- 强平价格或风险距离。
- 未结算或预计 Funding，仅作为观察。
- 最近实际 FundingSettlement。

### 15.4 多交易所资金

跨交易所组合额外展示：

- 每个平台的资金占比。
- 现货端与永续端资金失衡。
- 是否需要人工划转。
- 资金划转是否可用和当前状态。
- 交易所、托管和稳定币集中度。

## 16. 风险、异常和人工处理

### 16.1 主要风险

- Funding Rate 快速下降或反转。
- 综合基差不利变化。
- 现货或永续单腿成交。
- 两腿部分成交和长期未配平。
- 永续保证金不足和强平风险。
- 流动性、滑点和订单簿深度不足。
- 交易所、账户、托管和 API 风险。
- 稳定币、币种和结算风险。
- 标的和交易所集中度。
- 账户模式、合约规格或 Symbol Mapping 错误。
- Funding 数据、账户数据或结算记录缺失。
- Gateway 断线、回报延迟和结果未知。

### 16.2 风险指标候选

- 当前 Funding Rate 与策略阈值。
- 连续负费率或反转次数。
- 综合基差和历史分位。
- 配平偏差。
- 单腿暴露金额和持续时间。
- 永续保证金率和强平距离。
- 目标规模相对订单簿深度。
- 单交易所和单标的集中度。
- 数据新鲜度和对账差异数量。

具体阈值由 StrategyVersion 和 RiskRule 维护，本文不写死数值。

### 16.3 人工操作候选

在授权范围内可以：

- 撤销未成交订单。
- 终止未完成 ExecutionBatch。
- 补对冲或重新配平。
- 紧急减小单腿暴露。
- 平仓。
- 标记结果未知并启动查询。
- 接受差异或创建修正请求，进入正式审批流程。

人工处理必须记录原因、操作人、时间、对象版本、审批和最终结果。

## 17. 对账与数据质量

### 17.1 对账范围

至少覆盖：

- 平台 Order 与交易所 Order。
- 平台 Fill 与交易所 Trade。
- 平台现货持仓与交易所现货余额。
- 平台永续 Position 与交易所持仓。
- Balance／Margin 与交易所账户。
- FundingSettlement 与交易所账户账本。
- TradingFee 与实际费用。
- PnLResult 与底层 EconomicEvent 完整度。

### 17.2 差异类型

- 外部有订单，平台无记录。
- 平台有订单，外部未找到。
- 成交数量或价格不同。
- 重复成交。
- 现货余额或永续持仓不同。
- Funding 结算缺失、重复或金额不同。
- 手续费币种或金额不同。
- Instrument 或 Account 映射错误。
- 业务日期或时区错误。

### 17.3 处理规则

- 优先重新同步、补查询和确认外部事实。
- 不无痕覆盖原始订单、成交和结算记录。
- 差异接受需要原因、权限和审计。
- 正式修正使用 DataCorrectionRecord 或 AdjustmentEntry。
- 修正影响 PnL 时产生新计算版本。
- 数据不完整时 PnL 和报表必须显示质量和核对状态。

## 20. 实现能力依赖与外部组件候选

本节只描述实现能力候选，不改变策略业务定义，也不代表已批准采用具体仓库或版本。

### 20.1 平台必须自建的能力

- StrategyDefinition、StrategyVersion、StrategyInstance 和 StrategyAccountBinding。
- FundingRateSnapshot、FundingSettlement 的平台标准模型。
- TradeIntent、TradeCommand、ExecutionBatch 和 ExecutionPlan。
- 两腿数量换算、配平、暴露和残腿政策。
- 平台 Order、Fill、Position 和 ExternalReference。
- EconomicEvent、PnLResult 和资费套利归因。
- RiskDecision、ReconciliationResult 和人工处理。
- 数据质量、审计和 Read Model。

### 20.2 vn.py 候选能力

可以研究封装或参考：

- EventEngine：Runtime 内部事件驱动。
- MainEngine：Gateway 和运行 Engine 宿主。
- OmsEngine：当前活动订单、成交和持仓的运行缓存。
- BaseGateway 及状态映射模式：作为 Gateway Adapter 参考。
- SpreadTrading：多腿、主动腿／被动腿和成交驱动对冲思路。
- AlgoTrading：TWAP、Iceberg、Sniper 等低层执行工具。
- RiskManager：订单频率、数量等底层检查候选。
- RPC 或事件机制：仅作为 Runtime 内部或 PoC 候选。

不得直接交给 vn.py 的内容：

- StrategyId 和策略版本。
- Funding 业务语义和实际结算权威。
- 平台 TradeCommand 和 ExecutionBatch 权威。
- 平台订单永久记录。
- 策略损益和 EconomicEvent。
- 用户权限、审批、数据范围和业务风险判断。
- 对账差异和正式修正。

### 20.3 CCXT 候选能力

可以作为 Crypto 统一适配候选，重点评估：

- 市场和合约元数据。
- Ticker、Order Book、Trades 和 OHLCV。
- Funding Rate、Funding Rate History 和 Open Interest。
- 统一订单、余额、持仓和账户历史接口。
- REST 和 WebSocket 能力，具体按版本和交易所验证。

边界：

- CCXT 统一字段不能直接成为平台 Domain Model。
- 每家交易所的参数、账户模式和异常仍需专项 Adapter。
- 私有下单、订单恢复、实际 FundingSettlement 和账户账本需要逐交易所 PoC。
- 对于关键私有交易链，可以使用官方 API／SDK 或与 CCXT 组合，不能仅因为统一接口存在就假设语义完全一致。

### 20.4 交易所官方 API／SDK

优先用于验证和获得：

- 真实订单与成交状态。
- Client Order ID 能力。
- 余额、持仓和保证金。
- 实际 FundingSettlement 和账户账本。
- 交易规则、精度和限频。
- WebSocket 私有事件及断线补查询。

平台仍通过自有 Gateway Port 和 Adapter 接入，不能把官方 SDK 对象直接传到前端或业务领域。

### 20.5 其他项目参考

- NautilusTrader：命令、状态机、幂等、恢复和结果未知。
- rotki：EconomicEvent、原始事实、调整和重算思想。
- Freqtrade：StrategyInstance 启停、暂停和禁止新开仓的运营控制参考。

这些项目均不成为资费套利策略和平台数据的最终权威。

## 21. 明确不包含

- 负资金费率方向策略。
- 以借入现货为前提的自动反向 Funding 套利。
- 自动借币与还币系统。
- 未经审批的自动跨平台划转。
- 将预计 Funding 直接作为实际收益。
- 完整交易所信用评级。
- 由前端直接向两个交易所分别下单并自行拼接批次。
- 将外部组件对象作为平台业务权威。
- 配平误差一级损益项。
- 在本文中确定某个外部仓库的最终采用、Fork 或版本锁定。

## 22. 可测试验收标准

### 22.1 策略身份与范围

- StrategyId 固定为 `funding`。
- StrategyVersion、StrategyInstance 和 StrategyAccountBinding 可追溯。
- 仅正资金费率方向进入当前正式策略范围。
- Binance、OKX、Bybit 的能力按 GatewayCapability 分别表达。

### 22.2 行情与 Funding

- 上一期、即将结算、下一预测和实际 FundingSettlement 明确区分。
- Funding Interval、Funding Time、来源和质量可见。
- 现货、永续、Mark、Index、Bid／Ask 和 Last 不混用。
- Funding 或合约规格缺失时禁止正式执行。

### 22.3 执行

- 现货腿和永续腿由同一 ExecutionBatch 组织。
- 数量按照合约乘数和统一单位换算。
- Order 在外部提交前具有稳定平台身份。
- 部分成交、拒单、撤单、结果未知、未配平和单腿暴露均可表达。
- Runtime 或页面重启后可以通过 Query 和外部补查询恢复。

### 22.4 EconomicEvent 与 PnL

- 实际 FundingSettlement 进入库存费累计收益。
- 现货平台溢价和永续基差合并为综合基差损益。
- 交易手续费和已确认执行成本进入累计交易成本。
- 不设置配平误差一级归因。
- 累计总损益能够与归因和 AdjustmentEntry 核对。
- PnLResult 具有计算版本、截止时间、质量和对账状态。

### 22.5 账户、风险与对账

- 现货和永续账户用途明确。
- 多交易所资金和保证金状态可见。
- Funding 反转、基差恶化、单腿暴露和保证金风险可识别。
- Order、Fill、Position、Balance、Fee 和 FundingSettlement 可以对账。
- 差异和修正不无痕覆盖原始事实。

### 22.6 外部组件边界

- vn.py、CCXT 和官方 SDK 仅通过 Runtime、Gateway 或 Adapter 边界使用。
- 外部组件不拥有 Strategy、ExecutionBatch、平台 Order、EconomicEvent 和 PnL 权威。
- 具体采用结论经过 PoC、许可证、安全、恢复和对账评审后再形成 ADR。

## 23. 未决事项

以下事项在架构、交易执行或策略评审阶段确认：

1. 第一家打通完整私有交易链的 Crypto 交易所。
2. Binance、OKX、Bybit 各自使用官方 SDK、CCXT 还是组合适配。
3. 每家交易所现货和永续账户结构及 Position Mode。
4. 默认 ExecutionPlan 是 parallel 还是 active_passive。
5. 主动腿和被动腿的默认选择规则。
6. 最大裸露时间、目标配平容忍和紧急减险政策。
7. Funding 机会阈值、持续性指标和退出条件。
8. 综合基差的正式估值价格口径。
9. 滑点成本的正式计算和是否进入交易成本。
10. 跨交易所资金划转是否进入后续正式范围。
11. CCXT 私有 WebSocket、订单恢复和实际 FundingSettlement 的兼容性。
12. vn.py EventEngine、OmsEngine、SpreadTrading 和 AlgoTrading 的 PoC 范围。

未决事项不得由前端硬编码、Mock 或外部组件默认行为替代正式决策。
