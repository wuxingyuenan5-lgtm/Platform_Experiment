## 1. 文档定位

本文定义交易平台的用户任务、策略范围、行情分析、交易准备、命令提交、双腿执行、订单与成交反馈、配平与暴露、异常处理、实时恢复、权限、数据和验收标准。

交易平台是策略模块中的交易前分析与交易执行工作台，负责回答：

> 当前是否存在可执行机会、应如何构造交易、当前是否允许执行、实际执行到哪一步、是否出现单腿暴露或结果未知。

交易平台不承担：

- 全市场完整研究体系。
- 策略长期绩效和历史管理主视图。
- Account 主档、公司财务、IAM 和全局 Risk 规则维护。
- Gateway、终端和凭证的运维管理主入口。
- 金融AI分析任务和结果管理。

## 2. 产品目标

用户应能够：

1. 选择 StrategyDefinition、StrategyVersion 和 StrategyInstance。
2. 选择市场、交易场所、账户、标的和交易腿。
3. 观察实时或准实时行情、价差、费率、统计位置和市场结构。
4. 评估预计收益、手续费、滑点、资金成本、保证金和主要风险。
5. 构造开仓、平仓、调整或补对冲的双腿 TradeIntent。
6. 明确 DeploymentEnvironment、TradingMode、TradingPermissionState 和数据质量。
7. 完成前端提示校验和服务端正式执行前检查。
8. 提交具有幂等身份的 TradeCommand。
9. 跟踪 ExecutionBatch、ExecutionPlan、LegInstruction、Order 和 Fill。
10. 识别部分成交、拒单、撤单、结果未知、未配平和未对冲暴露。
11. 在权限范围内撤单、终止、补对冲、重新配平或进入人工处理。
12. 页面刷新或实时断线后重新查询并恢复当前执行状态。
13. 将实际执行事实交由策略管理、风险、对账、报表和审计继续处理。

## 3. 策略范围

| 策略 | StrategyId | 行情分析 | 交易执行 | 主要结构 |
|---|---|---:|---:|---|
| 资费套利 | `funding` | 有 | 有 | 现货腿 + 永续腿 |
| 跨所价差 | `crossSpread` | 有 | 有 | 两个交易场所或报价体系的双腿结构 |
| 海内外价差 | `domesticOverseas` | 有 | 有 | 国内腿 + 海外腿，包含汇率和单位换算 |

以下策略不进入交易平台：

- 抄底。
- 短线交易员 L。
- 短线交易员 W。

策略名称、ID、排序和页面能力由统一策略能力矩阵和策略注册表维护。

如果某策略的执行 Gateway、账户或产品能力尚未接入，页面必须明确显示：

- 当前仅支持行情分析。
- 当前仅支持 Simulation／Paper。
- 当前交易执行不可用。
- 当前缺失的具体能力。

不得使用前端模拟成交冒充真实平台执行。

## 4. 目标用户、权限与数据范围

### 4.1 目标用户

- 研究和交易人员。
- 策略负责人。
- 只读观察人员。
- 风险和运营观察人员。
- 异常处理和授权操作人员。

### 4.2 候选能力权限

读取和准备：

- `strategy.platform.read`。
- `strategy.execution.prepare`。

正式执行：

- `strategy.execution.submit`。
- `strategy.execution.cancel`。
- `strategy.execution.close`。
- `strategy.execution.rebalance`。

高风险和异常处理：

- `strategy.execution.override`。
- `strategy.execution.manualResolve`。
- `strategy.execution.liveSubmit`。
- `strategy.execution.emergencyHedge`，适用时。

### 4.3 数据范围

至少可以按以下维度限制：

- StrategyId 和 StrategyInstanceId。
- AccountId 和账户组。
- 市场、交易所、经纪商和 Gateway。
- InstrumentId 和产品类型。
- DeploymentEnvironment。
- TradingMode。
- 最大订单数量和名义价值范围。
- 敏感余额、保证金和审计详情。

### 4.4 权限规则

页面访问、行情读取、账户读取、参数准备、正式提交、Live 提交、撤单、补对冲、风险覆盖和人工处理分别授权。

无正式提交权限的用户可以按产品规则准备参数和查看执行上下文，但正式动作必须隐藏或禁用并显示原因。

审批通过不自动赋予执行能力；执行时仍需重新校验用户、账户、策略、风险、Gateway 和数据质量。

## 5. 运行上下文和交易许可

页面持续表达：

- DeploymentEnvironment：development、testing、staging、production。
- TradingMode：demo、simulation、paper、live。
- TradingPermissionState：disabled、read_only、enabled、blocked。
- StrategyDefinition、StrategyVersion、StrategyInstance。
- 当前账户、数据范围和账户模式。
- Gateway、Runtime、行情和账户同步状态。
- RiskDecision 和 GlobalTradingBlock。
- 最新对账与恢复状态，适用时。

规则：

- `production` 不等于 `live`。
- Demo、Simulation、Paper 和 Live 使用明确且不可混淆的文案。
- URL、前端常量和本地存储不能开启 Live。
- 运行上下文未知、账户状态未知、Gateway 未就绪或行情质量不足时禁止正式提交。
- `connected` 不等于 `ready`，`ready` 也不自动等于具有当前命令的交易许可。
- Live 操作必须由服务端综合用户能力、账户白名单、StrategyInstance、Runtime、Gateway、RiskDecision、行情质量、对账和审批判断。

## 6. 信息架构与路由

交易平台具有两个主要切换维度：

1. 策略。
2. 视角：行情分析、交易执行。

推荐路由语义：

```text
/strategy/platform?strategy=funding&view=analysis
/strategy/platform?strategy=crossSpread&view=execution
```

可进入 URL 的安全上下文可以包括：

- `strategy`。
- `view`。
- `marketId`／`venueId`。
- `instrumentId`。
- `primaryLegInstrumentId`／`hedgeLegInstrumentId`。
- `frequency`。
- `dateFrom`／`dateTo`。
- `currency`。
- 安全来源标记。

不得进入 URL：

- API Key、凭证和账户登录信息。
- Live 许可。
- approvalGrant 内容。
- 未提交数量、价格和完整 TradeIntent。
- 风险覆盖参数。
- 敏感余额和审计信息。

规则：

- StrategyId 必须有效且 `platform.enabled = true`。
- 非法参数回退至安全默认值并修正 URL。
- 切换策略默认进入目标策略的行情分析。
- 同一策略内从分析进入执行时只传递稳定、兼容和可重新查询的市场上下文。
- 未提交参数不跨策略继承。
- 离开存在未提交参数的执行页前提示确认。
- 页面刷新后重新 Query 权威状态，不依赖内存恢复订单和成交。

## 7. 行情分析

### 7.1 页面目标

用于回答：

- 当前是否存在值得进一步准备的机会。
- 当前价差、费率或换算结果处于什么历史位置。
- 收益是否可能覆盖手续费、滑点、资金和持仓成本。
- 应选择哪些场所、账户、标的、合约或市场组合。
- 当前报价和研究指标是否足够新鲜、完整和可比。

### 7.2 统一页面结构

1. 策略、市场和数据上下文。
2. 当前机会摘要。
3. 核心价格、价差或费率主图。
4. 历史分位、统计和分布。
5. 市场结构、期限结构或跨市场对比。
6. 成本、预计收益和风险补充。
7. 数据来源、时间、质量和计算说明。
8. 进入交易执行的参数准备入口。

具体区块由对应策略文档定义；不适用内容不显示空白卡片。

### 7.3 通用筛选

根据策略能力支持：

- 交易所、市场或交易场景。
- 标的和合约。
- 主腿和对冲腿。
- 时间精度。
- 统计区间和日期范围。
- 计价币种。
- 对比基准。
- 策略特有条件。

图表、指标、机会摘要和表格必须使用同一分析上下文。

### 7.4 行情与研究数据

至少表达：

- `instrumentId`。
- Bid、Ask、Last、Mark 或适用价格。
- sourceTime。
- receivedAt。
- QuoteStatus。
- 数据来源和 Gateway。
- 单位、币种、合约乘数和精度。
- 研究指标的数据截止时间、计算时间和计算版本。
- DataQualityStatus。
- 预计或实际属性。

规则：

- 延迟、失效、缺失、冲突和计算失败明确展示。
- 看板 Research Data 可以作为背景，但正式执行报价必须来自交易执行认可的数据源。
- 行情分析不直接产生权威订单。
- 从分析页进入执行页时，后端必须重新校验最新报价和账户状态。

## 8. 交易准备

### 8.1 TradeIntent

TradeIntent 表达用户准备执行的业务意图，至少包括：

- StrategyInstanceId。
- 开仓、平仓、调整或补对冲动作。
- 交易场景和执行模式。
- 每条腿的账户、市场、标的和角色。
- 买卖方向。
- 目标数量、名义价值或比例。
- 订单类型和价格参数。
- 最大滑点或价格保护。
- 最大裸露时间和残腿政策，适用时。
- 预计成本、收益和资金影响的计算引用。

未提交 TradeIntent 属于页面草稿，不是后端业务事实。

### 8.2 ExecutionPlan

ExecutionPlan 在产品上表达本次批次的执行策略，可以作为 ExecutionBatch 下的版本化值对象。

至少可以包含：

- `executionMode`。
- 主动腿和被动腿，适用时。
- 并行或顺序规则。
- 每条腿的订单类型。
- 最大滑点和价格保护。
- 超时政策。
- 最大裸露时间。
- 部分成交处理。
- 残腿处理。
- 重试、追价或转市价规则，适用时。
- 是否允许人工确认或覆盖。
- 计划版本。

执行过程中修改计划必须保留版本或修订记录，不得无痕修改历史执行条件。

### 8.3 执行模式候选

根据策略和 Gateway 能力可以支持：

- `parallel`：两腿近似同时提交。
- `active_passive`：主动腿成交后按实际成交量驱动被动腿。
- `sequential`：一条腿达到指定状态后提交另一条腿。
- `manual_confirmed`：关键步骤需要人工确认。
- `record_external`：仅记录外部执行，不由平台发送订单。
- `simulation`：使用模拟执行服务。

前端不得假设所有策略和 Gateway 均支持相同执行模式。

### 8.4 执行影响预估

提交前至少展示：

- 两腿目标数量和名义价值。
- 目标配平关系和容忍范围。
- 预计手续费和滑点。
- 预计 Funding、Swap、融资或持仓成本，适用时。
- 预计毛收益和净收益。
- 执行后资金占用和保证金变化。
- 主要风险和敏感假设。
- 计算时间、币种、版本和是否估算。

预计结果不得与实际 PnLResult、实际费用和实际成交混用。

## 9. 执行前校验与提交确认

### 9.1 前端提示校验

至少检查：

- 必填字段。
- 格式和基本数值范围。
- 数量大于零。
- 两腿方向和结构基本一致。
- 页面上下文完整。
- 当前报价是否明显过期。
- 未保存参数和重复点击。

前端校验只改善体验，不能代替服务端最终判断。

### 9.2 服务端正式校验

至少包括：

- 身份、能力和数据范围。
- DeploymentEnvironment、TradingMode 和 TradingPermissionState。
- StrategyDefinition、StrategyVersion 和 StrategyInstance。
- StrategyAccountBinding。
- Account、BalanceSnapshot 和 MarginSnapshot。
- Instrument、ContractSpecification 和 GatewayCapability。
- 报价来源、新鲜度和必要 DataQualityStatus。
- 价格、数量、最小名义价值、精度和订单类型。
- RiskDecision、RiskLimit 和 GlobalTradingBlock。
- 最大单笔数量、策略名义价值、单腿暴露和残腿时间。
- ApprovalGrant，适用时。
- `idempotencyKey`、请求版本和对象版本。

### 9.3 提交确认

正式提交前显示：

- 策略定义、版本和实例。
- 环境、交易模式和交易许可。
- 交易动作和执行模式。
- 两腿账户、市场、标的、角色和方向。
- 数量、价格和订单类型。
- 目标配平和残腿政策。
- 预计收益、成本、资金和风险。
- 数据质量、限制和审批。
- Live 或危险操作的显著提示。

### 9.4 TradeCommand 请求

正式命令至少具有：

- `requestId`。
- `correlationId`。
- `idempotencyKey`。
- 客户端时间。
- 目标 StrategyInstanceId。
- TradeIntent 和 ExecutionPlan 版本。
- `approvalGrantId`，适用时。

操作人、权限、数据范围和运行上下文由受信任会话确定，不接受前端伪造。

## 10. 命令、批次、订单和成交

### 10.1 TradeCommand

TradeCommand 表达命令是否：

- 已收到。
- 正在校验。
- 被拒绝。
- 已受理。
- 正在派发。
- 结果未知。

`accepted` 仅表示平台受理命令，不表示外部订单已经提交、接受、成交或完成。

### 10.2 ExecutionBatch

ExecutionBatch 表达一次多腿业务执行的实际进度，至少关联：

- TradeCommand。
- ExecutionPlan 版本。
- LegInstruction。
- Order。
- Fill。
- ExecutionBalanceStatus。
- ExposureStatus。
- 人工处理和对账。

### 10.3 LegInstruction

每条腿至少表达：

- `legInstructionId`。
- 角色和顺序。
- AccountId。
- Venue／Gateway。
- InstrumentId。
- 方向。
- 目标数量或名义价值。
- 订单政策。
- 依赖关系。

### 10.4 Order 身份

每个外部提交意图必须先具有稳定平台订单身份：

- `orderId` 或 `platformOrderId`。
- LegInstructionId。
- 稳定 clientOrderId 或等价外部映射，Gateway 支持时。
- `submission_requested` 或等价初始状态。

这样即使外部系统已接受订单但回报延迟或 Runtime 中断，平台仍能通过稳定身份、外部 ID、Magic Number、Comment 或历史查询找回订单。

### 10.5 Order 与 Fill 关系

- 每条腿可以产生一张或多张 Order。
- 一张 Order 可以产生多笔 Fill。
- 撤单不删除已发生 Fill。
- 外部状态映射为平台状态并保留原始值和原始错误码。
- Fill 必须具有稳定去重依据。
- 重复事件不能重复增加成交数量、持仓和损益。

## 11. 配平与暴露

页面分别展示：

- ExecutionBalanceStatus。
- ExposureStatus。
- 目标关系。
- 实际委托关系。
- 实际成交关系。
- 容忍范围。
- 暴露数量、名义价值、方向和持续时间。
- 当前允许的补救动作。

规则：

- 配平状态和风险状态不是同一状态。
- 未配平不自动等于实际损失。
- 单腿暴露需要明确开始时间和当前持续时间。
- 最大裸露时间到达后应产生风险或人工处理状态，具体政策由策略和风险规则决定。
- 两腿均未成交、单腿部分成交、双腿不同比例成交需要分别表达。

## 13. 状态和生命周期

交易平台涉及：

- QuoteStatus。
- DataQualityStatus。
- TradingPermissionState。
- TradeCommandStatus。
- ExecutionBatchStatus。
- OrderStatus。
- ExecutionBalanceStatus。
- ExposureStatus。
- RiskStatus。
- GatewayStatus。
- ReconciliationStatus。

完整状态码和生命周期以 `docs/architecture/domain/status-enums-and-lifecycles.md` 为唯一来源，本文件不维护冲突清单。

页面必须将以下维度分开：

- 命令是否被受理。
- 命令是否已派发。
- 外部订单是否被接受。
- 订单是否成交。
- 批次是否完成。
- 两腿是否配平。
- 是否存在暴露。
- 是否通过风险判断。
- 是否完成对账。

## 14. 异常和人工处理

至少识别：

- 报价过期、缺失或冲突。
- Gateway、Runtime 或账户同步不可用。
- 命令拒绝。
- 命令派发结果未知。
- 外部订单被拒绝或状态未知。
- 单腿成交、另一腿失败。
- 两腿部分成交。
- 配平超出容忍范围。
- 汇率或多腿暴露。
- 保证金或可用资金不足。
- 风险状态在执行中变化。
- 用户主动中止。
- 外部手工订单影响当前持仓。
- 重启后发现未知订单或成交。

异常区域至少展示：

- 发生时间、来源和原因码。
- 关联 TradeCommand、ExecutionBatch、LegInstruction、Order 和 Fill。
- 当前配平、暴露、账户和风险。
- 已执行动作、待确认事实和允许动作。
- 操作人、备注、审批和审计信息。
- 是否需要对账或人工确认。

### 14.1 结果未知

`result_unknown` 或等价状态表示平台无法确认命令或外部执行结果。

规则：

- 不得直接当作失败后使用新幂等键重下。
- 优先使用原 commandId、clientOrderId、外部 ID 和历史查询确认。
- 确认前限制可能导致重复风险的动作。
- 人工确认必须记录依据、时间和操作人。

### 14.2 人工动作

人工动作根据权限和状态可以包括：

- 撤销未完成订单。
- 终止后续提交。
- 补对冲。
- 重新配平。
- 接受残余持仓并转入人工管理。
- 标记外部手工订单。
- 触发重新同步和对账。
- 确认未知结果。

人工动作不得直接改写外部事实或删除已发生 Fill。

## 15. 实时事件、断线和恢复

实时推送可以包括：

- QuoteUpdated。
- TradeCommand 状态。
- ExecutionBatch 状态。
- Order 和 Fill。
- 配平和暴露。
- 账户和保证金摘要。
- RiskDecision。
- Gateway 和 Runtime 状态。

断线恢复：

1. 标记实时数据可能过期。
2. 重新连接和认证。
3. 恢复订阅。
4. Query 当前 TradeCommand、ExecutionBatch、Order、Fill、Account、Position、Exposure、Risk 和 Reconciliation。
5. 通过稳定 ID 合并实时事件与权威快照。
6. 用权威状态覆盖本地临时状态。
7. 重新判断操作能力。

恢复完成前：

- 禁止重复提交同一命令。
- 禁止仅根据本地旧状态执行危险动作。
- 页面可以保持只读并显示恢复进度。

前端关闭、刷新或断线不得终止已受理的后台执行。

## 19. 跨模块关系

- 对冲基金看板提供研究背景和 Research Data。

- 策略管理查询后端实际结果，不接收交易页面复制对象。
- 风险管理维护规则、事件、限制、阻断和审批入口。
- Account 维护账户主档；Strategy 维护 StrategyAccountBinding。
- Reconciliation 核对平台和外部交易事实。
- Audit 记录命令、审批、覆盖和人工处理。
- 金融AI分析可以读取授权材料，不修改执行事实。

## 20. 非功能要求

- 桌面交易工作台优先。
- 前端断线不终止后台执行。
- Command 具有幂等和完整追踪上下文。
- 高频行情渲染不能阻塞订单、账户和风险事件。
- 页面和服务重启后可以恢复未完成批次。
- 重复、延迟和乱序 Event 不得重复增加持仓和成交。
- 关键动作和人工处理可审计。
- Demo、Simulation、Paper 和 Live 清晰隔离。
- 单个 Gateway 故障不应导致其他无关 Gateway 页面整体不可用。
- 对结果未知、部分成交、残腿和恢复过程必须有自动化测试和故障演练。

## 22. 验收标准

### 范围与路由

- 只展示三类平台执行策略。
- 非平台执行策略无空交易页面。
- 策略和视角可以通过 URL 恢复。
- 不支持执行的策略或环境明确显示能力缺失。

### 行情分析

- 市场、标的、时间、币种、单位和数据版本一致。
- 指标具有来源、口径、时间和质量。
- 分析页不直接产生权威订单。
- 进入执行页后重新校验最新执行上下文。

### 交易准备

- TradeIntent、ExecutionPlan 和预计影响表达清晰。
- 预计与实际严格分开。
- 前端草稿不成为后端业务事实。
- 提交确认完整展示账户、两腿、数量、成本、风险和模式。

### 命令与执行

- TradeCommand 与 ExecutionBatch 分开。
- `accepted` 不被解释为已下单或成交。
- 双腿执行由后端批次组织。
- 每个外部提交具有稳定平台 Order 身份。
- Order、Fill、配平、暴露和风险使用独立维度。

### 权限与安全

- 准备、提交、Live、撤单、补对冲、覆盖和人工处理分别授权。
- 幂等、审批、服务端校验和对象版本有效。
- URL 和前端状态不能开启 Live 或绕过风控。

### 异常与恢复

- 部分成交、拒单、结果未知、未配平、单腿暴露和人工处理可表达。
- 结果未知不会直接触发重复下单。
- 前端断线、刷新和服务恢复后通过 Query 恢复权威状态。
- 重复事件不会重复增加 Order、Fill、Position 和 PnL。

### UI

- 正式交易、普通操作和危险操作层级明确。
- 两腿参数和结果保持视觉关联。
- 禁用原因、数据质量、交易模式和恢复状态清晰可见。

## 23. 未决事项

以下事项由策略文档、专项架构或后续规划确认：

- 各策略默认执行模式和主动腿／被动腿规则。
- ExecutionPlan 的正式领域生命周期。
- 各 Gateway 支持的订单能力和降级政策。
- 最大裸露时间、追价和紧急对冲默认政策。
- Live 提交、人工覆盖和紧急操作的审批等级。
- 外部手工订单进入当前执行批次的处理规则。
