# 风险管理：需求文档

状态：`active`  
产品基线：Platform V5  
架构版本：Platform V6  
适用分支：`refactor/frontend-architecture-v6`  
文档层级：一级产品模块需求

> 文件名中的“风控管理”暂时保留历史路径兼容；正式一级模块名称统一为“风险管理”。

模块定位依据：`docs/modules/风控管理-模块定位.md`

## 1. 文档定位

本文档定义风险管理一级模块的产品范围、子板块、权限、审批、数据权威、交互、非功能要求和验收标准。

风险管理是平台内部风险和管理能力的集中产品入口，但不是单一后端 Risk 模块。Account、IAM、Audit、Reporting、Notification、Configuration、Observability 等技术领域保持独立边界。

## 2. 产品目标

用户应能够：

1. 查看全平台风险状态、事件和影响对象。
2. 管理已确认的风险规则、额度和阻断。
3. 查看账户、资产、资金和保证金状态。
4. 查看数据源、Gateway 和系统服务健康。
5. 查询正式报表、审计记录和消息通知。
6. 管理用户、角色、能力、数据范围和个人配置。
7. 发起、审批和执行适用的高风险操作。
8. 对风险事件、数据差异和人工处理进行追溯与复盘。

## 3. 信息架构

固定子板块：

- 风控详情。
- 账户与资产。
- 财务与资金。
- 数据与服务监控。
- 报表。
- 审计。
- 用户与权限。
- 个人账号。
- 系统设置。
- 消息通知。

当前子板块属于同一一级产品模块，不因后端服务独立而新增一级导航。

## 4. 权限模型

至少区分：

- `risk.read`。
- `risk.rule.read`。
- `risk.rule.manage`。
- `risk.event.resolve`。
- `account.read`。
- `account.manage`。
- `report.generate`。
- `audit.read`。
- `user.manage`。
- `configuration.manage`。
- `approval.create`。
- `approval.review`。
- `data.correction.execute`。

页面访问、操作能力、数据范围、审批政策和目标对象状态分别判断。角色只是能力集合，不在页面中使用大量角色名称分支替代能力判断。

## 5. 风控详情需求

### 5.1 页面目标

用于回答：

- 当前整体风险处于什么状态。
- 哪些账户、策略、执行批次、持仓、数据源或服务受到影响。
- 触发了哪些规则和限制。
- 是否需要人工处理、审批或交易阻断。
- 风险事件是否已经解决。

### 5.2 页面结构

1. 风险总览。
2. 当前限制和 GlobalTradingBlock。
3. 风险事件列表。
4. 影响对象和指标明细。
5. 处置、审批和人工处理记录。
6. 历史趋势和复盘。

### 5.3 核心对象

- RiskRule。
- RiskLimit。
- RiskSnapshot。
- RiskDecision。
- RiskEvent。
- RiskResolution。
- GlobalTradingBlock。

状态码以 `docs/architecture/domain/status-enums-and-lifecycles.md` 为唯一来源。

### 5.4 处置规则

- 风险处置必须检查权限和对象版本。
- 需要审批的操作提交 ApprovalGrant。
- 阻断默认禁止新增风险，不无条件自动平仓。
- 人工覆盖必须有理由、有效范围、有效期和审计记录。
- 页面不能直接修改 Order、Position、Account 和 PnL 权威事实。

## 6. 账户与资产需求

### 6.1 页面目标

- 管理和查询业务账户主档。
- 查看账户权益、余额、可用资金和保证金。
- 查看账户状态、平台和币种结构。
- 查看策略绑定摘要和授权管理入口。
- 识别账户不可用、数据延迟和对账差异。

### 6.2 核心对象

- Account。
- BalanceSnapshot。
- MarginSnapshot。
- Position 摘要。
- AccountStatus。
- ReconciliationResult。

### 6.3 归属规则

- Account 服务维护账户主档和账户事实。
- Strategy 服务维护 StrategyAccountBinding。
- 页面可以组合展示两类信息，但不复制绑定关系。
- 账户凭证不进入普通页面和日志。
- 账户修改和绑定修改使用不同命令、权限和审批政策。

## 7. 财务与资金需求

用于公司经营资金、收支、费用和财务口径管理。

必须与以下内容区分：

- 策略 PnLResult。
- Strategy Economic Ledger。
- 账户实时余额。
- 策略资金分配。

正式财务会计科目、借贷记账和法定报表不由当前策略经济账本替代。未经确认的财务范围不得在页面中用策略损益数据拼接实现。

## 8. 数据与服务监控需求

### 8.1 监控范围

- Execution Market Data 数据源。
- Research Data 数据源。
- Content and Calendar Data 数据源。
- 数据同步任务。
- Gateway 连接。
- Platform API 和后端模块健康。
- 数据库、队列和异步任务，实施后。
- 实时连接和事件延迟。

### 8.2 状态要求

展示：

- 进程是否存活。
- 是否可接收请求。
- 关键依赖是否可用。
- 数据是否新鲜。
- 是否允许交易。
- 最近成功时间和最近错误。
- 当前告警级别。

监控状态不能成为订单、账户、持仓或风险业务事实的权威来源。

## 9. 报表需求

报表子板块负责：

- 报表定义。
- 报表生成任务。
- 报表版本。
- 数据截止时间。
- 筛选条件和计价口径。
- 展示、下载和访问记录。

报表读取权威领域数据或稳定 Read Model，不在报表模块重新形成第二套交易和损益事实。正式版本生成后保留版本和审计。

## 10. 审计需求

必须支持查询：

- 登录和安全事件。
- 权限和用户变更。
- 交易命令和人工处理。
- 风险规则、限制和覆盖。
- 审批发起、决定和授权使用。
- 账户、策略绑定和配置变更。
- 数据导入、修正和对账确认。
- 报表生成和导出。

审计记录至少包含操作人、会话、能力、目标对象、变更摘要、时间、requestId、traceId 和结果。

## 11. 用户与权限需求

### 11.1 用户管理

- 用户基本信息。
- 启用、禁用和会话失效。
- 角色集合。
- 具体能力。
- 数据范围。
- 高风险操作二次认证，适用时。

### 11.2 权限原则

- 默认拒绝。
- 最小权限。
- 页面权限与操作权限分开。
- 运维人员不默认拥有交易和资金权限。
- Checker 权限与 Maker 权限可以分开。
- 后端对每个命令最终校验。

## 12. 个人账号需求

负责：

- 当前用户资料。
- 安全和会话信息。
- 界面偏好。
- 通知偏好。
- 时区、语言和默认展示设置。

个人账号与业务 Account 明确分开。

## 13. 系统设置需求

系统设置提供受控配置入口，但不形成万能配置模型。

配置至少区分：

- 普通应用配置。
- DeploymentEnvironment。
- TradingMode。
- 风险与交易业务配置。
- Gateway 和账户连接配置。
- 密钥与凭证。
- 动态功能开关。

规则：

- 每项配置有主责领域、版本和来源。
- 实盘配置变更需要权限、审批和审计，适用时。
- 密钥与普通配置分开。
- 重要配置支持回滚。
- 页面不得通过本地常量决定实盘能力。

## 14. 消息通知需求

支持：

- 消息类型和优先级。
- 来源模块和业务对象。
- 创建时间和阅读状态。
- 关联跳转。
- 用户通知偏好。
- 发送和重试状态，实施后。

通知不重新判断风险严重程度，也不拥有原始风险事件、审计记录和系统健康对象。

## 15. 审批与双人复核

高风险操作可适用 Maker／Checker：

- 修改 Live 风险规则和额度。
- 覆盖风险限制。
- 接受重大对账差异。
- 修正正式损益或账本数据。
- 修改 Live 策略账户绑定。
- 启用 Live Gateway 或账户。
- 提高交易额度。

审批模型以 `docs/architecture/domain/approval-and-dual-control.md` 为准。审批通过不等于目标操作执行成功。

## 16. 数据与状态要求

所有页面应表达：

- 数据来源。
- 业务时间或数据截止时间。
- 最近更新时间。
- DataQualityStatus。
- 是否估算或待核对。
- 权限和数据范围。

不得通过中文文案或颜色解析业务状态。状态枚举统一引用公共状态规范。

## 17. 跨模块关系

- 策略模块读取风险判断、账户摘要和交易许可。
- 对冲基金看板提供研究背景，不维护风险规则。
- 新闻日历与理财提供事件背景，不形成风险结论。
- 金融AI分析可以解释授权风险材料，不执行处置。
- 首页只展示少量风险和系统状态摘要。

## 18. 非功能要求

- 关键管理页面面向桌面端。
- 高风险操作具有确认、审批、幂等和审计。
- 单个监控或数据源失败不导致整个模块白屏。
- 权限变化后敏感状态和订阅及时清理。
- 报表、审计和大列表支持稳定分页和导出控制。
- 关键告警、配置、审计和风险数据具有保留与恢复要求。

## 19. 验收标准

- 十个子板块均有清晰产品目标和数据权威。
- 风险管理不会被实现为吞并所有领域的单体 Risk 模块。
- Account 与 StrategyAccountBinding 所有权正确。
- 权限、风险、审批、审计和命令执行分别表达。
- 系统设置和监控不形成第二套业务事实。
- 高风险变更可执行 Maker／Checker 和审计。
- 页面具有来源、时间、质量、权限和异常状态。
- 正式产品名称统一为“风险管理”。
