# Variable-Global 全局非功能产品要求

状态：`draft`  
产品基线：Platform V5  
架构讨论版本：Platform V6+  
适用分支：`refactor/frontend-architecture-v6`  
文档层级：跨模块非功能产品需求  
更新日期：2026-07-17

## 1. 文档定位

本文定义整个 Variable-Global 平台的性能、可用性、可靠性、安全、数据质量、审计、可维护性、兼容性和用户体验要求。

具体数值在不同模块、环境和数据源中可以不同，但不得没有明确目标、测量方法和降级规则。

本文不直接确定最终生产容量、SLA 合同或云资源规格。

---

## 2. 需求等级

非功能要求分为：

- Mandatory：上线前必须满足。
- Target：目标要求，未达到时必须有差异说明和改进计划。
- Deferred：明确延后，不得伪装为已支持。

不同环境可以有不同等级，但 Live 不得低于正式确认的 Mandatory 门槛。

---

## 3. 用户体验与界面

### 3.1 设备与布局

- 桌面工作台优先。
- 主要支持常见桌面分辨率和浏览器缩放。
- 关键表格和图表支持大屏使用。
- 移动端当前可以只保证基本查看，若不支持正式操作需明确说明。

### 3.2 一致性

- 相同对象使用相同名称、状态、颜色语义和详情结构。
- 相同筛选条件在兼容页面中保持一致。
- 不同模块的相同金额、币种、时间和百分比遵循统一格式。
- 危险操作使用一致确认机制。

### 3.3 可理解性

- 业务术语使用正式词汇表。
- 估算、实际、结算、修订和人工调整明确区分。
- 延迟、缺失、冲突和结果未知不能使用普通成功样式。
- 不适用字段不显示无意义零值。

### 3.4 可恢复性

- 页面刷新后恢复主上下文。
- 深链接可以进入目标视角，前提是用户有权限。
- 未完成交易、报表、导入和 AI 任务由后端继续执行。
- 前端崩溃或关闭不改变正式业务状态。

---

## 4. 性能

### 4.1 页面交互

Target：

- 本地 UI 操作应在用户可感知延迟前反馈。
- 主要路由切换立即显示页面结构或加载状态。
- 大型表格、图表和筛选操作避免阻塞主线程。

### 4.2 API 查询

候选目标，需要按模块最终确认：

- 普通摘要和详情 Query：p95 不高于 1 秒。
- 普通分页列表：p95 不高于 2 秒。
- 复杂聚合、策略统计和多源研究查询：p95 不高于 5 秒；超过时采用异步任务、缓存或渐进加载。
- 正式报表和大型导出不通过长同步请求等待完成。

外部数据源慢不等于平台可以无提示等待；必须显示来源状态和超时。

### 4.3 Command 受理

- 用户提交 Command 后，平台应尽快返回“已受理、已拒绝或结果未知”。
- Command 受理响应不等待外部交易完整执行。
- 交易所或经纪商延迟单独反映在 ExecutionBatch 和 Order 状态中。

### 4.4 实时更新

- 交易、订单、成交、风险和 Runtime 事件需要按业务重要性设置目标延迟。
- 页面必须显示 sourceTime 和 receivedAt，适用时。
- 实时通道断线后通过 Query 恢复。
- 研究数据和内容数据不强制使用交易级实时目标。

---

## 5. 可用性和降级

### 5.1 模块独立降级

一个模块或数据源故障不应无条件拖垮全部平台。

示例：

- 新闻源异常不影响交易订单查询。
- AI 服务异常不影响研究和交易事实。
- 首页摘要异常不影响目标模块访问。
- 报表生成异常不删除正式交易数据。

### 5.2 关键链路优先级

优先保护：

1. 已受理交易和外部订单状态。
2. 风险阻断、撤单、减仓和人工处理。
3. 账户、持仓、成交和对账。
4. 策略管理和正式 PnL。
5. 研究、内容、首页和 AI 增值能力。

### 5.3 降级模式

至少支持表达：

- read_only。
- delayed_data。
- partial_data。
- trading_blocked。
- reduce_only，后续按业务确认。
- manual_intervention。
- service_unavailable。

降级不得静默发生。

## 6. 可靠性

### 6.1 幂等

以下操作必须具备幂等策略：

- 交易命令。
- 撤单和补对冲命令。
- 数据导入。
- 数据修正。
- 报表生成。
- 审批决策。
- Runtime Command 和 Event 消费。

### 6.2 重复、延迟和乱序

消费者必须能够处理：

- 重复事件。
- 延迟事件。
- 乱序事件。
- 恢复后的补发事件。
- 外部系统重复回报。

重复事件不得重复增加持仓、损益和审计结果。

### 6.3 结果未知

网络超时或服务中断不能自动解释为失败。

必须区分：

- 明确失败。
- 明确成功。
- 已受理但未完成。
- 结果未知。
- 等待外部确认。

### 6.4 恢复

关键服务恢复后至少执行：

- 同步。
- 对账。
- 未完成任务识别。
- 未知对象处理。
- 风险确认。
- 进入可用状态。

连接成功不等于业务已恢复。

---

## 7. 数据质量

### 7.1 必要元数据

关键数据至少具有：

- 来源。
- sourceTime。
- receivedAt。
- 截止时间，适用时。
- 单位。
- 币种。
- 精度。
- 数据质量状态。
- 版本或修订信息，适用时。

### 7.2 缺失处理

- 缺失数据不得默认当作零。
- 缺失汇率、价格、Funding、费用或账户事实不得静默进入正式 PnL。
- 部分可用时明确汇总是否仍可核对。

### 7.3 修订和调整

- 外部数据修订保留原值、修订值和来源。
- 人工修正形成 AdjustmentEntry 或授权修正记录。
- 不覆盖原始事实以伪造一致。

### 7.4 数据质量对业务的影响

每类关键数据需要定义：

- 允许只读展示的最低质量。
- 允许策略分析的最低质量。
- 允许正式交易的最低质量。
- 允许正式 PnL 和报表的最低质量。
- 允许金融AI分析使用的最低质量。

---

## 8. 时间、时区和交易日

- 数据库存储时间使用统一标准，推荐 UTC 时间戳。
- 前端按用户或业务时区展示，并明确时区。
- 交易日、自然日和结算日分开。
- CTP 夜盘、Crypto 24/7 和 MT5 经纪商时间需要专项映射。
- 报表和策略统计必须说明区间边界。
- 夏令时变化不得通过固定小时硬编码处理。

---

## 9. 金额、币种、数量和精度

- 金额、价格、数量和比例不得使用不可控浮点误差作为正式计算基础。
- 每个 Instrument 使用 ContractSpecification。
- 原始币种值和统一折算值分开保存或展示。
- 汇率来源、方向、时间和精度明确。
- 前端格式化不改变后端正式数值。
- 手续费、成本和损益使用统一正负号规则。

---

## 10. 安全

### 10.1 身份和会话

- 所有受保护 Query 和 Command 需要服务端身份校验。
- 会话失效后清理敏感前端状态。
- 高风险操作可以要求二次认证，后续确认。

### 10.2 权限

- Role、Capability、Data Scope、Environment 和 TradingMode 分开。
- 前端隐藏不替代后端校验。
- 未知权限默认拒绝高风险写入。

### 10.3 凭证和密钥

- 浏览器不持有交易凭证。
- 日志不输出完整密钥和密码。
- Demo、Paper 和 Live 凭证隔离。
- 密钥变更、访问和失效具有审计。

### 10.4 敏感数据

- 账户、持仓、损益和内部策略按敏感级别展示。
- 导出和报表遵循数据范围。
- AI 输出不得扩大来源权限。

---

## 11. 审计和可追溯性

以下至少需要审计：

- 登录和高风险认证事件。
- 权限和数据范围变更。
- TradeCommand 和人工交易处置。
- 风险规则、额度和覆盖。
- 审批。
- 账户主档和 StrategyAccountBinding 变更。
- 数据导入、修正和 AdjustmentEntry。
- 系统配置和凭证变更。
- 正式报表发布。
- AI 分析任务的来源、模型和版本，按数据安全要求。

审计记录至少具有：

- 操作者。
- 动作。
- 目标对象。
- 时间。
- 原因。
- 前后值，适用时。
- requestId、commandId 和 correlationId。
- 结果。

审计不得由普通业务用户任意修改和删除。

---

## 12. 可观测性

### 12.1 日志

- 使用结构化日志。
- 关键链路可按 requestId、correlationId、executionBatchId、orderId 等检索。
- 日志级别和敏感字段处理统一。

### 12.2 指标

至少覆盖：

- API 请求量、延迟和错误率。
- 数据源延迟和缺失。
- Runtime／Gateway 心跳。
- 活动订单和未知订单。
- 消息积压和失败。
- 对账差异。
- 报表和 AI 任务状态。

### 12.3 告警

告警具有：

- 严重程度。
- 来源。
- 影响范围。
- 目标对象。
- 首次和最近发生时间。
- 处理状态。
- 去重和抑制规则。

---

## 13. 备份、恢复和数据保存

需要按数据类型定义：

- 备份频率。
- 保存周期。
- 恢复验证。
- RPO。
- RTO。
- 归档。
- 删除和脱敏。

候选优先级：

- 交易、成交、账户、账本、审计和配置具有最高保护等级。
- Research Data 和 Content Data 可以根据外部可重建程度采用不同策略。
- Read Model 可重建，不作为唯一备份来源。
- Runtime 内存状态不得成为唯一恢复来源。

正式数值在部署和运维架构中进一步确认。

---

## 14. 兼容性和版本

- API、Command、Event 和导入格式具有版本。
- 前端和后端的破坏性变化可被契约测试识别。
- 数据库迁移可重复执行并具有回退或修复路径。
- 外部 SDK 和 Gateway 升级需要兼容性验证。
- 历史报表和 PnL 保留原计算版本。

---

## 15. 可维护性

- 一个业务对象只有一个主责领域。
- API 层不写核心业务规则。
- 外部 DTO 经过 Adapter。
- 页面不维护权威交易事实。
- Read Model 不接受业务写入。
- 文档、代码、测试和契约使用稳定术语。
- 新增复杂基础设施必须说明当前实际收益。
- 未达到拆分条件前不因目录数量拆微服务。

---

## 16. 测试要求

至少包括：

### 单元测试

- 核心业务规则。
- 状态转换。
- 金额、单位和精度。
- 权限和风险判断。

### 契约测试

- API DTO。
- Command／Event。
- Gateway Adapter。
- 导入格式。

### 集成测试

- 数据库事务和迁移。
- 外部接口模拟。
- 消息重复、重试和恢复。
- 权限和审计。

### 端到端测试

- 关键用户旅程。
- 页面刷新和断线恢复。
- 异常、降级和无权限。
- 报表、导入和 AI 任务，适用时。

### 故障演练

- 外部数据源中断。
- Runtime／Gateway 重启。
- 数据库或消息通道短时不可用。
- 结果未知和对账差异。

---

## 17. 金融AI分析专项要求

- AI 任务失败不影响原始业务数据。
- 模型输出保留来源、时间、模型和配置版本。
- 不输出伪造事实、价格、政策和引用。
- 敏感凭证不进入模型。
- AI 结果不能直接执行交易、风险和数据修正。
- 成本、配额、超时和取消具有明确状态。
- 暂不开发时，相关页面必须明确功能状态，不伪装为已接入真实模型。

---

## 18. 验收标准

- 六个一级模块引用同一套非功能要求。
- 性能、可用性、可靠性和数据质量具有可测量目标或待确认项。
- Command 受理、外部执行和结果未知分开。
- 缺失数据不被静默当作零。
- 时间、币种、单位和精度具有统一规则。
- 权限、敏感数据、凭证和审计边界明确。
- 关键链路具有日志、指标和告警。
- 备份、恢复和保存要求按数据类型定义。
- API、事件、数据和计算结果具有版本策略。
- AI 增值能力故障不会影响核心业务事实。
