# 策略：一级模块需求文档

状态：`active`  
产品基线：Platform V5  
架构版本：Platform V6  
适用分支：`refactor/frontend-architecture-v6`  
文档层级：一级产品模块需求

模块定位依据：`docs/modules/策略-模块定位.md`

## 1. 文档定位

本文档定义策略一级模块的共同产品规则、二级模块协作、策略身份、权限、数据语义和验收标准。

交易平台和策略管理的详细功能分别以以下文档为准：

- `交易平台-需求文档.md`
- `策略管理-需求文档.md`

本文不重复定义各策略的损益归因、交易参数和特有业务规则，具体口径以 `docs/strategies/` 下对应策略文档为准。

## 2. 产品目标

策略模块应形成以下闭环：

1. 对平台执行策略完成机会分析。
2. 在授权范围内发起交易命令并观察执行结果。
3. 对全部纳管策略持续查看损益、资金、持仓和订单。
4. 对外部执行数据完成标准化、质量检查和对账。
5. 对异常执行、资金变化和损益偏差进行穿透复盘。
6. 向风险管理、报表和金融AI分析提供授权的结构化数据。

## 3. 策略范围

### 3.1 平台执行策略

- 资费套利：`funding`。
- 跨所价差：`crossSpread`。
- 海内外价差：`domesticOverseas`。

进入交易平台和策略管理。

### 3.2 非平台执行策略

- 抄底：`dip`。
- 短线交易员 L：`shortLineTraderL`。
- 短线交易员 W：`shortLineTraderW`。

只进入策略管理，不创建空交易平台页面。

## 4. 统一策略身份

所有页面、Query、Command、Event、导入和报表统一使用稳定 `StrategyId`。

必须区分：

- StrategyDefinition：稳定策略定义和能力。
- StrategyVersion：正式规则与参数口径版本。
- StrategyInstance：具体账户、模式和参数下的运行实例。
- StrategyAccountBinding：策略实例与账户用途关系。

前端策略注册表只声明静态展示和页面能力，不是策略运行状态的最终权威。

## 5. 信息架构

策略一级模块固定包含：

### 5.1 交易平台

- 策略切换。
- 行情分析。
- 交易执行。

### 5.2 策略管理

- 策略切换。
- 策略损益。
- 账户资金。
- 订单信息。

主要策略和视角应通过路由表达，刷新和前进后退可以恢复上下文。

## 6. 二级模块协作

平台执行策略的技术协作：

```text
交易平台提交 TradeCommand
→ 后端创建 ExecutionBatch、Order 和 Fill
→ Account、Position、PnL、Risk、Reconciliation 维护各自事实
→ 策略管理通过 Backend Read Model 查询长期结果
```

规则：

- 交易平台前端不直接向策略管理前端传递订单对象。
- 策略管理不重新计算第二套 Order、Position、Account 和 PnL 权威事实。
- 两个模块使用同一 `strategyInstanceId`、`accountId`、`executionBatchId`、`orderId` 和 `executionId`。
- 当前执行反馈与长期查询可以使用不同 Read Model，但语义和身份一致。

## 7. 权限与数据范围

至少区分：

- `strategy.platform.read`。
- `strategy.management.read`。
- `strategy.execution.prepare`。
- `strategy.execution.submit`。
- `strategy.execution.cancel`。
- `strategy.execution.close`。
- `strategy.execution.rebalance`。
- `strategy.execution.manualResolve`。
- `strategy.reconciliation.read`。
- `strategy.reconciliation.confirm`。
- `strategy.data.import`。
- `strategy.data.correct`。

页面访问、操作能力、数据范围、风险限制和审批要求分别判断。前端表现不能替代后端最终校验。

## 8. 运行上下文

策略模块应明确展示：

- DeploymentEnvironment。
- TradingMode。
- TradingPermissionState。
- 当前策略实例。
- 当前账户和数据范围。
- 数据时间和质量。

Demo、Simulation、Paper 和 Live 不得使用容易混淆的文案。Live 交易必须由服务端综合权限、风险、账户、Gateway、执行服务和行情质量形成交易许可。

## 9. 数据标准

共同使用公共领域对象：

- StrategyDefinition／Version／Instance。
- Account／BalanceSnapshot／MarginSnapshot。
- Instrument／QuoteSnapshot。
- TradeCommand／ExecutionBatch／LegInstruction。
- Order／Fill。
- Position／ExposureSnapshot。
- PnLResult／PnLAttributionItem。
- RiskDecision／RiskEvent。
- ReconciliationResult／Difference。
- DataQualityState。

DTO、Domain Model、Backend Read Model、API DTO 和前端 View Model 必须分开。

## 10. 外部执行数据

外部或人工执行策略的数据进入策略管理前必须：

1. 保留原始来源和外部 ID。
2. 通过 Adapter 映射为平台稳定 ID 和对象。
3. 校验时间、币种、单位和状态。
4. 标记数据质量。
5. 执行适用的订单、成交、持仓、余额和损益对账。
6. 对差异和人工修正保留授权、原因和审计。

未核对或数据不完整的结果不得无提示进入正式统计。

## 11. 风险、审批和审计

- Risk 维护风险规则、判断、事件和处置。
- Approval 对高风险配置、风险覆盖、正式数据修正等操作进行独立复核。
- Audit 记录命令、审批、数据修正和人工处理。
- 策略页面只在授权范围内展示和发起相关流程。

审批通过不等于交易或修正已成功执行。

## 12. 跨模块关系

- 对冲基金看板提供研究数据和背景。
- 新闻日历与理财提供事件和内容输入。
- 风险管理提供风险判断、限制、账户管理入口和审计查询。
- 金融AI分析可以读取授权策略材料进行研究和复盘，不修改业务事实。
- 报表读取正式 PnL、Account、Order、Risk 等结果生成版本化输出。

## 13. 非功能要求

- 桌面工作台优先。
- 关键页面具有加载、空数据、延迟、错误、结果未知和待核对状态。
- 前端断线不终止后台执行。
- 页面刷新后能够重新查询未完成 ExecutionBatch。
- 实时事件不是唯一权威来源。
- 敏感数据按最小权限展示。
- 核心命令具备幂等和审计上下文。

## 14. 验收标准

- 策略一级模块只包含交易平台和策略管理。
- 三类平台执行策略和六类纳管策略范围准确。
- 策略身份、版本、实例和账户绑定明确区分。
- 两个二级模块读取同一套后端权威事实。
- 外部执行数据具有来源、质量和对账状态。
- 权限、风险、审批、审计和执行状态分别表达。
- 详细二级模块需求与本文件不存在冲突。
