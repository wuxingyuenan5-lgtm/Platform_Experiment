# 前端版本最小发布门槛

状态：`active`  
适用基线：Platform V5

## 1. 目的

为以 Vibe Coding 为主的开发方式建立低成本、可重复的质量门槛，避免每次修改依赖主观判断。

本规范不是完整测试体系，而是所有稳定提交必须达到的最低要求。

## 2. 提交前命令检查

在 `admin-risk` 目录执行：

```bash
pnpm sync:trading-tools
pnpm type:check
pnpm build
```

### 2.1 `sync:trading-tools`

确保交易工具 Markdown 源与生成数据一致。

失败时：

- 检查 Markdown 格式。
- 检查同步脚本。
- 不直接长期修补生成文件。

### 2.2 `type:check`

当前以项目已有的策略范围类型检查为最低门槛。

失败时：

- 修复本次修改引入的类型错误。
- 不以“全仓库历史错误很多”为理由忽略当前范围错误。
- 不要求本次顺手修复全部历史类型债务。

### 2.3 `build`

确认模板、导入、打包和静态资源不存在阻断错误。

构建通过不等于业务正确，仍必须执行人工冒烟检查。

## 3. 文档一致性检查

涉及以下变化时，必须先更新文档：

- 模块职责变化。
- 策略能力变化。
- 页面固定结构变化。
- 损益或风险口径变化。
- 统一组件使用规则变化。

普通样式微调和明确的缺陷修复不要求更新需求文档。

## 4. 变更范围检查

提交前确认：

- 没有意外修改一级架构和路由。
- 没有误改归档文档。
- 没有直接修改生成文件作为唯一修改。
- 没有因局部问题重写公共主题。
- 没有顺手删除未确认引用的文件。
- 没有将页面本地状态无理由放入全局 Store。

## 5. 人工检查

执行：

- `docs/quality/smoke-checklist.md`

本次未涉及的模块可以标记为“不适用”，但所有受影响路径必须检查。

## 6. 提交要求

一个稳定提交应当：

- 只表达一个清晰主题。
- 不混入无关重构。
- 提交信息能够说明改了什么。
- 对大规模自动生成变更给出来源说明。

推荐格式：

```text
feat: ...
fix: ...
refactor: ...
docs: ...
chore: ...
```

稳定版本可继续使用：

```text
Release platform vN ...
```

## 7. 阻断条件

存在以下任一情况时，不应视为稳定版本：

- 构建失败。
- 本次范围类型检查失败。
- 主要路由无法进入。
- 策略或 section 切换失效。
- 控制台出现持续性运行错误。
- 关键页面内容为空或明显错位。
- active 文档与实现存在重大冲突且未确认。

## 8. 后续升级

当页面和交互稳定后，再逐步加入：

- ESLint/格式检查的稳定门槛。
- Vitest 纯函数和适配器测试。
- Playwright 核心路径自动化。
- GitHub Actions 自动执行。

现阶段不以一次性建设完整测试平台为目标。
