# 文档治理规则

状态：`active`  
适用基线：Platform V5 及后续版本

## 1. 目标

建立唯一、可追溯、适合人工和 AI 协作的文档体系，避免旧需求、临时交接和当前口径同时存在并互相冲突。

## 2. 文档目录规则

```text
docs/
├─ README.md
├─ governance/
├─ audit/
├─ architecture/
├─ modules/
├─ strategies/
├─ strategy/
└─ archive/
```

目录职责：

- `README.md`：唯一文档入口和有效文档索引。
- `governance/`：术语、文档状态和维护规则。
- `audit/`：资产盘点、遗留清单和检查结果。
- `architecture/`：跨模块架构、注册表、职责矩阵和共享规范。
- `modules/`：一级、二级模块定位和模块需求。
- `strategies/`：当前策略定位和策略需求。
- `strategy/`：现有历史策略专题文档，逐步判定有效性并迁移。
- `archive/`：已废弃或只供历史查询的文件。

## 3. 文档状态

每份正式 Markdown 文档顶部必须标记状态。

### `active`

当前有效，可以作为产品、设计和开发依据。

规则：

- 同一主题只能存在一份主 `active` 文档。
- 修改业务口径时优先更新该文件。
- `docs/README.md` 必须列出其入口。

### `draft`

正在讨论，尚未成为正式口径。

规则：

- 不得替代现有 `active` 文档。
- 文件名或顶部必须明确标记草稿。
- 进入开发前必须转为 `active` 或由用户明确授权。

### `superseded`

已被新文档替代。

规则：

- 顶部注明替代它的新文档路径。
- 不再作为开发依据。
- 可以暂时留在原目录，之后移入 archive。

### `archived`

仅用于历史查询。

规则：

- 不参与当前产品和开发判断。
- AI 默认不得读取其内容作为当前需求。
- 可以保留原文件格式，包括 DOCX。

## 4. 文档头部信息

正式文档至少包含：

```text
状态：active | draft | superseded | archived
适用基线：Platform V5 或具体版本
```

按需要增加：

```text
策略 ID：funding
主负责模块：策略管理
替代文档：docs/...
被替代文档：docs/...
最后确认日期：YYYY-MM-DD
```

## 5. 命名规则

### 模块文档

- `模块名称-模块定位.md`
- `模块名称-需求文档.md`

示例：

- `交易平台-模块定位.md`
- `交易平台-需求文档.md`

### 策略文档

使用稳定策略名称：

- `资费套利.md`
- `跨所价差.md`
- `海内外价差.md`

策略 ID 写在文档内部，不直接用作中文文件名。

### 架构文档

使用英文小写连字符或清晰中文名称，仓库内保持同类一致。

### 临时文档

临时交接文件必须带日期，并在任务结束后判定为：

- 合并进 active 文档。
- 标记 superseded。
- 移入 archive。

## 6. 唯一事实来源规则

### 模块定位

唯一来源：`docs/modules/*-模块定位.md`

### 模块需求

唯一来源：`docs/modules/*-需求文档.md`

### 策略定位和策略需求

唯一来源：`docs/strategies/*.md`

### 策略能力

产品口径：`docs/architecture/strategy-capability-matrix.md`  
代码口径：`src/views/strategy/shared/strategyRegistry.ts`

两者必须保持一致。

### 平台术语

唯一来源：`docs/governance/glossary.md`

### 交易工具目录

唯一人工维护来源：`docs/trading-tools-bookmarks-review.md`

生成文件 `marketTools.ts` 不作为人工编辑来源。

## 7. 需求变更流程

每次产品需求变化按以下顺序：

1. 判断影响哪个模块或策略。
2. 更新对应 active 文档。
3. 如影响跨模块边界，更新职责矩阵或能力矩阵。
4. 如出现新术语，更新术语表。
5. 再修改代码。
6. 验证代码与文档一致。
7. 在版本说明中记录变更。

不得先长期修改代码，再依赖聊天记录补文档。

## 8. AI 和 Codex 使用规则

开始任务时优先读取：

1. `docs/README.md`。
2. 对应模块定位。
3. 对应模块需求。
4. 对应策略文档。
5. 相关架构规范。

默认忽略：

- `archive/` 下的文件。
- 标记为 `superseded` 的文档。
- 未被 README 列出的临时交接文档。
- 文件名含“旧版”“废弃”“临时”的内容。

当代码与 active 文档冲突时：

- 不自动判断文档或代码一定正确。
- 先指出冲突。
- 由用户确认实际口径。
- 确认后同时修正文档和代码。

## 9. DOCX 处理规则

DOCX 可以保留，但不再作为活跃需求的主要格式。

处理顺序：

1. 识别是否包含仍有效的唯一信息。
2. 将有效内容迁移到对应 Markdown active 文档。
3. 记录替代关系。
4. 将原 DOCX 移入 `docs/archive/legacy-docx/`。
5. 不直接删除，除非用户明确要求。

旧 DOCX 归档后不得继续被 AI 当作当前需求。

## 10. 交接文档规则

交接文档只用于临时恢复上下文，不应成为长期产品定义。

交接完成后：

- 产品信息合并到模块或策略文档。
- 工程信息合并到架构或审计文档。
- 版本信息合并到 changelog。
- 原交接文档标记 superseded 或 archived。

## 11. 文档审查规则

文档审查至少检查：

- 是否有明确状态。
- 是否与现有 active 文档重复。
- 是否使用统一术语。
- 是否明确负责和不负责。
- 是否写明当前完成状态。
- 是否把未确认内容当成确定需求。
- 是否包含过时版本描述。
- 是否与当前路由和代码结构明显冲突。

## 12. 删除规则

文档或代码不得仅因“看起来旧”而删除。

删除前必须确认：

- 无路由引用。
- 无代码引用。
- 无唯一业务信息。
- 已有替代文档或实现。
- 已记录删除原因。
- 用户已明确允许删除，或已进入确认后的清理阶段。

## 13. 更新责任

当前阶段由用户最终确认产品口径；AI 和 Codex 可以：

- 盘点冲突。
- 提议结构。
- 更新文档。
- 检查一致性。

不得在未确认时自行改变：

- 一级架构。
- 策略范围。
- 损益口径。
- 风险规则。
- 交易执行规则。

## 14. 验收标准

- `docs/README.md` 可以作为唯一文档入口。
- 每个 active 文档具有明确状态和范围。
- 模块和策略不存在多份互相冲突的 active 文档。
- 旧 DOCX 和交接文档具有明确归档计划。
- AI 开发任务可以通过固定阅读顺序获取当前口径。
