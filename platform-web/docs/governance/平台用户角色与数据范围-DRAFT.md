# Variable-Global 平台用户角色与数据范围

状态：`draft`  
产品基线：Platform V5  
架构讨论版本：Platform V6+  
适用分支：`refactor/frontend-architecture-v6`  
文档层级：全局用户、权限与数据范围需求  
更新日期：2026-07-17

## 1. 文档定位

本文定义平台用户类型、角色职责、能力权限、数据范围、高风险操作和跨模块访问原则。

本文不直接定义：

- 具体 IAM 技术实现。
- 用户表、Token、SSO 或密码算法。
- 每个页面的最终按钮位置。
- 已批准的组织架构和实际人员名单。

具体模块仍需在自身需求中声明所需能力权限和数据范围。

---

## 2. 核心原则

### 2.1 角色不等于权限

角色用于表达典型职责，实际授权由以下组合决定：

```text
Role
+ Capability
+ Data Scope
+ Environment Scope
+ Trading Mode Scope
+ Approval Requirement
+ Temporary Grant，适用时
```

不得仅凭“管理员”“交易员”等角色名称直接授予全部能力。

### 2.2 页面访问、数据读取和业务操作分开

必须分别判断：

- 是否可进入模块或页面。
- 是否可读取当前数据。
- 是否可查看敏感字段。
- 是否可准备操作。
- 是否可正式提交命令。
- 是否可审批、确认或覆盖。
- 是否可修正数据。
- 是否可导出或生成正式报告。

### 2.3 最小权限

默认只授予完成职责所需的最小能力和最小数据范围。

未知、缺失或冲突的权限结果默认拒绝写入和高风险操作。

### 2.4 Live 权限独立

具备 Demo、Simulation 或 Paper 权限不自动获得 Live 权限。

Live 至少独立判断：

- 用户 Live capability。
- 账户 Live 白名单。
- StrategyInstance Live 许可。
- Runtime／Gateway Live 许可。
- RiskDecision。
- GlobalTradingBlock。
- 数据质量。
- ApprovalGrant，适用时。

### 2.5 审批不替代执行权限

审批通过不等于：

- 用户自动获得目标数据范围。
- 命令已执行。
- 交易已成交。
- 风险检查已通过。
- 数据修正已成功。

目标领域仍负责最终校验和执行。

## 3. 典型用户类型

### 3.1 研究人员

主要任务：

- 查看宏观、商品、加密、美股、A 股和全球研究数据。
- 使用新闻、宏观日历和研究工具。
- 查看策略行情分析和历史表现。
- 创建金融AI分析任务，适用时。

默认不具备：

- 正式交易提交。
- 风险规则修改。
- 账户主档修改。
- 正式数据修正。

### 3.2 交易人员

主要任务：

- 查看策略机会和执行上下文。
- 准备交易参数。
- 在授权范围内提交、撤销、平仓、调整或补对冲。
- 跟踪订单、成交、配平和暴露。

必须限制：

- 可交易策略。
- 可交易账户。
- 可交易市场和标的。
- TradingMode。
- 最大额度和风险范围。

### 3.3 策略负责人

主要任务：

- 查看负责策略的研究、执行和长期结果。
- 管理或申请 StrategyVersion、StrategyInstance 和账户绑定变更。
- 查看策略损益、资金、订单、风险和对账。
- 处理策略异常或发起人工干预。

不自动拥有：

- 系统级管理员权限。
- 全部策略和账户权限。
- 未经审批的风险覆盖权限。

### 3.4 风险与运营人员

主要任务：

- 查看风险指标、风险事件和交易阻断。
- 查看账户、保证金、暴露和异常执行。
- 处理对账差异、服务异常和运行状态。
- 管理或审批风险规则、额度和高风险操作，按职责分离。

必须区分：

- 风险查看。
- 风险处置。
- 风险规则维护。
- 风险覆盖。
- 审批权限。

### 3.5 数据核对人员

主要任务：

- 查看数据来源、质量和同步状态。
- 执行订单、成交、持仓、账户和损益核对。
- 导入外部数据。
- 发起或确认数据修正。

不得未经授权直接覆盖原始事实。

### 3.6 系统管理员

主要任务：

- 用户、角色和权限管理。
- 系统配置和环境管理。
- Gateway、Runtime 和服务配置管理，按职责授权。
- 日志、审计和系统状态查看。

系统管理员不应因技术权限自动获得投资决策、交易提交或风险覆盖权限。

### 3.7 只读观察人员

主要任务：

- 查看授权模块和摘要。
- 查看已脱敏的策略、账户、风险或报表。

不得执行正式写入、交易、修正和审批。

### 3.8 个人账号用户

用于管理：

- 个人资料。
- 登录和安全设置。
- 通知偏好。
- 个人会话和设备。

个人账号页面不得成为系统权限配置的替代入口。

## 4. 数据范围维度

数据范围至少可以按以下维度组合。

### 4.1 组织范围

- 全组织。
- 业务中心。
- 团队或项目。
- 仅本人相关数据，适用时。

### 4.2 产品模块范围

- 首页。
- 对冲基金看板。
- 新闻日历与理财。
- 策略。
- 风险管理。
- 金融AI分析。

### 4.3 策略范围

- 指定 StrategyId。
- 指定 StrategyInstance。
- 全部纳管策略。
- 仅平台执行策略。
- 仅外部执行策略。

### 4.4 账户范围

- 指定 accountId。
- 指定账户用途。
- 指定经纪商或交易所。
- 指定 TradingMode。
- 指定账户币种或资产范围。

### 4.5 市场和标的范围

- 指定 Venue。
- 指定市场类型。
- 指定 Instrument。
- 指定资产类别。
- 指定地区。

### 4.6 数据类型范围

- Research Data。
- Execution Market Data。
- Content and Calendar Data。
- Account 和 Position。
- Order 和 Fill。
- PnL 和 Ledger。
- Risk。
- Audit。
- AI Task 和 Result。

### 4.7 时间范围

- 当前和实时数据。
- 指定历史区间。
- 归档数据。
- 受保存和合规规则限制的数据。

### 4.8 敏感级别

候选分级：

- Public：公开研究或市场信息。
- Internal：内部整理和普通业务信息。
- Confidential：账户、持仓、损益和内部策略信息。
- Restricted：交易凭证、密钥、个人敏感信息和高风险配置。

前端、导出、日志和 AI 使用范围均受敏感级别控制。

## 5. 能力权限结构

能力权限建议使用稳定命名：

```text
<domain>.<resource>.<action>
```

示例：

- `dashboard.macro.read`。
- `content.news.read`。
- `strategy.platform.read`。
- `strategy.execution.prepare`。
- `strategy.execution.submit`。
- `strategy.execution.cancel`。
- `strategy.execution.rebalance`。
- `strategy.execution.manualResolve`。
- `strategy.management.read`。
- `strategy.data.import`。
- `strategy.data.correct`。
- `strategy.reconciliation.read`。
- `strategy.reconciliation.confirm`。
- `risk.rule.read`。
- `risk.rule.manage`。
- `risk.override.request`。
- `risk.override.approve`。
- `account.master.read`。
- `account.master.manage`。
- `report.generate`。
- `audit.read`。
- `iam.user.manage`。
- `system.config.manage`。
- `ai.analysis.submit`。
- `ai.analysis.read`。

正式权限名称需要在 IAM 架构和各模块需求中统一维护。

## 7. 高风险操作

以下操作至少需要加强校验，部分操作需要 ApprovalPolicy：

- Live 交易提交。
- 超过普通额度的交易。
- 风险规则和额度修改。
- GlobalTradingBlock 解除。
- 风险覆盖和强制放行。
- 账户主档或 StrategyAccountBinding 生效。
- 交易凭证和 Runtime 配置变更。
- 正式数据修正和 AdjustmentEntry。
- 删除或归档关键业务数据。
- 正式报表发布。
- 用户高权限授予。

每个高风险操作需要记录：

- 操作者。
- 目标对象。
- 原因。
- 前后值。
- 权限和审批证据。
- 时间。
- 请求、命令和关联 ID。
- 执行结果。

## 8. 临时授权和代理

后续如支持临时授权，必须具有：

- 明确目标能力。
- 明确数据范围。
- 生效时间和失效时间。
- 授权人和理由。
- 是否允许转授权。
- 使用记录。
- 自动失效。

不得通过共享账号解决临时协作。

---

## 9. 前端要求

前端必须：

- 根据后端返回的 Capability 和 Data Scope 展示功能。
- 对禁用操作显示原因，适用时。
- 不将隐藏按钮当作安全控制。
- 不通过本地常量、URL 或环境变量赋予权限。
- 不缓存或展示无权访问的敏感数据。
- 权限变化后重新获取受影响数据。
- 会话失效时清理敏感状态并安全跳转。

---

## 10. 后端要求

后端必须：

- 对每个 Query 和 Command 执行服务端授权。
- 从受信任会话确定用户身份。
- 不接受前端伪造 operatorId、角色和数据范围。
- 对资源级访问执行 Data Scope 校验。
- 对 Live、风险覆盖和数据修正执行专项校验。
- 保留授权决策和审计上下文。
- 拒绝未知或无法判定的高风险请求。

---

## 11. 金融AI分析数据范围

金融AI分析只可使用用户本身有权读取的数据。

AI 输出必须继承来源权限，不得因为生成摘要而扩大数据范围。

禁止发送给模型：

- API Secret。
- 交易密码。
- MT5 登录密码。
- 私钥。
- 完整身份凭证。
- 未授权账户、订单、持仓和内部策略材料。

用户失去来源数据权限后，历史 AI 结果的访问和展示规则需要重新评审。

---

## 12. 验收标准

- 角色、能力权限和数据范围明确分开。
- 页面访问、数据读取、敏感字段和正式操作分别校验。
- Live 权限独立于普通交易权限。
- 系统管理员不自动获得投资和交易权限。
- 风险覆盖、数据修正和高权限授予具有审批和审计边界。
- 所有模块能够引用统一的用户和数据范围模型。
- 金融AI分析不扩大用户的数据访问范围。
- 前端权限展示不替代后端授权。
