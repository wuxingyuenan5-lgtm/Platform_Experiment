## 1. 采用方式

| 采用方式 | 定义 |
|---|---|
| 自建 | 由平台定义模型、契约和主要实现 |
| 直接复用 | 在隔离边界内直接使用成熟组件 |
| 封装复用 | 通过 Adapter／Port 包装后使用 |
| Fork 维护 | 以外部实现为基础，由平台维护分支 |
| 设计参考 | 只吸收模型、流程、状态机或可靠性思想 |
| 暂缓 | 当前保留可能性，但不进入主路径 |
| 待验证 | 需要 PoC、兼容性或性能验证后决定 |

## 2. 决策原则

每项能力必须分别回答：

1. 是否属于平台核心业务能力。
2. 是否需要平台自有领域模型和数据权威。
3. 外部组件是否会把平台绑定到其对象、状态或存储。
4. 组件是否支持 MT5、Crypto、CTP 和多账户实际需求。
5. 是否支持幂等、恢复、对账和故障隔离。
6. 许可证、维护活跃度、版本策略和安全风险是否可接受。
7. 替换成本和退出路径是否清晰。
8. 是否能通过 Adapter 隔离外部字段和错误语义。
9. 是否会形成第二套订单、持仓、损益或账本权威。

## 3. 策略文档与外部组件的关系

六份策略文档可以声明：

- 需要哪些行情、账户、订单、成交、Funding、Swap、合约和恢复能力。
- 哪些外部仓库或 SDK 是候选来源。
- 哪些能力只能作为设计参考。
- 哪些外部对象不得成为平台业务权威。

策略文档不得直接批准：

- 最终采用某个仓库。
- 锁定版本。
- Fork 维护。
- 许可证接受。
- 将外部数据库作为平台数据库。
- 将外部 Strategy、Order、Position、Risk 或 PnL 对象作为平台 Domain Model。

最终采用结论必须进入本文、专项 PoC 记录和 ADR。

### 8.1 CCXT 采用边界

CCXT 可以降低以下能力的重复开发：

- 市场和合约元数据。
- Ticker、Order Book、Trades 和 OHLCV。
- Funding Rate、历史 Funding 和 Open Interest。
- 订单、余额和持仓的统一接口。
- REST 和 WebSocket，取决于版本和产品。

但不得默认认为：

- 三家交易所账户语义完全一致。
- 统一字段足以覆盖所有私有状态。
- `fundingRate` 就是实际结算记录。
- 单次 createOrder 返回就代表最终订单成功。
- CCXT 对象可以直接作为平台 Order、Position 或 EconomicEvent。

关键私有链路必须与交易所官方文档和接口结果交叉验证。

### 10.1 SpreadTrading 适用判断

- 同一 Runtime 内的价差定义和低层腿算法可优先 PoC。
- 跨 Crypto、MT5、CTP 和外部记录的业务编排仍由平台 ExecutionBatch 负责。
- SpreadTrading 的 Position、Order 和 PnL 不替代平台对象。
- 必须验证部分成交、结果未知、重启、对账、平今平昨和换月。

## 14. 当前建议汇总

### 14.1 明确自建

- 平台产品和领域模型。
