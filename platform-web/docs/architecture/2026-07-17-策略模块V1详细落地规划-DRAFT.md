## 1. V1 核心目标

第一版本必须形成以下业务闭环：

```text
行情与账户数据接入
→ 策略机会分析
→ 交易参数准备
→ 权限与执行前检查
→ TradeCommand
→ ExecutionBatch
→ MT5 / Crypto 外部订单
→ Order / Fill / Position 回报
→ 配平与暴露判断
→ 基础对账与恢复
→ 策略损益、账户资金和订单查询
```

V1 的产品目标是让策略模块从前端工作台升级为可连接真实外部系统、可在 Demo／Paper 环境验证完整交易链路、可持续查询策略结果的平台。

V1 不以“全平台所有一级模块都接后端”为目标。

## 2. V1 产品范围

### 2.1 策略一级模块

完整落地：

```text
策略
├─ 交易平台
│  ├─ 行情分析
│  └─ 交易执行
└─ 策略管理
   ├─ 策略损益
   ├─ 账户资金
   └─ 订单信息
```

### 2.2 交易平台策略范围

| 策略 | 行情分析 | 平台真实执行链路 | V1 说明 |
|---|---:|---:|---|
| 资费套利 | 完整 | 完整 | Crypto 现货 + 永续双腿 |
| 跨所价差 | 完整 | 完整 | Crypto `XAUTUSDT.P` + MT5 `XAUUSD` 双腿 |
| 海内外价差 | 分析/模拟可用 | 不做完整真实执行闭环 | 保留页面、模型、换算、分析和字段预留；CTP、国内真实执行、正式人民币 FX PnL、平今/平昨、换月和结算级对账延后 |

### 2.3 策略管理范围

六类策略全部进入策略管理：

- 资费套利。
- 跨所价差。
- 海内外价差。
- 抄底。
- 短线交易员 L。
- 短线交易员 W。

数据来源分为：

| 策略 | V1 数据来源 |
|---|---|
| 资费套利 | 平台自动执行事实 + Funding 结算 + 外部账户事实 |
| 跨所价差 | 平台自动执行事实 + MT5／Crypto 外部事实 |
| 海内外价差 | 导入或现有数据源 + MT5 海外端数据；CTP 订单执行延后 |
| 抄底 | 外部或人工导入 |
| 短线交易员 L | 外部来源或 MT5 历史导入 |
| 短线交易员 W | 外部来源或 MT5 历史导入 |

### 2.4 其他一级模块

V1 不建设完整后端：

- 首页。
- 对冲基金看板。
- 新闻日历与理财。
- 风险管理。
- 金融AI分析。

但不得删除现有前端页面和产品结构。

策略交易必需的以下能力在 `platform-api` 内实现为内部模块：

- 最小用户和权限。
- 账户主档和快照。
- 最小业务风控。
- 审计日志。
- 对账与恢复。
- EconomicEvent 和基础 PnL。

这些能力不等于对应一级模块已经完成开发。

## 3. V1 总体工程结构

```text
liuchengtu/
├─ platform-web/                  # 现有 Vue 前端
├─ platform-api/            # Python 模块化单体业务后端
├─ execution-runtime/           # 独立交易执行与接入 Runtime
├─ packages/contracts/          # 跨进程稳定契约
└─ deploy/                      # 本地和测试部署
```

运行关系：

```text
Browser
   ↓
platform-web
   ↓ REST / WebSocket
platform-api
   ↓ PostgreSQL Outbox + Redis Streams
execution-runtime
   ├─ Crypto Gateway Workers
   └─ MT5 Runtime / Worker
         ↓
Binance / OKX / Bybit / MT5 Broker
```

CTP 接口和 Worker 不进入 V1 必须范围。

## 4. V1 技术基线

### 4.1 前端

沿用现有：

- Vue。
- TypeScript。
- 现有路由、页面和组件。
- REST 查询和命令提交。
- WebSocket 接收交易与账户实时更新。

### 4.2 平台业务后端

默认候选：

- Python 3.12。
- FastAPI。
- Pydantic v2。
- SQLAlchemy 2.x。
- Alembic。
- PostgreSQL。
- Redis。
- pytest。

### 4.3 Execution Runtime

默认候选：

- Python。
- 自有 Runtime 主程序。
- 自有 Command、Event、Port 和 Adapter。
- Runtime 本地 SQLite Journal。
- Redis Streams 消费和发布。
- vn.py、官方 SDK、MetaTrader5 包、aiomql 等按能力封装。

### 4.4 基础设施

V1 只使用：

- 一个 PostgreSQL 实例。
- 一个 Redis 实例。
- Docker Compose 管理 PostgreSQL、Redis 和可容器化组件。
- Windows 运行 MT5 Terminal 和 MT5 Worker。

V1 不使用：

- Kubernetes。
- Kafka。
- 多数据库拆分。
- 完整微服务体系。
- 独立数据湖。
- 全量 Tick 永久存储。

- 平台执行与外部执行来源标识。

### 5.2 Trading and Execution

V1 必须实现：

- TradeIntent 输入模型。
- TradeCommand。
- ExecutionBatch。
- ExecutionPlan 值对象。
- LegInstruction。
- Order。
- Fill。
- ExecutionBalanceStatus。
- ExposureStatus／ExposureSnapshot。
- 人工撤单、补对冲和终止入口的最小模型。

### 5.3 Account

V1 必须实现：

- Account 主档。
- Account 与 Gateway／外部账户标识。
- BalanceSnapshot。
- MarginSnapshot。
- PositionSnapshot。
- 账户币种、账户模式和交易许可。

不建设完整账户管理一级模块后台。

### 5.4 Risk

V1 只实现策略执行所需的最小风险检查：

- 用户是否具备提交能力。
- TradingMode 是否允许。
- StrategyInstance 是否可交易。
- Account 是否可用。
- Gateway 是否可用。
- 行情是否新鲜。
- 订单数量和价格是否符合规则。
- 账户可用资金和保证金是否满足。
- 最大单笔数量。
- 最大策略名义价值。
- 最大单腿暴露。
- 最大残腿时间。
- 全局禁止新增风险开关。

不建设完整风险规则配置中心和复杂 Maker／Checker 工作流。

### 5.5 Reconciliation

V1 只覆盖：

- 平台订单与外部订单。
- 平台成交与外部成交。
- 平台持仓与外部持仓。
- 平台账户快照与外部账户。
- 未知外部订单。
- 外部手工订单。

不自动覆盖或删除原始记录。

### 5.6 PnL and EconomicEvent

V1 从一开始保存：

- Fill EconomicEvent。
- TradingFee EconomicEvent。
- FundingSettlement EconomicEvent。
- MT5Swap／OvernightFee EconomicEvent。
- ManualAdjustment EconomicEvent。

V1 实现策略管理所需的基础 PnLResult；完整不可变账本和复杂重算流程可以后续增强。

## 6. execution-runtime V1 模块

```text
execution-runtime/
├─ runtime/
│  ├─ main.py
│  ├─ command_handlers/
│  ├─ event_publishers/
│  ├─ oms/
│  ├─ journal/
│  ├─ reconciliation/
│  └─ recovery/
├─ gateways/
│  ├─ fake/
│  ├─ crypto/
│  │  ├─ binance/
│  │  ├─ okx/
│  │  └─ bybit/
│  └─ mt5/
├─ workers/
│  ├─ crypto/
│  └─ mt5/
├─ adapters/
└─ tests/
```

### 6.1 Runtime Main

负责：

- 消费 RuntimeCommand。
- 命令幂等去重。
- 将命令路由到目标 Worker。
- 汇总标准 RuntimeEvent。
- Runtime 心跳和能力上报。
- 启动恢复。
- 本地 Journal。

### 6.2 Runtime 本地 Journal

使用轻量 SQLite 保存：

- 已处理 commandId。
- commandId 与外部请求映射。
- platformOrderId 与 externalOrderId 映射。
- 待发送 RuntimeEvent。
- 最近同步和恢复位置。
- Worker 会话信息。

它不是平台业务数据库，不计算最终 PnL。

### 6.3 Runtime OMS

V1 维护：

- 当前活动订单。
- 当前 Fill 缓存。
- 当前账户和持仓快照。
- Gateway／Worker 状态。

可评估封装 vn.py OmsEngine，也可以先自建最小 OMS。平台对象和持久化事实不直接依赖 vn.py 对象。

### 7.1 V1 核心 Port

第一版实现：

```text
TradingGatewayPort
MarketDataGatewayPort
AccountGatewayPort
FundingGatewayPort
```

- BorrowGatewayPort。

### 7.2 GatewayCapability

每个 Gateway 必须声明：

- 支持的市场类型。
- 支持的订单类型。
- Spot／Perpetual。
- Limit／Market。
- Stop／Stop Limit，适用时。
- IOC／FOK／Post Only，适用时。
- Reduce Only。
- Hedging／Netting。
- Partial Close。
- Funding 数据。
- Client Order ID。
- 历史订单和成交查询。

前端和后端不能假设所有 Gateway 能力相同。

## 8. Crypto 接入详细规划

### 8.1 V1 产品覆盖

V1 产品目标覆盖：

- Binance。
- OKX。
- Bybit。

三家均需要支持市场数据和机会分析。

三家最终均应具备基础账户和交易适配能力，但开发时采用逐家打通、复用标准 Adapter 的方式，不能三家同时从零实现。

### 8.2 接入顺序建议

接入顺序只代表开发验证顺序，不改变 V1 产品范围：

1. 选择一家测试账户打通完整端到端链路。
2. 抽取稳定 Crypto Adapter 和契约测试。
3. 接入第二家交易所。
4. 接入第三家交易所。
5. 完成三家行情、账户、订单、持仓和 Funding 统一查询。

具体第一家由账户准备、API 权限、测试环境和现有交易习惯决定。

### 8.3 Crypto 必须支持

#### 行情

- Spot Bid／Ask。
- Perpetual Bid／Ask。
- Mark Price。
- Index Price，交易所提供时。
- Funding Rate 当前值。
- 下一结算时间。
- 必要深度和可成交数量。
- sourceTime 和 receivedAt。

#### 合约和规则

- Symbol 映射。
- 价格精度。
- 数量精度。
- 最小数量。
- 最小名义价值。
- 合约乘数。
- Position Mode。

#### 账户

- 现货余额。
- 合约权益。
- 可用保证金。
- 持仓。
- 强平价或风险距离，能够取得时。
- 统一账户／经典账户差异。

#### 交易

- 现货买卖。
- USDT 本位永续买卖。
- 下单。
- 撤单。
- 查询活动订单。
- 查询历史订单。
- 查询成交。
- Client Order ID。
- Reduce Only。
- Post Only，支持时。

#### Funding

- 当前或预计 Funding Rate。
- Funding 历史。
- 实际 Funding 结算记录。
- 预计值与实际结算值严格分开。

### 8.4 V1 不要求

- 自动借币。
- 自动还币。
- 复杂跨账户自动划转。
- 全部币本位产品。
- 所有期权产品。
- 高频订单簿策略。

```text
Runtime Main
```

- Bid／Ask。
- Contract Size。
- Tick Size。
- Tick Value。
- 最小手数和手数步进。

- 下单和撤单。
- 部分平仓。

- PyTrader 只作为远程节点备用，不进入 V1 主路径。

## 10. 下单可靠性模型

### 10.1 下单前预创建 Order

平台在命令进入 Runtime 前创建：

- platformOrderId。
- Order 记录。
- `submission_requested` 初始状态。
- 稳定 clientOrderId。

链路：

```text
LegInstruction
→ 预创建平台 Order
→ 写 Command Outbox
→ Runtime 消费
→ Gateway 提交
→ 外部返回 externalOrderId
→ 平台 Order acknowledged
→ Fill
```

即使 Runtime 在外部提交后异常，平台仍可使用 platformOrderId、clientOrderId、Magic Number 和外部历史重新找回订单。

### 10.2 消息语义

采用：

```text
至少一次传输
+
幂等处理
```

不追求无法可靠保证的严格 Exactly Once。

### 10.3 去重规则

- Runtime 通过 commandId 和 idempotencyKey 去重。
- Platform 通过 eventId 去重。
- OrderUpdate 通过 externalOrderId、platformOrderId 和版本处理。
- Fill 通过外部成交 ID 或稳定复合键去重。
- 重复事件不能重复增加持仓和损益。

## 13. V1 两条真实执行链

### 13.1 资费套利

```text
Crypto Spot Quote + Perpetual Quote + Funding
→ 机会分析
→ Spot / Perpetual 目标数量
→ TradeCommand
→ ExecutionBatch
→ 两条 LegInstruction
→ 两张或多张 Order
→ Fill
→ 配平与单腿暴露
→ FundingSettlement EconomicEvent
→ PnLResult
```

必须支持：

- 正 Funding 机会筛选。
- 现货与永续方向相反。
- 同交易所或跨交易所账户。
- 两腿名义价值配平。
- 部分成交。
- 撤单和补对冲。
- 实际 Funding 结算。
- 资金费率反转提示。

V1 损益归因：

```text
累计总损益
├─ 库存费累计收益
├─ 综合基差损益
├─ 累计交易成本
└─ 已确认调整项
```

不设置配平误差一级损益项。

### 13.2 跨所价差

```text
Crypto XAUTUSDT.P Quote
+
MT5 XAUUSD Quote
→ 单位和币种标准化
→ 跨所价差
→ 机会分析
→ TradeCommand
→ ExecutionBatch
→ Crypto Leg + MT5 Leg
→ Order / Fill
→ 实际成交价差
→ 残腿和暴露
→ PnLResult
```

必须支持：

- XAUTUSDT.P 与 XAUUSD。
- USDT／USD 换算口径。
- 盎司、合约数量和 MT5 lot 换算。

```text
累计总损益

├─ 资金费或库存费成本／收益
```

## 18. TradingMode 和上线边界

V1 必须支持：

- demo。
- simulation。
- paper。
- live 的数据结构和服务端判断。

V1 验收以 Fake Gateway、交易所测试环境和 MT5 Demo 为主。

Live 真实资金启用属于独立 Go-Live Gate，不因为代码存在 `live` 枚举就自动开放。

Live 至少要求：

- Runtime Live capability。
- Gateway 健康。
- 行情质量通过。
- RiskDecision 通过。
- 无全局交易阻断。
- 恢复和对账通过。
- 凭证隔离。

## 19. 恢复和对账

### 19.1 Runtime 启动

```text
STARTING
→ CONNECTING
→ SYNCHRONIZING
→ RECONCILING
→ RECOVERING
→ READY
```

### 19.2 READY 条件

- Crypto／MT5 目标 Gateway 已连接。
- 合约和能力已同步。
- 账户和持仓已同步。
- 活动订单和近期成交已同步。
- 未完成 ExecutionBatch 已识别。
- 未知订单已进入对账。
- 无阻断级残腿或差异。
- Runtime 和 Platform 时间偏差在阈值内。

### 19.3 差异处理

V1 支持：

- 标记外部订单。
- 关联或保留未归属订单。
- 重新同步。
- 冻结相关 StrategyInstance。
- 只允许减仓或人工处理。
- 记录人工决定和审计。

不自动覆盖外部和平台原始记录。

## 21. 实施阶段

阶段表示依赖顺序，不表示固定工期。

### 阶段 A：架构与契约冻结

交付：

- 三工程目录。
- 核心对象和状态清单。
- RuntimeCommandEnvelope。
- RuntimeEventEnvelope。
- Gateway Port。
- 数据库初版 ERD。
- API 和事件命名约定。

验收：

- 前端、Backend、Runtime 的责任无重叠。
- MT5 和 Crypto 可以使用同一平台契约。
- CTP 延后不会导致模型重做。

### 阶段 B：工程骨架与 Fake Gateway

交付：

- FastAPI 后端骨架。
- PostgreSQL 和 Alembic。
- Redis Streams。
- Outbox／Inbox。
- Runtime 主程序。
- Runtime SQLite Journal。
- Fake Gateway。
- WebSocket 状态推送。

验收：

- 从前端提交命令到 Fake Fill 完成闭环。
- 重复命令不产生重复订单。
- Backend 和 Runtime 重启后可以恢复。

### 阶段 C：Crypto 市场数据和账户

交付：

- Binance、OKX、Bybit 行情 Adapter。
- Spot／Perpetual Quote。
- Funding 当前值、历史和结算时间。
- 合约规则。
- 账户、余额和持仓。

验收：

- 三家行情可以统一展示和比较。
- 时间、精度、单位和数据质量明确。
- 数据断线和过期状态可见。

### 阶段 D：首个 Crypto 交易 Gateway

交付：

- 一家交易所测试账户完整下单链路。
- Spot 和 USDT Perpetual。
- Order、Fill、Position 和 Funding Settlement。
- clientOrderId 和幂等。
- 启动同步和基础对账。

验收：

- 现货与永续订单可真实提交测试环境。
- 部分成交、撤单、拒单和重启可处理。

### 阶段 E：其余 Crypto 交易 Gateway

交付：

- 第二、第三家交易所交易 Adapter。
- 契约测试复用。
- 交易所特有能力映射。

验收：

- 三家均可查询账户、订单、成交和 Funding。
- 至少按已配置测试账户执行基础订单。

### 阶段 F：MT5 Gateway 和 Worker

交付：

- MT5 Worker。
- XAUUSD 行情、账户、持仓和订单。
- Magic Number／Comment 映射。
- 部分平仓和手工订单识别。
- Swap／OvernightFee 摄取。
- 恢复和对账。

验收：

- MT5 Demo 下单、撤单、成交和持仓闭环。
- 终端和 Runtime 重启后可恢复。

### 阶段 G：资费套利完整落地

交付：

- 行情分析真实数据。
- 现货／永续双腿执行。
- 配平和暴露。
- Funding Settlement。
- 资费策略 PnL。
- 策略管理三类页面。

验收：

- 一次资费套利开仓、持有、Funding 结算和平仓可完整追溯。

### 阶段 H：跨所价差完整落地

交付：

- Crypto XAUTUSDT.P + MT5 XAUUSD。
- 统一价差和数量换算。
- 双腿执行。
- 残腿和紧急对冲。
- 跨所策略 PnL。
- 策略管理三类页面。

验收：

- 一次跨所开仓和平仓的双腿、成交价差、成本和异常可完整追溯。

### 阶段 I：六策略管理与数据导入

交付：

- 六类策略 Read Model。
- 外部订单、成交、账户和损益导入。
- 海内外价差只读／导入支持。
- 抄底、短线 L、短线 W 管理页面数据。

验收：

- 六类策略均可进入损益、资金和订单视图。
- 数据来源和质量清晰，不使用虚构零值。

### 阶段 J：可靠性与发布验收

交付：

- 恢复报告。
- 对账差异处理。
- 日志关联 ID。
- 权限和模式隔离。
- Demo／Paper 回归测试。
- Go-Live Gate 清单，暂不自动启用 Live。

验收：

- 断网、重启、重复消息、未知订单和外部手工订单均有明确结果。

## 22. V1 验收矩阵

### 22.1 策略产品

- 交易平台三类策略页面保留。
- 资费套利和跨所价差使用真实 Backend／Runtime 数据。
- 海内外价差明确标识国内执行未接入。
- 策略管理覆盖六类策略。

### 22.2 外部接入

- Binance、OKX、Bybit 行情接入。
- 三家账户、订单、成交和 Funding 适配达到配置范围。
- MT5 Demo 行情、账户、订单、成交和持仓接入。
- CTP 不作为 V1 验收阻断项。

### 22.3 交易可靠性

- TradeCommand accepted 不等于成交。
- 下单前创建 platformOrderId。
- 命令和事件幂等。
- 部分成交、撤单、拒单和结果未知可表达。
- Backend 与 Runtime 重启后可恢复。
- 平台与外部订单、成交、持仓和账户可对账。

### 22.4 策略管理

- 策略损益可核对。
- 账户资金来源明确。
- 订单、Fill 和 ExecutionBatch 可穿透。
- 外部和导入数据具有来源、批次和质量状态。

### 22.5 安全

- 浏览器不持有交易凭证。
- Demo、Paper、Live 凭证和许可隔离。
- 未授权用户不能提交交易。
- 日志不打印完整 Secret。
- Live 默认不开放。

## 25. 本规划的核心判断

V1 后端只围绕策略模块建设，但底层必须具备真实交易平台不可缺少的最小能力：

```text
Strategy
+
Trading and Execution
+
Account Snapshots
+
Minimum Risk
+
Reconciliation and Recovery
+
EconomicEvent and PnL
```

这不是建设其他一级模块，而是在策略模块内部建立可真实运行、可恢复、可核对的必要基础。

V1 的关键价值不在于页面数量，而在于同时打通：

```text
Crypto 双腿策略
+
Crypto-MT5 跨市场双腿策略
+
六策略管理视图
+
可靠订单、成交、持仓、对账和损益链路
```
