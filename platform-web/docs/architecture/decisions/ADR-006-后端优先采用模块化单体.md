# ADR-006：后端优先采用模块化单体

状态：`accepted`  
日期：2026-07-16  
适用分支：`refactor/frontend-architecture-v6`

## 背景

Platform V6 已经明确前端、后端、前后端协作和公共领域模型四层架构，但真实后端尚未建设，具体语言、数据库、消息队列、交易内核和部署方式仍待后续评审。

当前平台业务包含行情、策略、交易执行、账户、持仓、损益、风险、对账、审计、通知和报表等多个领域。如果在业务边界、数据口径和团队能力尚未经过真实运行验证前直接拆分大量微服务，将显著增加：

- 部署和运维复杂度。
- 分布式事务和状态一致性问题。
- 接口和事件协调成本。
- 本地开发和故障排查难度。
- 对新人和小团队的学习负担。

同时，交易执行、Gateway、行情接入和异步任务可能具有独立进程和故障隔离需求，不能将“模块化单体”理解为所有逻辑必须运行在一个进程中。

## 决策

Platform V6 后端初期优先采用模块化单体架构：

- 业务代码按照稳定领域模块组织。
- 每个核心对象具有唯一主责模块和数据权威。
- 模块之间通过公开应用服务、领域接口或事件协作。
- 即使共用数据库，也禁止跨模块任意修改对方内部数据。
- Platform API／BFF 作为前端主要访问入口。
- 交易执行、外部 Gateway、行情接入和重型异步任务可以根据可靠性需要采用独立进程。
- 不在业务边界和运行压力未验证前拆分大量微服务。

初始逻辑模块包括：

- IAM。
- Market Data。
- Strategy。
- Trading and Execution。
- Account and Position。
- PnL and Ledger。
- Risk。
- Reconciliation and Data Quality。
- Audit。
- Notification。
- Reporting。
- Integration Gateway。

## 原因

- 适合当前团队规模和系统成熟度。
- 降低前期部署、测试和运维成本。
- 便于建立强类型领域模型和统一事务边界。
- 能够先验证真实业务流程，再决定服务拆分。
- 保留交易执行和 Gateway 的独立可靠性边界。
- 将未来微服务拆分建立在数据和负载证据上，而不是预想上。

## 影响

- 后端目录和代码必须体现逻辑模块边界。
- 不得因为同库部署而形成跨模块任意读写。
- 前端菜单结构不用于定义后端模块。
- 外部系统接入通过 Gateway／Adapter 隔离。
- 跨模块流程使用命令、查询和事件，而不是共享大型内部对象。
- 数据库、消息队列和部署拓扑仍需后续专项 ADR。

## 独立进程边界

以下能力可以在初期独立运行，但仍遵循统一领域和接口规范：

- 实盘交易执行工作进程。
- 交易所、经纪商、MT5 或 CTP Gateway。
- 高频行情接入。
- 损益重算和报表任务。
- 对账和批量导入任务。
- AI 分析任务。

独立进程不等于独立微服务；其部署、存储和通信方式根据实际需求确定。

## 未来拆分条件

只有出现以下情况之一时，才评审独立服务：

- 某模块需要明显独立扩缩容。
- 需要严格故障隔离或安全隔离。
- 发布节奏和生命周期显著不同。
- 单体部署成为性能或可用性瓶颈。
- 团队已经形成独立模块维护责任。
- 外部合规或部署要求强制隔离。

拆分前必须确认：

- 领域边界稳定。
- 稳定 ID 和接口契约已存在。
- 数据所有权明确。
- 事件和一致性方案可验证。
- 运维能力能够承担新增复杂度。

## 重新讨论条件

当真实后端建设、交易负载、团队规模或合规要求发生显著变化时，可以新增 ADR 替代本决策。

vn.py、数据库、消息队列和具体部署方式不由本 ADR 决定。
