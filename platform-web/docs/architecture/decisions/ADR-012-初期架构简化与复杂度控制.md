# ADR-012：初期架构简化与复杂度控制

状态：`accepted`  
日期：2026-07-18  
适用分支：`refactor/frontend-architecture-v6`

## 背景

当前平台已经形成较完整的产品、领域、数据、交易可靠性和运行时架构。继续无限细化对象、状态和基础设施，会导致文档复杂度高于实际开发能力，并增加初期实现成本。

平台当前目标不是一次性建设完整基金行政管理、复杂多账户清算、全量事件溯源或大型微服务体系，而是先落地一个可用、可测试、可逐步接入真实交易的内部投资管理平台。

## 决策

### 1. 总体原则

采用：

```text
必要正确性
+
最小可实现结构
+
明确扩展点
```

不采用：

```text
为未来所有可能性提前建模
```

### 2. 初期只保留三个工程主体

```text
platform-web
platform-backend
execution-runtime
```

不拆分微服务，不引入 Kubernetes，不为六个逻辑层分别建立服务。

### 3. Fund、Portfolio 与 Book 简化

- Fund、Portfolio、Book 保留为正式对象。
- 每个 Fund 默认一个 Portfolio。
- 每个 Portfolio 默认一个 Book。
- 默认对象由系统自动建立，普通用户无需配置。
- 暂不建设多 Book 划转、复杂合并核算、投资人、份额和申赎。

### 4. 初期核心业务对象

第一阶段优先实现：

- StrategyDefinition／StrategyVersion／StrategyInstance。
- Account。
- Instrument／InstrumentMapping／ContractSpecification。
- TradeCommand／ExecutionBatch／Order／Fill。
- Position／BalanceSnapshot。
- EconomicEvent／PnLResult。
- RiskDecision／ReconciliationResult／AuditEvent。

其余对象只有在真实业务流程需要时才实现。

### 5. 状态模型简化

领域内部可以保留必要的独立状态，但普通页面只展示聚合状态：

- 可用。
- 处理中。
- 受限。
- 异常。
- 未知。

页面不直接展示所有 Runtime、Gateway、同步和恢复子状态。详细状态只进入运维和故障诊断页面。

### 6. 数值模型简化

- API 和数据库金额、价格、数量继续使用 Decimal。
- 不要求为每个数值类型建立复杂类继承体系。
- 初期可以使用简单结构：`value + currency/unit`。
- 页面继续只接收已经格式化的 View Model。

### 7. 数据存储简化

初期默认：

- 一个关系型业务数据库。
- Runtime 本地可靠 Journal。
- 必要的对象存储用于文件和报表。

暂不默认引入：

- 多数据库分片。
- ClickHouse。
- Kafka。
- 完整 Event Sourcing。
- 独立数据湖。

是否增加 Redis、时序库或消息中间件，由实际性能和可靠性 PoC 决定。

### 8. Runtime 简化

初期 Runtime 只需要：

- Command 接收。
- 幂等处理。
- Gateway／Worker 管理。
- 外部订单提交与回报。
- 本地 Journal。
- 启动同步和基础恢复。

不提前实现复杂调度平台、动态集群编排和通用量化框架。

### 9. 文档控制

后续架构文档必须满足至少一个条件：

1. 直接约束近期开发。
2. 解决已确认的业务歧义。
3. 防止真实资金风险。
4. 为技术选型或 PoC 提供验收标准。

不满足以上条件的内容不继续展开。

## 影响

- 后续优先从文档收敛转向工程骨架、契约和 PoC。
- Instrument 等领域只设计近期必须字段。
- 默认 Fund／Portfolio／Book 对用户隐藏。
- 运维详细状态与普通业务状态分层展示。
- 暂停扩展完整基金行政管理和大型数据平台能力。

## 禁止事项

- 不因为架构文档存在就一次性实现全部对象。
- 不为尚未出现的多租户、跨区域和超高并发需求提前拆服务。
- 不把“未来可能需要”作为当前增加系统复杂度的唯一理由。
- 不牺牲订单幂等、结果未知、对账、审计和 Decimal 等必要金融正确性。

## 重新讨论条件

只有出现以下情况时才扩大架构：

- 多基金或多 Portfolio 已实际运营。
- 数据量或延迟已超过现有存储能力。
- 单体部署已形成明确故障或团队协作瓶颈。
- 正式建设基金 NAV、投资人和申赎系统。
- 真实交易 PoC 证明需要更复杂的消息或运行时基础设施。
