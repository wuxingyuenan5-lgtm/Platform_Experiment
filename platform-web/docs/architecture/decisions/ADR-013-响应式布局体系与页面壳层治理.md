# ADR-013：响应式布局体系与页面壳层治理

状态：`accepted`  
日期：2026-07-25  
适用工程：`platform-web`

## 1. 背景

当前平台页面在不同浏览器视口、屏幕比例、系统缩放和浏览器缩放下表现差异明显。常见问题包括：

- 页面在某一尺寸下正常，在另一尺寸下组件错位或互相覆盖。
- 固定底栏、浮层或局部面板遮挡正文。
- 表格、图表、筛选区和按钮组在中间宽度失效。
- 多层滚动容器导致内容看得到但无法到达。
- 页面背景、卡片边界和模块衔接不连续。
- 为某个页面或分辨率编写的 CSS 补丁影响其他页面。

已有 UI 和共享组件文档包含少量响应式原则，但没有统一定义：

- Application Shell 和 Page Shell 的布局所有权。
- 支持视口和缩放矩阵。
- 断点、Container Query 和内容重排规则。
- 纵向／横向滚动所有权。
- 固定、粘性和 Overlay 的层级治理。
- 可量化的跨视口验收标准。

继续逐页面修补会增加样式冲突和回归风险。

## 2. 决策

平台采用“页面壳层优先、容器约束驱动、组件自主重排”的响应式治理方式。

### 2.1 唯一架构主文档

`../frontend/responsive-layout-architecture.md` 成为响应式布局、视口支持、滚动、溢出、固定定位和组件重排规则的唯一主文档。

其他 UI、组件和页面文档只保留摘要和链接，不重复建立另一套断点或滚动规范。

### 2.2 桌面工作台优先

- 最小正式目标视口宽度为 `1280 CSS px`。
- 主要设计和验收区间为 `1366–1920 CSS px`。
- `2560px` 用于超宽屏验证。
- 小于 `1280px` 不要求移动端完整体验，但不得出现关键操作不可达、组件重叠或正文被遮挡。

### 2.3 页面壳层优先

后续实施顺序必须是：

```text
缺陷基线
→ Application Shell
→ Page Shell 与布局原语
→ 共享组件响应行为
→ 核心页面迁移
→ 自动化视觉回归
```

不得从随机业务页面开始，以大量局部媒体查询替代壳层治理。

### 2.4 滚动所有权

- 应用原则上只有一个主要纵向滚动容器。
- 超宽表格拥有局部横向滚动。
- 明确高度的日志、长列表、弹窗和抽屉可以拥有受控局部纵向滚动。
- 同一方向滚动不得由多个嵌套容器竞争。

### 2.5 断点与组件响应

- 全局媒体查询只负责 Application Shell 和 Page Shell 的离散结构变化。
- 可复用业务区块优先根据自身容器宽度响应。
- 组件必须声明最小尺寸、重排策略和局部滚动责任。
- 空间不足时优先换行、降列、上下重排、折叠或局部滚动，不无限压缩内容。

### 2.6 禁止分辨率补丁治理

以下方式不得作为默认正式方案：

- 针对单一分辨率增加专用 CSS。
- 使用绝对定位组织页面主布局。
- 通过负 margin、`overflow: hidden` 或任意高 `z-index` 掩盖结构问题。
- 多层页面分别计算 `100vh`。
- 每个业务页面建立独立断点体系。

受控例外必须在 PR 中说明适用范围、原因、回归测试和移除条件。

### 2.7 可量化验收

`../../quality/responsive-layout-acceptance.md` 统一定义：

- 测试视口、视口高度和缩放组合。
- 遮挡、碰撞、溢出和滚动缺陷等级。
- 页面和组件的通过条件。
- 后续截图回归和 Playwright 建设方向。

## 3. 理由

### 3.1 为什么不继续逐页修补

逐页修补无法解决共享壳层和滚动所有权问题，并会形成相互覆盖的媒体查询和选择器。

### 3.2 为什么不立即进行移动端重构

平台是高信息密度的研究和交易工作台。当前业务价值主要来自桌面场景，强制移动端优先会牺牲图表、表格和交易操作完整性，并显著扩大范围。

### 3.3 为什么需要 Container Query

组件可能处于主区、侧栏、分屏面板或折叠侧边栏后的不同容器中。只根据浏览器宽度判断，无法准确表达组件实际可用空间。

### 3.4 为什么先统一滚动

许多“底部被遮挡”和“内容滚不到”的问题来自多个滚动上下文及重复高度计算。滚动所有权是页面稳定性的基础，而不是视觉细节。

## 4. 结果

### 4.1 正面影响

- 设计师可以交付明确的结构变化规则，而不仅是单尺寸画布。
- 前端可以按壳层、布局原语和组件类别分阶段实施。
- 页面缺陷可以按照统一测试矩阵复现和验收。
- 媒体查询、滚动和定位的责任边界更清晰。
- 后续可以建立稳定的视觉回归基线。

### 4.2 成本

- 需要先审计现有 Application Shell、页面容器和滚动上下文。
- 某些当前“看起来正常”的页面在统一壳层后仍需重新迁移。
- 自动化截图和视觉回归需要独立建设。
- 旧页面的固定高度和绝对定位不能一次性全部移除，需要分批治理。

### 4.3 风险

- 将全平台响应式治理放入单个大 PR 会导致范围失控。
- 只新增布局组件但不迁移页面，会形成新旧两套体系。
- 为追求截图一致而过度固定尺寸，会再次制造中间宽度失效。

因此每个实施阶段必须使用独立 Issue、任务包和 PR。

## 5. 被否决的方案

### 5.1 只增加更多媒体查询

否决原因：无法解决布局所有权、滚动上下文和共享组件问题，且容易产生规则冲突。

### 5.2 统一缩放整个页面

否决原因：文字和交互区域会变小，无法保证可读性、可访问性和图表清晰度。

### 5.3 强制固定页面宽度

否决原因：会浪费宽屏空间，并在窄屏或侧边栏展开时产生横向溢出。

### 5.4 立即重写所有页面

否决原因：风险和改动面过大，难以回归，也不符合当前复杂度控制原则。

### 5.5 依赖 JavaScript 监听窗口宽度完成普通布局

否决原因：增加运行时复杂度和状态同步问题。普通布局应优先由 CSS Grid、Flex、媒体查询和 Container Query 完成。

## 6. 后续实施要求

后续 Issue 至少拆分为：

1. 响应式缺陷与截图基线审计。
2. Application Shell 和唯一主滚动治理。
3. Page Shell 与布局原语。
4. 共享工具栏、卡片、图表、表格和 Overlay 响应行为。
5. 核心交易／策略页面迁移。
6. 视觉回归自动化。

任何后续实现 PR 都必须说明：

- 覆盖的视口和高度。
- 滚动所有者是否变化。
- 是否新增固定／粘性定位。
- 组件最小宽高和重排策略。
- 截图或自动化验证结果。
