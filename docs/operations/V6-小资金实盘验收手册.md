# V6 小资金实盘验收手册

状态：`active / operational acceptance required`  
适用阶段：`V6 Phase 4C–4D`  
对应计划：`../planning/V6-Phase4C-受控实盘适配器.md`  
工程范围：`Issue #96 / PR #97`  
更新时间：`2026-07-25`

## 1. 目的

Bybit 与 MT5 的模拟环境不能完整复现实盘账户、成交、Funding、Swap、券商终端和网络行为，因此最终验收采用真实账户的小资金、最小仓位测试。

本手册把“小钱实盘测试”定义为受控运营验收，而不是普通策略交易：

```text
只读实盘
→ 影子核对
→ 最小仓位写入
→ 撤单／成交／事实导入
→ Kill Switch
→ 日终对账
```

任何阶段失败，立即回退到只读模式。

## 2. 不可突破的底线

- 实盘 Runtime 与 Simulation 使用不同数据库、Journal、Account ID 和凭证引用。
- 实盘凭证不进入代码、Git、Markdown、日志、截图或聊天记录。
- `liveWriteEnabled` 默认 false。
- Platform Kill Switch 与 Runtime Write Gate 必须同时放行，任何单点不能独立开启交易。
- Account、StrategyInstance 和 Symbol 必须全部位于精确 allowlist。
- 单笔与单日名义金额上限必须大于零且完成审批。
- 测试使用交易场所或经纪商允许的最小下单单位，不使用“为了方便观察”而放大的仓位。
- 一个测试窗口只允许一个 StrategyInstance 和一组明确标的。
- 不允许把 ACK 当成交，不允许在 `result_unknown` 时重下。
- 未完成日终对账前，不扩大资金、仓位、品种或自动化频率。

## 3. 当前临时验收限制

以下限制是 Issue #96 为第一轮真实账户验收设置的**临时限制**，不是最终产品能力上限。它们必须保留到 Issue #39 形成足够的真实验收证据，并通过独立 Issue／PR 逐项复审。

| 临时限制 | 当前值 | 目的 |
|---|---:|---|
| 单次跨所价差请求上限 | `1 troy ounce` | 把最坏单腿敞口限制在最小可监督范围 |
| Runtime 实际写入上限 | Bybit 与 MT5 均按实时合约乘数换算后不超过 `1 oz` | 防止绕过 Platform 直接放大仓位 |
| 活动生命周期数量 | 最多 `1` 个非 closed Exit Plan | 避免多仓位、Ticket 和退出条件混淆 |
| 未决状态后的新开仓 | 禁止 | `manual_intervention`、`result_unknown` 或未决 Batch 必须先处置 |
| 执行模式 | 仅 Market Open／Close 与价差触发的 Market TP／SL | Limit 执行尚未完成，不允许 UI 误路由 |
| 合约规格来源 | 每次写入前实时查询 Bybit 与 MT5 | Seed 规格不得作为实盘下单依据 |
| 数量映射 | Bybit 实际成交量必须精确映射到 MT5 min／step／contract size | 禁止四舍五入留下残余敞口 |
| 开仓后核对 | 必须核对 Bybit 与 MT5 真实 Position | Batch `hedged` 不能代替外部持仓证据 |
| 平仓后核对 | 两边真实 Position 必须归零 | Close Batch 成功不能代替外部归零证据 |
| 第二腿明确失败 | 只允许一次幂等 Bybit `reduceOnly` 回滚尝试 | 缩减已确认第一腿敞口 |
| 第二腿结果未知 | 禁止自动回滚、禁止盲目重试 | 避免 MT5 已成交后反向单造成双倍或反向敞口 |
| Live Write 默认值 | Platform=false，Runtime=false | 工程合并不等于实盘授权 |
| 自动退出监控默认值 | false | 受控主机验收前不自动触发写入 |

### 3.1 临时限制与永久安全原则的区别

以下原则即使未来删除 1 oz 或单仓限制，也必须永久保留：

- ACK 不等于 Fill。
- `result_unknown` 不得触发重复业务意图。
- Bybit、MT5 与 Platform 的外部身份必须可追溯。
- Close 必须使用 Bybit `reduceOnly` 和明确的 MT5 Position Ticket。
- Platform 与 Runtime 必须保持独立写入门禁。
- 合约规格、权限、仓位和余额查询失败时必须 fail-closed。
- 凭证不得进入 Git、Markdown、日志或测试。
- 扩仓必须通过独立审批、Issue、PR 和运营验收。

## 4. 阶段 0：静态配置

从 `execution-runtime/.env.live.example` 建立真实主机配置，但保持：

```text
VG_RUNTIME_LIVE_WRITE_ENABLED=false
VG_RUNTIME_LIVE_MAX_ORDER_NOTIONAL=0
VG_RUNTIME_LIVE_MAX_DAILY_NOTIONAL=0
VG_RUNTIME_LIVE_ACCEPTANCE_MAX_ORDER_QUANTITY=1
VG_RUNTIME_LIVE_ACCEPTANCE_MAX_POSITIONS_PER_SYMBOL=1
```

Platform 保持：

```text
VG_LIVE_TRADING_ENABLED=false
VG_CROSS_SPREAD_EXIT_MONITOR_ENABLED=false
VG_CROSS_SPREAD_ACCEPTANCE_MAX_QUANTITY_OZ=1
VG_CROSS_SPREAD_ACCEPTANCE_MAX_ACTIVE_PLANS=1
```

验收：

- [ ] `environment=live`。
- [ ] `gateway_name=bybit_mt5`。
- [ ] Bybit 与 MT5 Account ID 不重复、不歧义。
- [ ] Instrument Map 使用 Platform 正式 Instrument ID。
- [ ] Bybit `demo_mode=false`。
- [ ] Bybit API Key 是交易专用子账户 Key、绑定固定 IP、只开 Order 与 Position 所需权限。
- [ ] MT5 Terminal 路径、账户、Server 和 Magic Number 明确。
- [ ] MT5 `account_info.login` 与配置账号一致，Account／Terminal 均允许交易。
- [ ] Runtime 仅监听本机或受控内网。
- [ ] Journal 与 Platform Database 已备份并与 Simulation 隔离。

执行：

```powershell
.\scripts\live-readonly-preflight.ps1
```

该脚本只读，不会提交或撤销订单。

## 5. 阶段 1：只读实盘

保持所有写入门禁关闭，依次核对：

```http
GET /gateway/capabilities
GET /gateway/connectivity
GET /gateway/venue-readiness
GET /venue/orders?accountId=...&symbol=...&limit=50
GET /venue/orders/{externalOrderId}
GET /venue/fills?accountId=...
GET /venue/positions?accountId=...
GET /venue/balances?accountId=...
GET /venue/instruments/{symbol}?accountId=...
GET /venue/economic-events?accountId=...
```

### 5.1 无 Route 读单验收

Runtime 本地 `live_order_routes` 只能用于补充 Platform 身份，不能成为读取真实订单的前提。

必须验证：

- [ ] Runtime 启动前存在的订单可以按 External Order ID 查询。
- [ ] 人工创建的订单可以被 bounded order list 返回。
- [ ] Route Store 丢失或 Runtime 重启后，Bybit／MT5 外部订单仍可读取。
- [ ] 无 Platform Route 的订单标记为 `external_only`，使用合成 Platform Identity，不伪造完整映射。
- [ ] Bybit 订单同时查询 Active Orders 与 Order History。
- [ ] MT5 市价成交可以从 Order Ticket 或 Deal Ticket 反查到最终订单。
- [ ] MT5 Order Ticket、Deal Ticket、Position Ticket 不互相冒充。

Bybit 至少核对：

- Unified Account 身份。
- 现有订单与历史订单。
- Execution。
- Position。
- Wallet Balance。
- Funding 与 Fee。
- `minOrderQty`、`qtyStep`、`maxMktOrderQty` 和交易状态。
- API Key `readOnly`、IP 绑定和 ContractTrade 权限。

MT5 至少核对：

- Terminal 登录账户、Server 与账户币种。
- Order、Deal、Position。
- AccountInfo Balance、Equity、Margin 和 Free Margin。
- Deal 中的 Swap、Commission 和 Fee。
- Symbol 名称与券商后缀，例如 `XAUUSD+`。
- `trade_contract_size`、`volume_min`、`volume_step`、`volume_max`、`trade_mode` 和 `filling_mode`。

验收要求：

- [ ] 查询失败时返回明确错误，不返回伪造空列表或零余额。
- [ ] 外部 Account、Symbol、Order／Deal／Position Ticket 能映射到 Platform 对象或明确标记 `external_only`。
- [ ] 所有时间戳和币种可解释。
- [ ] 未映射事件进入 `skippedExternalIds`，不标记为完整导入。

## 6. 阶段 2：影子核对

仍保持写入关闭，将真实外部数据导入 Platform：

```http
POST /api/v1/ops/live-economic-events/import
```

并执行：

- External Order／Fill／Deal 与 Platform Order／Fill 核对。
- Venue Position 与 Formal Position 核对。
- Venue Balance 与 Formal NAV 输入核对。
- Funding、Swap、Fee 与 FinancialFact 核对。
- 重复导入测试，确认 factCount、Position 和 PnL 不重复变化。

验收要求：

- [ ] 连续多个核对周期没有未解释差异。
- [ ] `result_unknown` 可以通过 Venue 查询恢复。
- [ ] 外部结果冲突生成 Reconciliation Difference，不无痕覆盖本地事实。
- [ ] Formal Position／PnL 可以从不可变事实重建并保持一致。

## 7. 阶段 3：1 盎司受控实盘写入

只有完成阶段 0–2 后，才允许在单次人工监督窗口中开启写入。

开启前必须同时填写：

- 测试负责人。
- 开始与结束时间。
- Account ID。
- StrategyInstance ID。
- Symbol。
- 允许方向和订单类型。
- 单笔名义金额上限。
- 单日名义金额上限。
- 最大成交数量：`1 oz`。
- Kill Switch 操作人。
- Bybit `reduceOnly` 回滚路径。
- MT5 Position Ticket 人工平仓路径。

配置原则：

```text
liveMaxOrderNotional = 1 oz 测试所需的最小上限
liveMaxDailyNotional = 不高于少量重复测试所需的总上限
```

测试顺序：

1. 写入开启前再次查询实时合约规格与权限。
2. 确认 Bybit 与 MT5 目标 Symbol 均无已有持仓。
3. 以不超过 1 oz 的 Market Open 提交 Bybit 第一腿。
4. 只有 Bybit 终态成交后，按实际成交量精确计算 MT5 手数。
5. 查询 Bybit Fill、MT5 Deal 和两边 Position，确认方向与数量完全匹配。
6. 创建 Exit Plan 并绑定唯一 MT5 Position Ticket。
7. 通过人工 Market Close 或受控 TP／SL 触发一次平仓。
8. 查询两边 Position，确认目标仓位归零后才标记 closed。
9. 导入 FinancialFact，重建 Formal Position／PnL。
10. 开启 Kill Switch，确认所有新写入 fail-closed。
11. 关闭 Platform／Runtime Write Gate，并恢复名义金额上限为零。

## 8. 双腿失败处置验收

必须分别演练：

- 第一腿 ACK、未确认成交：不得提交第二腿。
- 第一腿终态部分成交：只对冲实际成交量，且必须精确满足 MT5 最小手数与步长。
- 第一腿成交、第二腿明确拒绝：只允许一次幂等 Bybit `reduceOnly` 回滚。
- 第一腿成交、第二腿超时或 `result_unknown`：禁止自动回滚和盲目重试，立即人工接管。
- Bybit 可用、MT5 不可用。
- MT5 Deal 已发生但本地事件丢失：必须通过 Deal／Order Ticket 读取恢复。
- Runtime 重启或 Route Store 丢失：必须依靠 Venue 事实恢复。
- 处置命令重复提交：不得产生第二个外部业务意图。
- 残留敞口超过阈值。

处置结果必须是以下明确状态之一：

- 撤销未成交腿。
- 反向平仓已成交腿并经外部仓位核对确认。
- 替代对冲完成并经外部仓位核对确认。
- 保持敞口并升级人工接管。

不能只停留在没有后续动作或责任人的 `manual_intervention`。

## 9. 日终验收

每个实盘测试日必须核对：

- Order。
- Fill／Deal。
- Position。
- Balance／Equity。
- Funding。
- Swap。
- Fee／Commission。
- FinancialFact。
- Formal PnL。
- Formal NAV。

差异分类至少包括：

- `missing_local`
- `missing_external`
- `quantity_mismatch`
- `price_mismatch`
- `currency_mismatch`
- `status_mismatch`

每个差异必须记录责任人、原因、处置和关闭时间。

## 10. 临时限制解除条件

只有 Issue #39 连续记录以下证据，才允许提出“删除或放宽临时限制”的新 Issue：

1. 多次真实最小仓位 Order、Fill／Deal、Position、Balance 读取成功。
2. Runtime 重启、Route Store 丢失后仍能恢复订单身份与最终状态。
3. Bybit 第一腿成交、MT5 明确失败时，幂等 `reduceOnly` 回滚演练成功。
4. MT5 `result_unknown`、断网和超时演练未产生重复或反向仓位。
5. 每次开仓后两边 Position 与实际成交量完全一致。
6. 每次平仓后两边目标 Position 均归零。
7. TP／SL 原子 Claim 与 exactly-once Market Close 演练通过。
8. 多个真实交易日无未解释 EOD Reconciliation Difference。
9. Kill Switch、Runtime 重启、备份恢复和人工接管流程通过。
10. 认证、RBAC、双人审批和生产密钥托管已落地。

### 10.1 解除流程

- 不允许通过环境变量直接静默提高限制。
- 必须新建独立 Issue、任务包、Issue 编号分支和 PR。
- PR 必须逐项列出支持证据、拟删除限制和仍保留的永久安全原则。
- 每次只放宽一个明确维度，例如数量、并发仓位或自动化，不得一次全部解除。
- 放宽后必须重新执行最小规模验收和 EOD 对账。
- 若证据不足，限制继续保留。

### 10.2 未来复审提醒

Issue #96 合并后，项目必须持续把 Issue #39 作为运营证据源。当上述证据成熟时，应主动提醒项目负责人创建“临时实盘限制复审”Issue，逐项删除已经不再必要的限制；未成熟时不得机械催促放宽。

## 11. 扩大范围的条件

通过小资金测试不等于正式 Live 发布获批。讨论增加资金、并发仓位或自动化前，除第 10 节外还必须满足：

- Funding、Swap、Fee 与外部账单一致。
- 双腿残留敞口处置通过。
- 监控、告警、备份和恢复演练通过。
- 私有 WebSocket 或现有 REST 确认路径的可靠性已有独立结论。
- Limit 执行若进入范围，必须有单独执行引擎设计与验收。
