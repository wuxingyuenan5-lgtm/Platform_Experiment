# 全球变量平台：稳定性与交易执行独立调研及优化方案

日期：2026-09-15。用途：独立研究、已批准优化方案及实施核验。第 2–10 节保留实施前证据与取舍；当前实施结果见第 11 节。长期运行和真实成交质量另以实际证据验收。

历史 V2 仅用于识别参考项目和恢复当时的考虑。当前需求、实际代码和故障证据优先；既不要求恢复旧方案，也不默认后续调整都正确。后续方案统一使用 Markdown。

历史材料为《全球变量平台-策略与底层架构优化方案-V2-2026-09-08》，其同目录 `report-source.md`（用户文档目录 `Codex/Reports/2026-09-08-strategy-architecture/v2/`） 可供对照。

## 1. 结论与建议

**需要继续优化，但当前最有依据的方向是减少重复读取、分清失败边界、收敛实际执行路径，并补齐安全恢复。立即整体更换交易框架，没有足够证据。**

用户要求的“正常平台长期运行”应落实为：页面持续可用，网络恢复后数据恢复，账户信息一致，已接受指令不依赖浏览器，服务故障后能核对原订单并恢复，维护不用反复猜测进程和仓位状态。

本次新增的关键证据是：**账户快照成功落库后，后续资金费归属计算失败，会把账户状态改为 `runtime_unavailable`。** 隔离探针同时观察到快照存在、最近成功时间存在、对外状态却为 Runtime 不可用。这个问题来自职责和错误分类混在一起，安装另一个交易 SDK 不会自动修复。

此外，Bybit 账户同步仍反复读取最近七天的订单和成交；MT5 完整读取与下单共享同一个串行 Worker；原生 Chase 接入后，适配器仍保留没有正常入口调用的旧追价方法。它们分别带来持续负载、对冲等待风险和额外维护面，值得优先处理。

建议顺序如下，均为本报告建议，尚未把新选择写成已批准的产品或部署规则：

1. 修正账户观测与财务计算的失败边界，测量并减少历史重复读取。
2. 收敛前端查询、日常发布与服务恢复，完成连续运行验收。
3. 用真实业务故障场景审查 Chase、部分成交和恢复；先明确需要替换的责任，再决定是否引入成熟订单引擎。
4. 每次引入组件必须停用其实际替代的旧路径。不能同时保留两个订单决策者、两个账户连接管理器或两套同用途页面缓存。

## 2. 本次核查方法与边界

核查覆盖 Web 会话与查询、Platform 账户同步和财务计算、Runtime Bybit/MT5 读取与执行、原生 Chase、Windows 看护和已存在的场景测试。读取了当前工作区、Git 已提交版本和差异，核对了实际安装的组件版本，并刷新公开官方资料。

当前工作区包含大量尚未分成独立提交的后续修改。因此可以确认某段代码现在做什么、已提交版本原来做什么；**不能仅凭现有 Git 历史为每一次修改确定当时理由或把所有故障归因于某一次调整。** 没有证据的因果关系保持未确认。

证据在本文分三类：

| 证据类型 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 当前调用路径与源码 | 某项责任、等待或错误传播确实存在 | 它一定触发了用户每次掉线 |
| 隔离探针与定向测试 | 指定输入和故障下的行为可复现 | 交易所实际成交速度、真实断线质量 |
| 官方接口与项目源码 | 组件提供的语义、限制及可借鉴机制 | 安装后自动适配本平台全部业务 |

本次没有修改交易业务代码、下真实订单、停止业务进程或安装候选引擎。已有修复和当前运行状态与本报告新提出的改造分别列明。

## 3. 当前系统真正的问题在哪里

### 3.1 账户同步状态包含了不属于连接故障的失败

`_sync_one_account()` 先取得并校验 Runtime 快照，在事务中保存余额、仓位、订单、成交和最近成功时间；事务提交后调用 `sync_funding_settlements()`。两者在同一个异常处理范围内，后者抛错也会进入账户同步失败分类。

本次用临时 SQLite、Fake Runtime 响应、禁止网络的探针注入资金费处理异常，得到：

```json
{
  "snapshotPersisted": true,
  "successTimestampPresent": true,
  "reportedSyncStatus": "runtime_unavailable",
  "externalConnections": 0
}
```

这证明当前错误提示可能把财务处理失败说成账户连接失败，不能据此断定每一次实际告警都是 Bybit/MT5 掉线。它也解释了为什么“快照似乎更新了，却仍提示同步中断”在代码上可能发生。

**建议：** 原生账户观测成功保持为观测成功；费用归属和历史收益处理分别记录自己的失败及重试进度。页面沿用现有资金、损益和订单区域，在受影响区域表达不完整，不增加用户不关心的后台证据表。仍需保留真实数据过期告警，不能把全部错误隐藏成正常。

代码：[账户同步与后续处理](../../platform-api/app/live_venue_snapshot_sync.py)。探针输出：[隔离证据](../../.codex/strategy-research-settlement-probe.json)。

### 3.2 首屏变轻了，不代表后台历史读取已经变轻

前端摘要 `includeDetails=false` 已减少页面返回的订单、成交和财务明细，这是有用的修复。但 Runtime 的 `get_account_snapshot()` 仍在每轮构造“当前时间向前七天”的订单、成交历史查询；多个市场类别各自分页，内部最多四线程。Platform 同步循环等待本轮结束后再睡眠 30 秒，所以真实更新间隔是“本轮耗时 + 30 秒”，不是固定每 30 秒必有新快照。

同一 Bybit 适配器又用一个锁串行执行不同账户的完整快照。这避免快照扇出竞争，具有现实理由；代价是一个账户的大量历史读取会推迟另一个账户。内部每个查询 Future 都需要成功，某个历史接口失败会使整份新快照返回失败，即便余额已经读到。

**建议：** 在现有账户观测链内分清三类工作：余额/仓位/保证金的当前观测、活动订单核对、历史成交及结算补齐。历史采用持久化进度和有界重叠区间，去重后推进进度；只有初始化、发现缺口或明确重建时回扫大窗口。不要先把锁删掉或无限加线程。

这里“分清工作”不要求拆成微服务或引入消息队列。不同读取有各自新鲜度，合成页面时不能伪装成同一时刻的原子快照。改造同时调整 owning contract，不能私自改变 `account-snapshot` 的完整性含义。

代码：[七天历史与内部并发](../../execution-runtime/app/bybit_live_adapter.py)、[同步调度](../../platform-api/app/live_venue_snapshot_sync.py)。

### 3.3 手写查询管理确实存在，但不是每一处都已证明有故障

`useCrossSpreadFinance`、`useCrossSpreadRecords` 仍管理自己的请求状态；执行页还每三秒刷新行情、退出计划和监控。Funding、通用账户和部分 Cross 监控已使用 TanStack Query。此前 Cross 手写 `inFlight` 在已提交版本就存在，本轮生命周期保护不能被说成造成所有问题的新设计。

现有统一 QueryClient 明确关闭查询重试、窗口聚焦刷新和重连刷新；所以“用了 TanStack”也不等于断线恢复已由它负责。是否开启某种读取恢复要明确配置并验收，而不是机械恢复所有默认值。[TanStack 查询默认行为](https://tanstack.dev/query/latest/docs/framework/vue/guides/important-defaults)

**建议：** 用已安装的查询库逐项接管同一服务端资源的请求、取消、失效和过期响应。查询键包含会话、策略、账户和摘要/详情范围；同一资源只保留一个查询入口。表单输入留在页面状态，不放进服务器缓存。读取可以做有限重试，交易提交继续禁止通用自动重试。

不能声称查询库自动跨浏览器标签页去重；本轮没有提出为此再建共享 Worker。应先证明当前单页切换、隐藏再显示和网络重连不会累积刷新任务。

代码：[QueryClient 配置](../../platform-web/src/api/platform/strategyQueries.ts)、[Cross 资金查询](../../platform-web/src/views/strategy/management/composables/useCrossSpreadFinance.ts)、[执行页轮询](../../platform-web/src/views/strategy/spread-carry/composables/useCrossVenueExecutionWorkspace.ts)。

### 3.4 MT5 的串行连接有必要，但历史查询可能挤占执行时间

固定账户对应固定 Terminal/Worker 是合理的连接边界，不能为了并发再次对同一终端随意初始化。现有 Worker 把所有调用放在同一把锁下，单次 IPC 等待最长 60 秒。完整账户读取与下单进入同一串行通道，因此慢历史读取可能让随后到来的对冲排队。

这是代码层面确认的等待关系；本轮没有在实盘中人为阻塞终端，也没有测得真实对冲因此延迟多少秒。

**建议：** 先缩短/分段历史工作、让已有 Worker 在调用之间优先处理执行及必要风险读取。正在 SDK 内执行的调用不能靠队列优先级强行抢占，也不能通过杀死可能正在下单的 Worker 消除等待。若仍不能满足实测对冲时限，再比较专用通路的代价。

代码：[MT5 串行调用](../../execution-runtime/app/mt5_account_worker.py)。官方 Python 包通过本机 Terminal 进行进程间通信；它不是可以直接换成 CCXT 的交易所接口。[MetaTrader5 Python API](https://www.mql5.com/en/docs/python_metatrader5)

### 3.5 原生 Chase 已替换追价入口，旧实现却未完整收敛

当前 `_submit_postonly_chase()` 直接调用原生 Chase；正常路径通过 REST 查询 strategy、子订单及逐笔成交。旧 `_execute_chase_action()`、`_place_postonly_child()`、`_private_source()` 仍在同一适配器中。

本次对 Runtime Python 源文件做 AST 调用搜索：旧执行方法只找到内部递归及其调用旧子单方法；私有流工厂方法未找到调用。再对照当前提交入口，支持将这些列为待移除的遗留路径。静态搜索不能完全排除外部动态调用，删除前仍应核对导出、测试与历史恢复依赖；不能把旧数据的恢复能力一并删除。

仓库虽然有 `bybit_private_stream.py`，不能因此宣称当前原生 Chase 已使用它获得及时成交推送。其过滤依据是旧 `orderLinkId` 前缀，也不能直接用于识别原生策略的子单。

**建议：** 原生 Chase 保留唯一追价权威。沿明确的 `strategyId → orderId → execId` 映射比较官方私有 strategy/order/execution 事件与 REST 补查。推送用于及时获知事件，持久化和补查用于恢复缺口；二者进入同一个去重处理路径，不各自决定对冲。

Bybit 官方已提供包含 Chase 的 strategy 私有主题，并分别提供订单和成交主题；当前 SDK 的具体封装仍需按安装版本验证，不能凭文档名称假设方法存在。[Strategy 主题](https://bybit-exchange.github.io/docs/v5/websocket/private/strategy)、[Execution 主题](https://bybit-exchange.github.io/docs/v5/websocket/private/execution)

代码：[原生入口](../../execution-runtime/app/bybit_fill_confirming_adapter.py)、[旧追价方法](../../execution-runtime/app/bybit_fill_confirming_adapter.py)。

### 3.6 “看护存在”与“实盘故障后能自动恢复”是两回事

当前脚本在实盘开关开启且检测到需要恢复的服务时，会阻止自动中断。这个保护避免随意杀掉执行进程，但也意味着现有看护无法自动修复这些实盘运行故障。代码中的该判断覆盖当轮恢复目标，不能简单说只有 Runtime 受限制。

建议把普通 Web 服务、API 业务调度和 Runtime 执行恢复分别处理。Web 独立重启不应默认中断交易；API/Runtime 恢复必须先加载原命令和场所证据，未知订单维持未知，不自动重提。最终应由成熟进程管理负责启停/日志/进程退出恢复，平台只保留必要的交易恢复准入。

WinSW/Windows 服务管理可承担普通进程包装；它能重启退出的进程，不会理解“订单是否成交”。其重启配置不可直接照抄示例中的主机重启行为。MT5 Terminal 在目标 Windows 服务会话下的可用性须单独验证。[WinSW 失败处理](https://github.com/winsw/winsw/blob/v3/docs/xml-config-file.md)

代码：[看护恢复保护](../../scripts/platform-watchdog.ps1)。

## 4. 成熟项目怎样用，哪些不能替我们解决

| 项目/组件 | 本平台具体用途 | 明确限制与本次建议 |
|---|---|---|
| pybit | Bybit 原生接口、签名、连接及官方 WebSocket | 已在使用。Bybit 专有 Chase/UTA 能力优先沿既有原生通道，不为“统一”增加第二个账户连接 |
| CCXT | 标准规格、公共行情；候选的标准历史读取/解析 | 已使用 4.5.78。库提供历史方法不等于替平台持久化进度、维护跨所订单或解决归属。私有历史先用同一批原始样本比较能删掉多少自研代码，再决定迁移 |
| TanStack Query | 服务端查询缓存、取消、失效与读取恢复 | 已安装 5.102.8，应优先复用。明确读取策略，停止被替代的页面定时器和 inFlight 管理 |
| vn.py / SpreadTrading | 主动/被动腿、价格公式与交易数量乘数、冻结可平量和事件组织 | 适合学习业务设计和场景。不能把净持仓模型直接当成 MT5 指定 Ticket 的替代，也不能默认所有网关在事件进入前已完成同样去重 |
| Hummingbot | 成交 ID 去重、订单状态与成交更新分离、执行器完成/停止的条件 | 适合事件处理比较。只复制一个类未必减少依赖；费用估值、账户模式和策略行为不能照搬 |
| NautilusTrader | 候选订单生命周期、恢复、对账及持仓映射引擎 | 值得保留为有明确范围的候选，不是当前页面不稳定的直接药方。先解决真实精度与 MT5/Chase 接入边界；不要拿预览版直接替换实盘核心 |
| Freqtrade | 长运行交易循环、活动订单/钱包同步与超时处理场景 | 当前需求是跨 Bybit/MT5 双腿协同，不是把策略改写成该框架的单套交易机器人。保留运作场景参考，不整体移植产品 |
| LEAN / QuantConnect | 重启状态、既有持仓、回测成交与真实成交差异的验收思路 | 回测可成交不证明 maker 限价在真实盘口可成交；本轮没有证明迁入其运行栈能减少 Windows MT5 适配成本 |
| Caddy、WinSW/Windows 服务、Prometheus | 固定构建入口、进程管理、历史指标 | Caddy 已接入；其余按实际部署和运行需求采用。已有指标导出不等于历史采集及告警已部署 |

CCXT 当前安装代码含 `fetch_my_trades`、`fetch_funding_history` 等标准能力，但平台的账户快照仍自己做分页与原生归一化。**保留必要的 Bybit 扩展不等于造轮子；同一能力包一层库后又保留全部旧逻辑，才没有减少维护责任。** 依据：[CCXT Bybit 4.5.78 源码](https://github.com/ccxt/ccxt/blob/v4.5.78/python/ccxt/bybit.py)。

vn.py 官方例子区分价差公式与交易乘数，强调主动腿成交后及时对冲。其本地 OmsEngine 把事件交给 converter，不能仅凭字典中按 trade ID 保存就推断重复事件不会再次进入下游。应核对 gateway 到 converter 的完整路径，不能把成熟项目当作无条件正确的黑盒。[SpreadTrading 官方说明](https://www.vnpy.com/docs/cn/community/app/spread_trading.html)、本地 OmsEngine（参考代码库 `量化平台GitHub项目研究/vnpy-master/vnpy/trader/engine.py`）

Hummingbot 的 `update_with_trade_update` 在累计成交前检查 trade ID，这是可以直接变成本平台验收场景的做法。它的费用转换及序列化还有自己的假设，因此参考范围以事件机制为主。[Hummingbot 2.16.0 InFlightOrder](https://github.com/hummingbot/hummingbot/blob/v2.16.0/hummingbot/core/data_type/in_flight_order.py)

Freqtrade 和 LEAN 的价值主要在长期运行及实盘语义比较；本报告没有完成它们的 MT5 适配试验，也不作“它们完全不支持”的无证据断言。[Freqtrade 运行说明](https://www.freqtrade.io/en/stable/bot-basics/)、[LEAN 实盘差异与重启](https://www.quantconnect.com/docs/v2/writing-algorithms/live-trading/reconciliation)

## 5. 对旧 V2 和后续改动的独立判断

| 旧思路或后续调整 | 本次判断 |
|---|---|
| 成熟组件承担通用责任 | 保留，但以删减实际维护责任为验收，不能以依赖清单为验收 |
| 先完成引擎选择，再推进其他优化 | 对当前已复现的读取和运维问题不合适；这些修复不应等待引擎试验 |
| CCXT 应接管更多标准读取 | 方向可比较，不自动要求迁移。单一 Bybit 原生能力若更清晰，允许保留；尤其不能改变原币、订单 ID 和缺失字段语义 |
| Nautilus 精度不符，停止旧试验 | 对旧 Windows 1.231.0 候选有依据。不能扩大成自研更可靠或所有版本均不适配 |
| 为拒绝引擎要求所有内部 Money 保留任意原始小数 | 需重新区分“原始财务事实无损”和“执行引擎按品种精度表示”。不允许丢失金融边界；也不应强迫候选内部估值取代平台账务，再因其币种舍入淘汰整个组件。真实执行精度不符仍应直接拒绝 |
| 认证数据库等待移出事件循环 | 有复现及定向验证，保留；不能因为是局部修复就一律叫补丁 |
| 完整账户快照串行化 | 有抑制竞争的价值；后续应减少完整扫描及长占用，不能无限叠加锁 |
| 原生 Chase 取代本地追价 | 符合 Owner 的已确认意图；目前遗留代码和终态后才释放对冲仍须收敛、评估 |
| 自动扩大交易规则页面、展示内部权限证据 | 不符合 Owner 已明确的使用体验，不纳入新方案；保持原简表，只显示用户有用的时段与限制 |

旧 Nautilus 探针确实关闭了 reconciliation，并使用 Mock Client；这并不使精度测试失效，但它没有证明外部重启恢复。重新比较要先给出实际品种/金额精度需求，分别验证命令、成交回执、引擎内部数值与正式财务事实。

截至本次查阅，Nautilus latest 文档针对 2.x 预览，普通安装仍可能得到 1.x，API 不同；官方明确不建议 release candidate 控制真实资金。latest 的官方高精度 wheel 说明也不能倒推旧版 Windows 试验错误。因此当前不建议为解决不稳定直接升级为 2.x。[官方安装与版本说明](https://nautilustrader.io/docs/latest/getting_started/installation/)

候选订单引擎只有在相同输入下正确处理原身份、重复回报、取消竞争和恢复，且能停止旧状态机责任时才值得切换。其 NETTING/HEDGING 映射还须验证不会丢失 MT5 Ticket。[Nautilus 执行与持仓映射](https://nautilustrader.io/docs/latest/concepts/execution/)

## 6. 具体场景：价差限价与两腿执行

### 6.1 触发条件、保护条件与真实成交价分开

按 Bybit 买、MT5 卖的方向，可观察的当前双边成交价差为 `Bybit Ask - MT5 Bid`；希望越低越好。假设触发值为 -10、不利容忍为 5，则观察值劣于 -5 时停止继续追逐、撤销未成交余量。

反向 Bybit 卖、MT5 买，使用 `Bybit Bid - MT5 Ask`，希望越高越好；若目标为 T，不利边界为 `T - 5`。具体开/平仓通过两腿买卖方向映射，不能所有场景套同一个不等号。

这里的 5 仅沿用讨论示例，作为参数，不是新写死规则。实际已实现价差必须用两边成交价、实际数量及正确单位计算。USD 与 USDT 汇率和手续费另按既有口径核算，不能当作完全同币。

原生 Chase 的 Bybit 限价/最大追逐价格只约束 Bybit 一腿，不能跟随 MT5 价格自动保证跨所最终价差。动态跨所保护仍有必要。Bybit 说明达到最大追逐距离后订单可能停在该价格，而不是自动撤销；平台不能把“停止追价”当作“没有活动订单”。[Bybit Chase 规则](https://www.bybit.com/en/help-center/article/Chase-Order)

### 6.2 部分成交后怎样及时对冲

当前实现发现已成交数量能完整映射为 MT5 最小量/步长后，停止余下 Chase，等待策略与子单终态、成交覆盖一致，再返回最终成交量。它避免用不完整数量提前结算，但不是每次 Bybit 成交后立刻发送 MT5。

应比较两种执行机制，而不是直接拆掉现有终态保护：

| 机制 | 收益 | 代价及验收重点 |
|---|---|---|
| 当前“停止余单、确认终态、对冲实际量” | 流程较简单，数量终态清晰 | 等待 REST/撤单终态期间有裸露；可能提早结束原计划剩余量，需要清楚反馈 |
| “确认增量成交、按可对冲步长释放、最终补核”候选 | 可缩短已成交部分等待 | 必须持久化已确认量、已派发/已完成对冲量；撤单晚成交、重启、余量不足最小步长均不能多对冲 |

候选规则应基于 `已确认成交 - 已保留或已派发对冲量`，按 MT5 数量步长向下形成可执行部分，并校验最小量。不能每收到累计成交就把累计值再下单一次。若 MT5 每个最小合法订单对应 1 oz，而 Bybit 仅成交 0.4 oz，就不能发送非法的 0.004 lot，也不能假装已配平。

测试需覆盖累计 0.4 → 1.0 → 1.4 oz、重复 1.0、撤单时再成交、MT5 回执未知等情形。上述数量只是示例，执行时必须使用账户品种的真实规格。最终选择应比较等待时间和残余风险，不单比较 maker 费率。

### 6.3 撤单、止盈止损与极端行情

撤单只能作用于未成交部分；已经成交无法“取消成交”。Bybit 官方指出取消与成交同时发生时可能收到两条 Filled 回报，因此对冲计量应以独立成交身份去重，订单终态不能直接充当新增成交量。[Bybit Order 事件](https://bybit-exchange.github.io/docs/v5/websocket/private/order)

保留 Owner 要求的两种选择：触发后市价执行、触发后原生 Chase。Chase 用于止损不保证及时成交；本报告不擅自增加自动转市价、追加数量或单边强平策略。应明确显示触发、已成交、未成交/已撤余量和待核对结果，而不是只有一句“执行失败”。

实际效果至少记录：触发时双边盘口、Bybit 各笔成交/费用、MT5 各笔成交/费用、首次成交到对冲派发/成交的间隔、最大未配平量、余量终态、最终价差。没有这些证据，不能宣称 Chase 已比市价或旧追价更优。

## 7. 具体场景：休市、重启、共享账户和费用

| 场景 | 预期结果与需要验证的边界 |
|---|---|
| MT5 休市，Bybit 报价剧烈变化 | 继续观察价差与风险；不因单边极端价差启动正常双腿指令。不能把剩余旧 Tick 当当前可成交报价 |
| MT5 开/收盘前后 N 分钟 | 按 Owner 已明确规则暂停自动 TP/SL，真实可交易时保留人工开平；N 可配置。页面简表显示时段、缓冲说明与异常状态 |
| 节假日、临时早收、夏冬令时 | 按实际经纪商、品种和服务器时区核对；不能用北京时间经验值或通用外汇日历覆盖经纪商规则 |
| 活动 Chase 期间 MT5 断线/休市 | 停止继续扩大 Bybit 未对冲量，核对原策略和已成交；残余风险明确保留，不伪造双腿完成 |
| Bybit 接受 create，但响应丢失 | 原业务意图保持未知，查原策略/订单。若 API 缺可可靠匹配的客户端身份，不能仅按同品种同方向猜测，更不能自动重新 create |
| Bybit 已成交，MT5 提交前 API/Runtime 停止 | 从持久化意图和场所证据恢复，按实际差额继续原意图；是否能自动继续由既有权限及恢复边界控制 |
| MT5 已接受，但本地未收到回执 | 先查指定账户、订单、成交、Ticket；超时不等于未成交。恢复不能多发同一腿 |
| Funding、Cross、外部手工单共享账户 | 原生持仓全量可见；策略归属按明确身份/事实处理。没有归属的单腿仍可见，不能根据有无 Exit Plan 让它消失 |
| 部分平仓与后到资金费/库存费 | 开平组和剩余量不被后到事件改变；费用原币归属、重复同步不重复记账；缺少分摊依据保留待核对 |
| 人工平仓与后台 TP 同时竞争 | 对同一可平数量只领取一次；另一路应读到已领取/已处理结果，不能各自下完整双腿 |
| 同一 Bybit 账户、多组同时申请相同品种方向的 Chase | 核对场所策略数量限制及已有活动策略；拒绝冲突时不取消其他组的策略，也不能自动换成市价或本地追价 |

Bybit 帮助文档说明同品种同方向 Chase 有数量限制，因此多组并行不能只按平台内部“组 ID 不同”就假设场所允许。具体 API 账户适用条件在接入验收时核对。[Chase 使用限制](https://www.bybit.com/en/help-center/article/Chase-Order)

MT5 的周交易时段 API `SymbolInfoSessionTrade` 在 MQL5 端存在；Python 官方函数目录未提供同名调用。当前配置日历加日期覆盖是合理折中，但“支持覆盖配置”不代表已经自动取得节假日变更。如果需要直接同步 Terminal 规格，可评估一个只读 MQL5 导出接口；只有它确实减少错误时才引入，不能顺便新建完整 MT5 网关。[MQL5 时段接口](https://www.mql5.com/en/docs/marketinformation/symbolinfosessiontrade)、[Python 函数目录](https://www.mql5.com/en/docs/python_metatrader5)

服务器时钟、原生 Tick 时间和本地观察时间要分别保存。`TimeCurrent` 是最近接收报价的服务器时间，休市时不能拿它当永远持续更新的实时时钟。[MQL5 TimeCurrent](https://www.mql5.com/en/docs/dateandtime/timecurrent)

## 8. “长期正常运行”应怎样落地

### 8.1 登录体验与后台运行

当前配置默认空闲期限 30 分钟、绝对期限 12 小时；空闲按成功认证请求更新，不是单纯统计鼠标活动。后台策略不替浏览器续期。关闭页面、会话到期与后台已接受计划的生命周期必须分开。

正常使用中因网络抖动、慢查询或服务短时不可达而反复清空身份是缺陷，应修复。真正到期后的再次登录是会话产品规则，不等于平台停机。后续会话体验应做到保留返回位置、清楚说明真实过期原因，并保持原计划可查；不能用永不过期、后台伪造活跃或自动重发交易掩盖连接问题。本报告不把默认 30 分钟固化为 Owner 已接受的最终体验。

### 8.2 主机、连接和恢复

本轮已有读证据显示 Windows 时间服务未启动、当前进程无管理员权限。系统时间维护应交给 Windows 标准服务，不再写一个平台自有校时守护进程。Bybit 签名偏移校准可以处理接口时差，但不应代替宿主校时；系统校时完成后仍应核对原生 MT5 时间语义。[Bybit 签名要求](https://bybit-exchange.github.io/docs/v5/guide)、[Windows 时间服务](https://learn.microsoft.com/en-us/windows-server/networking/windows-time-service/windows-time-service-tools-and-settings)

进程恢复的顺序应是：启动 → 加载持久化工作 → 核对账户与场所 → 恢复已知状态 → 放行允许的动作。只让进程重新监听端口，不算恢复完成。真实结果未知时可以需要人工核对，普通读取断线则应自动重连；两者不能共用一条“全部自动重试”。

数据库暂不建议整体迁移。先量出写事务时间、锁等待、每轮处理行数及读查询成本。当前 SQLite 连接封装采用同步连接，之前移出事件循环的修复有必要；在没有并发证据前直接换 PostgreSQL、队列或微服务会扩大变量。若优化后确有锁竞争，再以副本验证 WAL/事务组织或数据库选择，不能在线随意切换。

### 8.3 连续运行的建议验收

下列是建议验收目标，不是已完成结果，也不保证未来绝不故障：

| 验收 | 方法与通过条件 |
|---|---|
| 读取随数据增长 | 固定同一设备和账户夹具，比较 1 倍/10 倍历史量；当前余额仓位读取不随全历史量线性恶化，历史接口按分页或增量工作 |
| 页面连续使用 | 打开、切页、隐藏、恢复、短断网后重连；无身份误清理，无重复提交，刷新任务数量回到稳定值 |
| 首屏与接口性能 | 建议先以热摘要 p95 ≤ 1 秒、冷首屏 ≤ 3 秒为优化目标；分别统计端到端页面和 API。此前冷摘要 2–3.5 秒说明冷启动仍有工作，不能只报热结果 |
| 72 小时基础运行 | 固定发布版本；记录错误、资源、请求量、数据年龄和重连结果。无不可解释的会话撤销、监控停止或持续内存/线程增长；不因测试生成交易 |
| 跨完整交易周 | 覆盖实际日间休市、周末及恢复；夏冬令时和节假日使用离线日期场景补测，不能等待自然发生才发现算法错误 |
| 进程/网络故障 | 在隔离环境注入已接受未回执、第一腿完成、第二腿回执丢失、数据库等待；恢复后同意图不多成交，当前读状态准确 |
| 实盘成交质量 | 只利用 Owner 明确授权的具体订单收集证据；maker 比例、最终价差与对冲等待实际测量，不用 mock 成交替代 |

现有 Prometheus 是指标导出，运维文档明确并未因此安装历史采集服务。长期验收应使用成熟采集工具或现有运行证据机制，记录真实曲线和失败时刻；不为显示“监控已启用”再建一套平行状态数据库。[现有运维边界](../../docs/operations/PRODUCTION.md)

## 9. 可执行的改造顺序与停止条件

| 工作 | 改什么、复用什么 | 验收后停止维护什么 |
|---|---|---|
| 第一批：观测正确性 | 修复快照成功/费用归属失败被混报；分清数据年龄和财务完整性，沿用现有展示区域 | 后续财务错误覆盖整个账户连接状态的路径 |
| 第二批：读取成本 | 当前状态与历史补齐分清，历史持久化进度与有界重叠；对标准历史比较 CCXT 与现有 pybit，不先决定全部迁移 | 每轮无条件七天历史回扫、同一事实重复归一化；保留明确的补缺/重建入口 |
| 第三批：前端与运行 | 复用 TanStack；独立固定构建；成熟进程管理处理普通服务，交易恢复保留身份核验 | 被接管资源的手写轮询/缓存、被进程管理接管的通用 PID/启停实现 |
| 第四批：执行场景 | 原生 Chase 唯一追价；比较事件推送+补查、当前终态对冲与增量对冲；复用既有 Journal 与身份链 | 已无入口的旧追价动作和不再适用的私有流接线，不删历史恢复数据 |
| 第五批：是否替换订单内核 | 仅在前述比较证明现有状态机仍是主要成本时，对明确候选/版本完成同一场景试验 | 若采用候选，停止该范围旧 OMS；若不采用，记录具体不适配点而非泛称“自研更灵活” |

前三批并不依赖订单引擎选型；第四批中生命周期变化则不应先大改一遍，随后又为候选引擎重写一遍。优先完成共同的场景输入与结果核对，再选对应实现。

每批只交付一种可说明的业务结果，验证后再改下一批。版本应记录实际依赖、构建和可回滚产物。本次读取到 Runtime 安装版本包括 CCXT 4.5.78、pybit 5.17.0、MetaTrader5 5.0.6090；服务 pyproject 仍有多个范围依赖，后续发布需验证可重复安装。此项是运行建议，不要求现在整体升级依赖。

新组件若不能减少重复责任、需要大规模核心 fork、损失原始身份/精度、引入另一个真实下单者，或不能通过同一故障场景，应停止接入。修复若已达到相关行为和性能目标，也应停止扩大重构范围，不把每个局部问题升级成全平台重写。

## 10. 防止再次“改着改着变了”的具体约束

这些是建议的工作方式，不增加新的审批系统或任务文档：

- 修改前明确本次用户可见结果，例如“账户正常但费用待核对”，不要只写“重构同步层”。
- 已确认的交易表格、开平选择、N 分钟自动保护、人工操作和共享账户归属保持为验收输入。技术替换不能附带改变它们。
- 一次只改变一个主要变量。不要同批更换数据库、会话政策、交易引擎和页面布局。
- 对代码区分正在使用、只用于旧记录恢复、真正无调用的遗留实现；处理时说明哪一项责任退出，而不是按文件名大批删除。
- 交易测试检查实际适配器/Runtime 接线、原命令身份和最终数量；仅验证旧 reducer 或 mock 页面不够。新库接入要验证替代路径确实被调用。
- 发布后核对用户入口实际加载的新构建和服务版本。单元测试通过与代码已在业务服务运行分别记录。
