# 前端访问权限矩阵

状态：`active contract`

本矩阵同时约束菜单展示、直接 URL 访问、浏览器 API 权限和个人账号数据范围。角色权限与账户绑定共同决定正常业务权限，Live Write、Kill Switch 和交易风控继续独立生效。

## 角色权限

| 角色 | 正式业务页面 | 风险管理 | 用户管理 | 本人个人账号 | 业务写入 |
|---|---|---|---|---|---|
| CEO | 全部 | 允许 | 允许 | 允许 | 产品权限允许，但仍受全部正式安全门禁约束 |
| 技术负责人 | 接近完整 | 允许 | 允许 | 允许 | 产品权限允许，但仍受全部正式安全门禁约束 |
| 员工 | 全部正式业务页面只读 | 只读 | 用户列表只读 | 允许 | 仅本人密码、头像、设备和会话等自助范围；不得修改业务数据或其他账号 |
| 会员 | 规定范围内正式业务页面只读 | 禁止 | 禁止 | 必须允许 | 仅当前登录会员本人的自助范围；不得修改业务数据或其他账号 |

## Financial AI

Financial AI 不新建角色体系。已授予 `platform:read` 的主体可查看配置状态、读取研究数据、检查连接并运行普通分析。只有已授予 `settings.write` 的 CEO、技术负责人或 API-Key `admin` 可保存、替换或清除服务端共享 AI 配置。员工、会员/Guest、viewer 和其他只读主体不得修改机器级 API Key。

## 会员个人账号口径

会员不是“无个人账号”角色。正确边界为：

- 菜单必须显示个人账号；
- `/account/index` 必须可访问；
- 页面数据必须绑定当前登录会员本人；
- URL 中的 ID、Query 或 Path 参数不得改变本人数据范围；
- API 不得读取其他用户、用户列表或内部组织数据；
- `/risk` 与 `/risk/users` 不显示且直接访问返回 403 页面；
- 风险管理和用户管理菜单不得显示。

三个会员演示账号 `e2e_vip_1`、`e2e_vip_2`、`e2e_vip_3` 必须分别显示自己的账号资料，不得复用或串读其他会员、员工、技术负责人或 CEO 的身份数据。

## 其他角色个人账号

CEO、技术负责人和三个员工演示账号同时保留：

- 风险管理访问；
- 用户管理的相应读写或只读权限；
- `/account/index` 本人个人账号访问；
- 本人密码、头像、设备和会话等获准自助能力。

## 双重访问控制

前端菜单过滤不是唯一授权边界。正式验收必须同时覆盖：

1. 菜单项是否按角色显示；
2. 直接 URL 是否按权限进入页面或 403；
3. API 是否验证权限点和目标数据范围；
4. 本人个人账号是否始终绑定当前认证主体；
5. 非本人 ID、Query、Path 与 API 请求是否被拒绝或保持本人范围。

## Live Write 边界

2026-09-09 起，CEO 的有效浏览器登录会话可以通过 CSRF 发起 Cross/Funding 正常交易。技术负责人、员工和会员不能发起这两个策略的交易，API-Key admin 也不自动等同 CEO。具体授权由 [认证授权合同](AUTHORIZATION.md) 统一拥有。

上述策略批次的风险处置沿用同一 CEO 边界；CEO 具有对应风险管理权限，其他主体不能通过 RiskAction 间接发起策略交易。

单笔订单的 Runtime Journal 恢复 `reconcile` 与原生查询/事实回补 `venue-reconcile` 归现有 `reconciliation:review`；CEO 已有该权限，浏览器请求仍校验 CSRF。两者不创建 Venue 订单，不等同于订单缺失接受、风险平仓或任意管理写权限。

正常开平仓不需要临时 LiveTradingSession、双人验收审批、固定小额额度、限定时间窗口或旧 Strategy/Symbol 白名单。账户交易绑定、真实总开关、Kill Switch、对账、数量精度、可用保证金和执行安全仍须通过。开发身份不能在真实写入开启时提交写请求。
