# 产品平台工程标准

状态：`active`

适用基线：Platform `0.9.1`

适用范围：基金投研、策略、交易、风险、账户、资管、会计、运营与管理功能。

本标准的目标不是把平台改造成复杂的企业级技术体系，而是在初创阶段保持结构简单、业务边界清楚、交易安全可控，并让后续升级、替换数据源和扩展模块保持低成本。

## 1. 总体架构

平台保持以下运行拓扑：

```text
admin-risk（Vue 3 + TypeScript）
        ↓ HTTP / WebSocket
platform-backend（Python 模块化单体）
        ↓ 版本化执行契约
execution-runtime（交易所与券商外部副作用）
        ↓
外部 Venue / Broker
```

永久边界：

- 前端只调用 Platform API，不直接访问数据库、交易所 SDK 或第三方研究数据源。
- Platform Backend 承担业务规则、风险、投研、账户、编排、查询和正式会计，不导入 Venue SDK。
- Execution Runtime 只负责外部执行、外部读取、幂等、Journal 和规范化结果，不拥有 Platform 内部业务规则。
- 研究行情不得自动成为真实下单、风险或对账的权威行情。
- 真实交易、订单、成交、仓位、会计与审计语义不得被普通投研页面改动。

初创阶段不拆全面微服务。只有模块出现独立扩缩容、故障隔离、发布节奏或团队所有权需求时，才评估服务化。

## 2. 业务域

平台按业务边界组织，而不是按页面或技术名词组织：

1. 投研域：宏观、A 股、美股、商品、加密、全球市场、研报、事件概率和研究数据。
2. 策略域：策略定义、参数、信号、回测、模拟、版本和运行实例。
3. 交易与执行域：订单意图、风险前置检查、提交、撤单、成交、生命周期和外部适配。
4. 账户与组合域：基金、账户、子账户、现金、仓位、净值、配置和风险暴露。
5. 会计与绩效域：FinancialFact、已实现与未实现损益、费用、资金费、归因、NAV 和报表。
6. 管理与治理域：用户、角色、权限、审批、审计、数据质量、来源、发布和系统运行状态。

业务域是模块边界，不等于独立服务。

## 3. 前端标准

### 3.1 页面职责

页面组件只负责：

- 页面级布局和模块顺序；
- 路由参数和页面级筛选；
- 少量跨模块协调；
- 子组件装配。

页面组件不得长期内联：

- 大量表格行和演示数据；
- 外部 API 调用；
- 复杂指标计算；
- 多模块加载和错误状态实现；
- 可独立测试和复用的业务区块。

### 3.2 前端分工

```text
page / index.vue        页面编排
components/             UI 与用户交互
composables/            状态、并发、请求和生命周期
mappers/                API DTO → UI View Model
types/                  页面与 API 类型
fixtures/               演示、测试或显式降级数据
api/                    Platform API Client
```

不得为了目录对称建立空层。一个职责出现第二个使用点，或已经有独立加载、状态、交互和验收口径时，再拆为单独模块。

### 3.3 通用组件与市场差异

采用“通用基础组件 + 市场专属配置 + 少量专属模块”。

禁止把一个通用组件扩展成大量布尔开关，例如：

```text
showVol20 / showTurnover / showEmotion / hide4h / showSw2 / showFunding ...
```

当市场之间的字段、交互或业务区块明显不同，应通过每市场列配置、slot 或独立区块实现，不得强迫所有市场保持完全相同结构。

### 3.4 UI 设计规范

所有产品页复用现有平台视觉，不复制外部参考项目的页面、组件、配色、布局、Tailwind 类或设计语言。

统一规则：

- 使用平台主题变量，不在业务页面散落新颜色值。
- 名称和文字列左对齐，数值和金额右对齐。
- 空值统一显示 `—`。
- 金额按元、万、亿、万亿统一格式化。
- 百分比精度按业务口径统一，不由各页面随意决定。
- 数据模块显示真实来源、来源时间和平台抓取时间。
- 加载、正常、部分缺失、暂无数据、过期和错误使用统一状态。
- 外层模块已有标题时，内部组件不得重复标题。
- 产品页面不得展示工程解释、验收说明、调试快照或架构术语。
- 展开、折叠、抽屉、弹窗、筛选器和导出按钮使用同一交互规范。

### 3.5 数据状态

研究数据模块统一使用：

```text
loading
ready
partial
no_data
stale
error
```

单模块失败不得导致整页白屏。多个请求并行时，旧请求不得覆盖用户后续查询的结果。

## 4. Platform Backend 标准

### 4.1 模块化单体

Platform Backend 保持一个部署单元，但内部按业务模块分离。推荐职责：

```text
routes / API            参数校验、鉴权、调用 Service、HTTP 错误映射
schemas / DTO           稳定公开契约
service                 用例编排、并发、业务计算、部分失败处理
policy / domain         纯规则和确定性计算
repository              SQL、DDL、事务和持久化映射
provider                外部研究数据源和第三方只读接口适配
```

简单功能不必强制拥有全部层。出现业务规则、多个调用方、多个数据源或持久化语义后，再建立对应边界。

### 4.2 Route 规则

Route 不得：

- 直接请求第三方网站；
- 编写指标公式和行业聚合；
- 直接写复杂 SQL；
- 承担缓存和降级策略；
- 调用 Venue SDK。

### 4.3 Service 规则

Service 负责：

- 多 Provider 并发；
- 业务计算和结果聚合；
- 部分失败与数据质量；
- 统一 DTO 输出；
- 用例级权限和业务检查。

### 4.4 Provider 规则

每个 Provider 负责一个明确外部来源或同类接口：

- 超时、限流、重试和请求头；
- 外部字段解析；
- 转换成平台内部模型；
- 标注实际原始来源；
- 明确空数据、被限流、接口变化和解析失败。

Provider 不得返回要求前端理解的供应商字段，例如 `f2`、`f3`、`RZYE`。必须转换为 `price`、`change_pct`、`margin_balance` 等平台字段。

## 5. 投研数据标准

### 5.1 请求链路

```text
Vue
  → Platform Research API
  → Research Service
  → Provider Adapter
  → 免费公开数据源
```

不得：

- 前端直连腾讯、东方财富、同花顺、巨潮等来源；
- 将 GitHub 参考仓库当作运行时数据 API；
- 运行第二套复制来的 FastAPI 后端；
- 将 AKShare 等封装库名称显示为实际数据来源。

### 5.2 吸收外部参考项目

允许吸收：

- 数据请求和解析逻辑；
- 固定指标公式；
- 并发、缓存、限流和降级经验；
- 数据覆盖范围；
- 客观功能交互。

禁止直接复制：

- 整套后端应用结构；
- React 页面和组件；
- UI 样式和布局；
- AI Agent、对话和研究流程；
- 与平台现有契约冲突的字段和持久化方式。

代码进入平台后必须由平台模块拥有，并遵守平台测试、来源、错误和缓存规范。

### 5.3 数据元信息

每份外部研究数据至少携带：

```text
source
source_timestamp
fetched_at
status
is_stale
error_code
```

来源必须显示实际上游，例如腾讯财经、巨潮资讯或东方财富，不显示参考 GitHub 仓库。

### 5.4 缓存和最后有效数据

- 实时行情使用秒级或分钟级 TTL。
- 财务、估值分位、公告和事件数据按变化频率设置 TTL。
- 空拉取和解析异常不得覆盖已有有效数据。
- 使用最后一份有效结果时必须标注数据时间和 `stale` 状态。
- Redis 只用于缓存、锁、限流和短期任务状态，不作为正式账本。

### 5.5 分类与行情分离

行业分类是独立主数据。A 股板块统一使用申万分类：

```text
security_code
sw_l1_code / sw_l1_name
sw_l2_code / sw_l2_name
classification_version
effective_from / effective_to
```

行情和资金流可以来自免费公开来源，但必须通过证券代码关联申万分类后再聚合。不得使用供应商行业名称作为申万行业键。

未匹配股票不得静默丢弃，必须进入数据质量统计。

## 6. 研究数据与执行数据隔离

```text
Research Market Data
用于看板、研究、统计和人工判断

Execution Market Data
用于订单定价、风控、成交确认、仓位和对账
```

硬约束：

- Research API 不得被 Execution Runtime 调用为权威行情。
- 免费研究数据不得触发自动下单。
- 投研缓存不得覆盖订单、成交、仓位和 FinancialFact。
- 研究功能改动不得改变 Live Write、Kill Switch、审批、对账或执行契约。

## 7. 存储标准

初创阶段使用一套主要关系数据库，当前 SQLite 兼容架构按既有迁移纪律演进；生产规模需要时再迁移到 PostgreSQL，不为投研功能单独增加多套数据库。

必须持久化：

- 用户、角色和权限；
- 基金、账户和绑定；
- 策略定义和版本；
- 订单、成交、仓位权威事实和审计；
- FinancialFact 和正式会计结果；
- 申万分类映射和版本；
- 用户自选股与必要配置。

通常不长期保存：

- 一键个股查询的全部实时返回；
- 可按需重新获取的短期新闻列表；
- 页面演示数据。

这些数据优先使用缓存和最后有效快照。

## 8. 可靠性与测试

### 8.1 测试优先级

最高优先级：

- 交易、风险、权限、账本、迁移和对账；
- 业务公式和数据聚合；
- 外部 Provider 字段转换；
- 空数据不覆盖有效缓存；
- 部分失败和请求竞态；
- 页面结构守卫和类型检查。

低频纯展示页面不建立重型测试体系。

### 8.2 最小验收

前端标准改动至少通过：

```text
npx pnpm@9.15.9 type:check
相关页面结构守卫
必要时 production build
```

后端标准改动至少通过：

```text
python -m ruff check app tests
python -m pyright
相关 pytest
```

边界或持久化变化还必须通过仓库结构、文档一致性、迁移和安全检查。

## 9. 变更纪律

- 从指定正式基线建立独立分支，不直接修改正式基线。
- 一个分支只交付一个可衡量结果。
- 不把无关重构、依赖升级和历史清理混入功能开发。
- 不为架构好看批量移动文件。
- 页面变大时按自然业务区块拆分，不做全仓重写。
- 替换第三方数据源时，原则上只改 Provider 和对应测试。
- 外部接口变化不得迫使所有前端页面同步修改。
- 交易、权限、数据库、契约和生产行为变化使用高风险工作流。

## 10. 初创阶段禁止默认引入

没有明确瓶颈和验收目标时，不引入：

- Kubernetes；
- Kafka；
- 全面微服务；
- 服务网格；
- GraphQL；
- 前端微应用；
- 自研工作流引擎；
- 自研通用组件框架；
- 多套数据库；
- 全面事件溯源；
- 每个业务功能独立 Python 服务。

推荐长期保持：

```text
Vue 3 + TypeScript
Platform Backend 模块化单体
独立 Execution Runtime
关系数据库
Redis 缓存（需要时）
REST API + 必要的 WebSocket
Provider Adapter
GitHub CI
```

## 11. 非技术负责人验收清单

每个新功能至少回答：

1. 属于哪个业务模块？
2. 是否复用原平台 UI 和组件？
3. 前端是否直接调用第三方接口？
4. 外部字段是否先转换成平台字段？
5. 一个数据源失败是否会导致整页失败？
6. 是否改变交易执行、权限或权威账本？
7. 是否有明确口径、验收标准和测试？
8. 是否从正确基线建立独立分支？
9. 是否夹带无关修改？
10. 替换数据源时需要修改几处？

第 10 项的目标答案是：只替换一个 Provider 及其测试，不修改页面和核心业务逻辑。

## 12. 当前实施基准

对冲基金看板后续优化遵守本标准：

- A 股与宏观优先；
- 申万分类作为唯一板块维度；
- 一键个股数据按需查询，不需要 AI；
- 参考项目的数据逻辑吸收到 Platform Backend Provider；
- 所有客观数据模块独立加载和降级；
- 不复制参考项目 UI；
- 不修改 Execution Runtime；
- 不把研究行情作为真实执行权威输入。
