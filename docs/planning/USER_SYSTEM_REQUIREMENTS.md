# 用户系统产品需求与验收标准

状态：`implemented / automated verification passed / manual acceptance pending`<br>
适用版本：`Platform Experiment 0.9.0`  
Issue：`#117`  
分支：`feature/issue-117-user-system`

## 1. 文档定位

本文档只定义用户系统“必须实现什么”和“如何验收”，不规定具体代码组织。技术实现以 `USER_SYSTEM_TECHNICAL_ARCHITECTURE.md` 为准，开发顺序以 `USER_SYSTEM_EXECUTION_PLAN.md` 为准。

第一阶段目标是在现有平台内形成一个可本地运行、可测试、默认拒绝、权限清晰的完整闭环：

```text
注册申请
→ 后台审核
→ 登录并建立服务端 Session
→ 后端解析角色、权限和数据范围
→ 前端生成菜单、路由和操作能力
→ 用户管理个人资料和安全设置
→ 授权人员管理用户
→ 会员查看自己的基金持仓
→ 敏感操作留下审计证据
```

## 2. 产品原则

1. `platform-backend` 是浏览器用户、Session、业务角色、权限、会员持仓和用户审计的唯一权威。
2. 前端隐藏不构成授权；所有权限和数据范围必须由后端再次校验。
3. 未知角色、未知权限、异常状态和无法确认的数据范围均默认拒绝。
4. API-Key `admin` 不自动等同于业务 CEO，也不能自动读取或修改客户身份和持仓数据。
5. 资金、份额、净值、收益和收益率使用精确十进制边界。
6. 第一阶段不实现用户硬删除；使用审核、启用、停用和拒绝状态保留审计连续性。
7. CEO 的业务权限不能绕过现有 API-Key、LiveTradingSession、Kill Switch、对账、绝对限额和双 Live Write 闸门。
8. 不为用户系统重构无关交易、Runtime、风控或跨所价差模块。

## 3. 用户类型与主要场景

### 3.1 CEO

CEO 是最高业务权限角色，主要场景包括：

- 查看全部内部菜单和业务页面；
- 管理会员、员工、技术负责人和其他 CEO；
- 审核注册申请；
- 查看敏感用户字段；
- 查看和维护全部会员基金持仓；
- 查看用户安全记录和操作审计；
- 使用其业务权限允许的管理、风控和交易功能；
- 不能停用、降级或通过并发操作移除最后一个有效 CEO；
- 不能查看任何用户原密码。

### 3.2 技术负责人

技术负责人负责账号支持、系统运行和技术配置，默认边界为：

- 查看绝大多数内部页面；
- 管理会员和员工账号；
- 审核会员或员工注册申请；
- 查看完整联系方式以处理账号支持；
- 查看技术配置、异常、接口和运行信息；
- 不能修改 CEO；
- 不能创建、修改、停用或降级其他技术负责人；
- 不能提升自己或扩大自己的权限；
- 默认不能查看全部会员完整持仓；
- 默认不能修改会员持仓；
- 默认不能执行真实交易或修改核心风控参数。

### 3.3 员工

员工是内部只读为主的业务用户：

- 看到被明确授予读取权限的正常内部业务导航；
- 可以进入风控、策略、报表等与工作相关的只读页面；
- 可以进入用户管理的只读视图；
- 用户联系方式默认脱敏；
- 不得新增、编辑、启停、重置密码或修改角色；
- 不得执行真实交易或修改系统级配置；
- 未来可以通过新增权限点扩展，不把员工能力写死在页面组件中。

“正常内部导航”不代表自动获得当前或未来所有页面；新增敏感菜单仍须显式权限。

### 3.4 会员

会员是外部客户：

- 只查看和修改本人允许修改的资料；
- 只查看本人基金持仓；
- 不查看其他会员、员工或内部组织信息；
- 不进入用户管理、风控、运行监控、技术配置和交易管理；
- 菜单中直接显示顶级“个人账号”，不显示“风控管理”。

## 4. 第一阶段范围

### 4.1 必须完成

- 统一浏览器注册、登录、退出和当前用户查询；
- 服务端 Session、CSRF、会话撤销和权限即时失效；
- CEO、技术负责人、员工、会员四类固定业务角色；
- 固定角色到权限点映射；
- 菜单、路由、页面、字段、按钮、API 和数据范围授权；
- 登录页和同视觉体系的注册申请页；
- 个人资料、头像、密码和登录设备；
- 用户列表、详情、审批、创建、编辑、角色、启停、密码重置和强制退出；
- 会员基金持仓和基金单位净值展示；
- 敏感操作审计；
- 增量数据库迁移、初始 CEO、兼容和回滚；
- 本地完整闭环及完整 CI。

### 4.2 明确不做

- 社交登录；
- 短信或邮件验证码登录；
- 自动邮件或短信找回密码；
- 多租户、企业 SSO 或 IAM；
- 任意自定义角色、可视化权限编辑器或逐用户权限覆盖；
- 用户硬删除；
- 基金申购、赎回、支付、清算和结算；
- 独立对象存储；
- 浏览器真实交易认证方式的重新设计；
- 删除旧 Go 服务；
- 无关页面和交易模块重构。

## 5. 功能需求

### 5.1 注册申请

**USR-REG-001** 登录页必须提供“注册申请”入口，并保持现有浅蓝灰白、蝴蝶拓扑和中央卡片视觉骨架。

**USR-REG-002** 公开注册只允许申请：

```text
member
employee
```

公开页面不得显示或接受 `ceo`、`tech_lead`。即使客户端伪造参数，后端也必须拒绝。

**USR-REG-003** 注册字段至少包括：

- 用户名；
- 姓名；
- 邮箱或手机号至少一项；
- 申请身份；
- 部门或会员类型；
- 申请说明；
- 密码及确认；
- 隐私政策确认。

**USR-REG-004** 所有公开申请均进入待审核状态，不能自动登录。

**USR-REG-005** 用户名、邮箱和手机号必须执行规范化和唯一性校验。

**USR-REG-006** 注册接口必须具备请求频率限制、统一错误语义和审计，不能通过返回值枚举已存在账号。

**USR-REG-007** 审核人必须显式选择最终角色，不能自动执行 `role = requested_role`。

**USR-REG-008** 技术负责人只能批准为会员或员工；CEO 可批准为四类角色，但公开申请仍只能申请会员或员工。

**USR-REG-009** 拒绝申请必须填写理由；内部可查看理由，公开登录接口不披露审核人信息。

### 5.2 登录与退出

**USR-AUTH-001** 登录入口供会员和所有内部用户共同使用。

**USR-AUTH-002** 浏览器登录成功后建立服务端 Session；长期认证 Token 不得写入 `localStorage`、`sessionStorage` 或持久化 Pinia。

**USR-AUTH-003** 账号不存在或密码错误统一返回“账号或密码错误”。

**USR-AUTH-004** 密码验证成功后，可分别提示待审核、停用或临时安全锁定。

**USR-AUTH-005** 登录失败达到安全阈值后进入临时锁定；临时锁定与账号生命周期状态必须分离。

**USR-AUTH-006** 退出登录必须撤销服务端 Session，并在 Session 已失效时仍能幂等清除浏览器 Cookie。

**USR-AUTH-007** 角色、密码或账号状态变化后，旧 Session 在下一次鉴权时立即失效。

**USR-AUTH-008** 同一请求同时携带 Session Cookie 和 Bearer API Key 时必须拒绝歧义认证，不得静默选择其中一种。

**USR-AUTH-009** 生产环境浏览器用户接口只允许同源 HTTPS Session；不得开放任意跨域凭据请求。

### 5.3 个人账号

**USR-ME-001** 个人账号至少展示：

- 用户名；
- 展示名称和真实姓名；
- 头像；
- 手机号；
- 邮箱；
- 角色；
- 部门或会员类型；
- 账号状态；
- 注册时间；
- 最近登录时间。

**USR-ME-002** 用户名、角色、部门或会员类型及账号状态对本人只读。

**USR-ME-003** 用户可修改展示名称、头像、手机号和邮箱；修改联系方式必须重新验证当前密码或满足近期再认证要求。

**USR-ME-004** 个人资料必须保存在后端权威数据库，不得继续以浏览器 `localStorage` 作为事实来源。

**USR-ME-005** 个人账号页面包含：

```text
资料与安全
基金持仓
登录设备
```

会员默认进入“基金持仓”，内部用户默认进入“资料与安全”。

### 5.4 头像

**USR-AVATAR-001** 支持上传、替换、删除和默认头像。

**USR-AVATAR-002** 第一阶段支持 JPEG、PNG、WebP，最大文件 2 MB。

**USR-AVATAR-003** 后端必须解码验证真实格式、限制尺寸和像素数、重新编码并随机命名，不能信任扩展名。

**USR-AVATAR-004** 原始上传文件不得直接保留，不得写入源码目录或 Git。

**USR-AVATAR-005** 不接受用户输入任意外部头像 URL。

**USR-AVATAR-006** 失败时必须提供可理解的类型、大小、解码或服务错误提示。

### 5.5 密码与重置

**USR-PWD-001** 密码不得明文、可逆或出现在日志、响应、审计、测试快照或 Markdown 中。

**USR-PWD-002** 密码长度为 12—128 字符，后端拒绝常见弱密码、与用户名相同及包含完整邮箱或手机号的密码。

**USR-PWD-003** 用户修改密码必须输入当前密码、新密码和确认密码。

**USR-PWD-004** 修改成功后撤销该用户全部 Session，要求重新登录。

**USR-PWD-005** 管理员不得设置、查看或长期掌握用户临时密码。管理员重置密码时，后端生成一次性、短时有效的重置凭证，只返回一次并只保存其哈希。

**USR-PWD-006** 用户使用一次性重置凭证直接设置新密码；凭证单次使用、到期失效，成功后撤销旧 Session。

**USR-PWD-007** 重置凭证不能进入日志、审计详情、URL、Git 或前端持久化存储。

### 5.6 Session 与登录设备

**USR-SESSION-001** 用户可查看当前 Session 和其他登录设备摘要。

**USR-SESSION-002** 摘要至少包括创建时间、最近活动、IP 脱敏值、User-Agent 摘要和当前设备标记。

**USR-SESSION-003** 用户可退出单个其他 Session或全部其他 Session。

**USR-SESSION-004** CEO 和技术负责人可强制撤销普通用户的全部 Session；技术负责人不能撤销 CEO 或其他技术负责人的 Session。

**USR-SESSION-005** Session 必须具备绝对有效期、空闲有效期、撤销状态和授权版本。

### 5.7 用户管理

**USR-ADMIN-001** 用户列表支持分页、用户名、姓名、联系方式、角色、状态、创建时间和最近登录筛选或排序。

**USR-ADMIN-002** 列表显示头像、用户名、姓名、角色、联系方式、状态、注册时间、最近登录和操作入口。

**USR-ADMIN-003** 员工收到后端脱敏 DTO，不得先收到完整联系方式再由前端隐藏。

**USR-ADMIN-004** 用户详情采用详情页或抽屉，分区展示：

```text
基本资料
角色与权限
账号和 Session
会员持仓
登录记录
审计记录
```

**USR-ADMIN-005** 根据权限支持：

- 新增用户；
- 编辑用户；
- 审核或拒绝注册；
- 修改角色；
- 启用或停用；
- 发起一次性密码重置；
- 强制退出；
- 查看会员持仓；
- 查看操作记录。

**USR-ADMIN-006** 第一阶段不提供用户硬删除接口或按钮。

**USR-ADMIN-007** 停用、角色变化、密码重置和持仓修改必须二次确认并提示影响。

**USR-ADMIN-008** 关键可变记录使用版本号进行乐观并发控制；旧版本写入返回冲突，不静默覆盖。

### 5.8 会员基金持仓

**USR-HOLD-001** 会员只能查看自己的持仓；本人接口不得接受 `user_id`、`member_id` 或可替换的数据范围参数。

**USR-HOLD-002** CEO 默认可查看和维护全部会员持仓。

**USR-HOLD-003** 技术负责人默认只能查看会员基本资料，不能查看全部完整持仓；员工和会员不能查看他人持仓。

**USR-HOLD-004** 持仓至少包含：

- 基金名称；
- 基金代码；
- 持有份额；
- 最新单位净值；
- 持仓市值；
- 累计投入；
- 累计收益；
- 收益率；
- 净值更新时间；
- 份额确认时间；
- 持仓状态；
- 数据来源和数据时点。

**USR-HOLD-005** 权威公式为：

```text
持仓市值 = 持有份额 × 最新单位净值
累计收益 = 持仓市值 - 累计投入
收益率   = 累计收益 ÷ 累计投入
```

**USR-HOLD-006** 后端使用 `Decimal`，数据库和 API 使用规范化十进制字符串；前端浮点数不得成为权威结果。

**USR-HOLD-007** 累计投入为零时收益率返回 `null`；没有净值时不能用零代替；净值过期时明确标记 `stale`。

**USR-HOLD-008** `strategy_nav_snapshots` 不能直接作为客户基金单位净值。

**USR-HOLD-009** 第一阶段持仓是客户报告读模型，不是申购、赎回或正式清算账本；手工维护必须记录来源、时点、操作者和审计。

### 5.9 权限与导航

**USR-ACCESS-001** 底层采用：

```text
User → Role → Permission Set
```

第一阶段角色固定，但页面和接口使用权限点，不直接写角色判断。

**USR-ACCESS-002** 授权分为：

```text
权限点
目标角色范围
字段范围
数据范围
认证方式与安全等级
```

**USR-ACCESS-003** 内部用户显示：

```text
风控管理
├─ 用户管理
└─ 个人账号
```

会员显示顶级：

```text
个人账号
```

**USR-ACCESS-004** 个人账号使用统一真实路由 `/account`；旧 `/risk/profile` 重定向到 `/account`。

**USR-ACCESS-005** 菜单和路由由同一权限注册表生成，不在多个组件重复写角色判断。

**USR-ACCESS-006** 前端只有体验层权限；后端必须独立拒绝越权 API。

### 5.10 审计

**USR-AUDIT-001** 以下操作必须审计：

- 登录成功和失败；
- 退出登录；
- 注册、批准和拒绝；
- 新增或编辑用户；
- 角色变化；
- 启用或停用；
- 密码修改、重置凭证签发和使用；
- Session 撤销；
- 头像变化；
- 查看他人完整持仓；
- 修改会员持仓；
- 权限拒绝。

**USR-AUDIT-002** 敏感成功写操作与审计写入同一事务；审计失败时业务写入回滚。

**USR-AUDIT-003** 拒绝审计失败不能导致请求放行。

**USR-AUDIT-004** 审计记录操作者、认证方式、目标、事件、结果、Request ID、时间、来源 IP、原因和被修改字段名称。

**USR-AUDIT-005** 审计不得记录密码、密码哈希、原始 Session/CSRF/API Key、一次性重置凭证、完整请求体或完整客户敏感快照。

## 6. 账号生命周期与安全锁定

账号生命周期只包含：

```text
pending
active
disabled
rejected
```

允许转换：

```text
pending  → active
pending  → rejected
active   → disabled
disabled → active
```

临时登录锁定使用独立字段：

```text
failed_login_count
locked_until
```

当 `locked_until > now` 时，认证层返回临时锁定；到期后自动恢复，不修改账号生命周期状态。

## 8. 字段可见性与可修改性

| 字段 | 本人 | CEO | 技术负责人 | 员工查看他人 |
|---|---|---|---|---|
| 用户名 | 只读 | 只读 | 只读 | 只读 |
| 展示名称 | 可改 | 可改 | 可改普通用户 | 只读 |
| 真实姓名 | 只读 | 可改 | 可改普通用户 | 脱敏或只读 |
| 头像 | 可改本人 | 可改 | 可改普通用户 | 可见缩略图 |
| 手机/邮箱 | 可改，需再认证 | 完整可改 | 完整可改普通用户 | 后端脱敏 |
| 角色 | 只读 | 可改，受保护规则 | 仅会员/员工 | 只读 |
| 部门/会员类型 | 只读 | 可改 | 可改普通用户 | 只读 |
| 状态 | 只读 | 可改 | 仅会员/员工 | 只读 |
| 密码 | 修改本人 | 仅发起重置 | 仅发起普通用户重置 | 仅修改本人 |
| 完整持仓 | 本人 | 全部 | 默认仅本人 | 仅本人存在时 |

## 9. 非功能需求

### 9.1 安全

- 生产环境必须使用 HTTPS；
- 浏览器 Session 只允许同源；
- Session Cookie 使用 HttpOnly、Secure、SameSite；
- 写操作使用 CSRF Token 与 Origin 校验；
- 敏感管理操作要求近期再认证；
- 登录和注册具备账号及 IP 维度的速率限制；
- 敏感响应使用 `Cache-Control: no-store`；
- 密码使用 Argon2id；
- Session 和一次性凭证只保存高熵 Token 的哈希；
- 未配置安全参数时 fail-closed。

### 9.2 可维护性

- 用户身份只有一个权威后端；
- 角色映射集中定义；
- 菜单和路由共用权限注册表；
- 金融计算集中在后端；
- 数据库迁移只能追加；
- 不为了形式拆分大量微型模块。

### 9.3 性能和容量

第一阶段面向单机、小型私募规模：

- 用户列表必须服务端分页；
- 默认 `page_size` 不超过 50，最大不超过 200；
- Session 最近活动时间不得每个请求都写数据库，应节流更新；
- 头像读取支持私有缓存和 ETag，但不得公开永久缓存；
- 常用用户、Session、角色、状态、持仓和净值查询建立索引。

### 9.4 可观测性

至少监控：

- 登录成功、失败、锁定和异常比例；
- 活跃 Session 数；
- 401、403、409 和 5xx；
- 注册待审核数量；
- 审计持久化失败；
- 过期基金净值数量；
- 数据库迁移版本。

## 10. 本地验收标准

1. 公开注册只能提交会员或员工申请。
2. 待审核用户无法登录。
3. CEO 或技术负责人审核普通申请后用户可登录。
4. 会员只看到顶级“个人账号”。
5. 会员直接访问用户管理、风控或他人持仓 API 被后端拒绝。
6. 员工用户列表只收到脱敏联系方式，没有写操作按钮。
7. 技术负责人不能修改 CEO 或其他技术负责人。
8. 任何人不能修改自己的角色或停用自己。
9. 并发请求不能移除最后一个有效 CEO。
10. 停用、角色变化或密码变化后旧 Session 立即失效。
11. 同时携带 Cookie 和 Bearer 凭证的请求被拒绝。
12. 管理员重置密码不会设置或回显临时密码，只签发一次性重置凭证。
13. 重置凭证到期、重复使用或错误使用均失败。
14. 头像异常格式、超大文件、超高像素和路径穿越被拒绝。
15. 会员本人持仓接口不能指定其他用户。
16. CEO 查看他人持仓产生审计；普通会员查看本人持仓不产生高噪音审计。
17. Decimal 计算与测试向量完全一致。
18. 没有净值显示不可用，过期净值显示 stale，不显示零。
19. 一键本地启动能够完成注册、审核、登录、个人资料、用户管理和持仓闭环。
20. 现有 API-Key、LiveTradingSession、Market、FOK、PostOnly、TP/SL、Runtime 和 Live Write 安全测试无回归。

## 11. 实施前决策门

以下事项不阻塞设计文档，但在对应开发批次开始前必须核实：

1. 旧 Go/MySQL 用户库是否存在需要迁移的真实用户；若存在，必须先形成脱敏数量和角色分布清单。
2. 第一阶段会员持仓的初始数据来源是人工录入、一次性导入还是已有数据源；默认按 CEO 人工维护的客户报告读模型设计。
3. 正式生产域名和反向代理必须保持前后端同源；若改为跨域部署，需要重新评审 Cookie、CORS 和 CSRF。
4. 浏览器真实交易认证不属于本次用户系统；现有 Live 路由继续使用 API-Key 和 LiveTradingSession。未来若允许浏览器 Session 执行真实交易，必须另建 Critical Issue。
