## 3. Phase 1：交易安全底线

已完成：

- 未知账户、停用账户、未知标的和缺失 ContractSpecification 全部 fail-closed。
- 数量满足最小下单量和数量步长，限价满足价格步长。
- 凭证只保存 `secret://...` 引用。
- Live 受全局 `live_trading_enabled=false` 门禁保护。
- Runtime 通过 `INSERT OR IGNORE` 原子抢占 command，只有抢占成功者可以调用 Gateway。
- 重复 command 读取已持久化事件，不重复产生外部副作用。
- CI 覆盖 main、hardening 分支和面向 main 的 PR。
- Backend、Runtime、Frontend 的测试、类型检查和生产构建均纳入门禁。

验收：`Platform CI #58 / run 29983926790`，全部通过。

## 4. Phase 2：命令入口与结果恢复

实施目标：

1. 单腿交易统一通过 `TradeCommand + idempotencyKey`。
2. ExecutionBatch 每条腿生成独立 TradeCommand。
3. Batch 必须提供 `strategyInstanceId` 与 `idempotencyKey`。
4. TradeCommand 校验 Strategy、Account Binding、Account、Instrument 和 ContractSpecification。
5. `/trading/orders` 只保留为 deprecated 兼容入口。
6. `result_unknown` 从 Runtime Journal 恢复，不得重新下单。
7. Fill event 重放不能重复更新 Position 和 PnL。
8. 前端从 Backend Catalog 动态获取策略、账户、绑定与标的。

已落地：

- [x] 新增权威 `trade_commands.py` 服务。
- [x] Batch 两腿通过确定性 leg idempotency key 创建 TradeCommand。
- [x] Batch 和 TradeCommand 均采用数据库唯一键认领。
- [x] 新增 `POST /trading/orders/{orderId}/reconcile`。
- [x] Runtime event 校验 command_id 与 platform_order_id。
- [x] Fill 插入成功后才更新 Position、EconomicEvent 和 PnL。
- [x] Funding 面板删除 Demo UUID 硬编码，改为动态 Catalog。
- [x] 不支持资产或缺失合约规格时禁止提交并清晰提示。
- [x] Smoke Script 改为权威 TradeCommand / Catalog 链路。
- [x] 新增恢复、重放幂等和批次命令测试。
- [ ] 最终 CI 与文档验收完成后合并 PR #5。

详细记录：`V6-Phase2-命令入口与结果恢复.md`。

## 5. 当前明确限制

即使 Phase 2 合并，系统仍存在以下限制：

- 只有 Fake Gateway 具备完整下单闭环。
- Bybit/MT5 Gateway 尚未形成真实 Demo 下单、撤单和查单链路。
- `result_unknown` 当前只从 Runtime Journal 恢复，尚未主动查询外部 Venue。
- PnL 尚未完整使用 Contract Multiplier、Currency、Unit、Funding、Swap、Fee 和 FX。
- StrategyNavSnapshot 尚未按同一估值时点汇总全部绑定账户。
- 双腿失败后尚无自动反向平仓、替代对冲和 Kill Switch。
- 应用层认证、RBAC、双人审批和生产密钥托管尚未落地。

因此，禁止将当前版本解释为可实盘版本。

## 6. Phase 3 入口

Phase 3 只处理金融事实和账务正确性：

1. ExternalOrderEvent、Fill／Deal、Funding、Swap、Fee、Balance、Position 不可变事实。
2. 所有投影支持去重、重放和重建。
3. ContractSpecification、Currency、Unit 和 FX 进入正式 PnL。
4. StrategyNavSnapshot 按统一 valuation time 汇总全部账户。
5. 用金样本与交易所／MT5 账单逐笔核对。

Phase 3 完成前，PnL 和 NAV 仍只能作为工程演示结果。
