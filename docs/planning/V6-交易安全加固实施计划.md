## 1. 目标

当前阶段不扩展新策略、新页面或复杂基础设施，先建立内部交易平台必须具备的安全底线：

```text

+

+
异常结果必须可追踪
+
每次变更必须有测试、文档和 CI 留痕
```

Phase 1 完成后，系统仍只允许 Simulation / Fake Gateway。Paper 与 Live 需要后续阶段单独验收。

## 3. Phase 1 实施内容

### 3.1 订单安全校验

订单进入 Runtime 前必须完成：

- 账户必须存在。
- 账户状态必须为 `active`。
- 凭证引用只能保存为 `secret://...` 引用，不能保存真实密钥。
- 标的必须存在。
- 标的必须存在 ContractSpecification。
- 数量必须满足最小下单量和数量步长。
- 限价必须满足价格步长。
- Live 账户仍受全局 `live_trading_enabled=false` 门禁保护。

任何信息无法确认时一律拒绝，不允许默认放行。

### 3.2 Runtime 幂等

旧流程：

```text
先查询 command 是否存在
→ 再写入 command
→ 再调用 Gateway
```

存在并发竞态。

新流程：

```text
INSERT OR IGNORE 原子抢占 command_id
→ 只有成功插入者允许调用 Gateway
→ 重复调用读取已持久化事件
→ 首次调用仍执行中时返回 409，不重复执行
```

### 3.3 CI

GitHub Actions 必须覆盖：

- `main`。
- `hardening/**`。
- 所有面向 `main` 的 Pull Request。

检查项：

- Platform Backend：Ruff + Pytest。
- Execution Runtime：Ruff + Pytest。
- Frontend：类型检查 + 正式 Build。

## 6. Phase 1 验收

必须全部满足：

1. Platform Backend Ruff 与 Pytest 通过。
2. Execution Runtime Ruff 与 Pytest 通过。
3. Frontend `pnpm type:check` 与 `pnpm build` 通过。
4. 未知账户、未知标的、停用账户和不符合合约规格的订单均被拒绝。
5. 相同 Runtime command 只触发一次 Gateway。
6. Pull Request 中的代码、测试、计划、发布门槛和 Changelog 一致。

## 7. 下一阶段入口

Phase 2 只处理三个主题：

1. 前端所有交易写请求统一为 `TradeCommand + idempotencyKey`。

3. `result_unknown` 通过外部订单、成交和持仓查询恢复。

在 Phase 2 完成前，不应接入真实资金账户。
